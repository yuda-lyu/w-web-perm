## Security: caller identity

> Caller-identity responsibility (cross-package principle `dspec/使用者身分驗證原則.md`): the frameworks (`w-converhp`, `w-serv-hapi`, `w-serv-webdata`, `w-serv-orm`) do not verify tokens; this package does, entirely. The connection gate (`verifyConn`) and the executing identity (`getUserIdByToken`) are both fully verified (valid token, user present and active in this system, deployer authorization); hapi `apis` routes verify themselves; functions check the role on their own; public entries are limited to the ones named.

- **Connection gate and executing identity (since 2026-10-23, perm-run03)**: a data-channel request carries two tokens: the `Authorization` header (checked by `verifyConn`) and the `__sysToken__` of the request body (looked up by `getUserIdByToken`, which decides the user a function runs as). Both now go through the same full check `getAndVerifyClientUser`: your `getUserByToken` returns the user, the user must exist in the `users` table of this system (looked up by `mappingBy`) with `isActive: 'y'`, and your `verifyClientUser(user, from)` must return `true`. If the body token fails any step the function is **not executed** (nothing is written; the response carries a fixed message key such as `cannotFindUserFromToken`, `cannotGetUserFromPerm` or `userNoPermission`; srLog `getUserIdByToken-error`, never the token). The two tokens may belong to different users; each is verified, the framework does not compare them, and the function runs as the body token's user. Before this release `getUserIdByToken` only asked `getUserByToken` for an id, so a body token that was not in the `users` table, was disabled, or that `verifyClientUser` would refuse was accepted as long as the header token was valid.
- **What `verifyClientUser` sees**: for the body token it is called with `from = 'main'` (the same `apiType` as the connection gate, the only channel on which the framework looks up the executing identity), so a policy that branches on `from` behaves the same for both. The id returned to the framework (and written to `userId` / `userIdUpdate`) is the id **of the user's row in the `users` table of this system**, not the id your `getUserByToken` reported; they are the same with the default `mappingBy: 'id'` and differ when `mappingBy` is `'email'` or `'name'`.
- **Function-level role check (behavior change)**: `updateTargets`, `updatePemis`, `updateGrups` and `updateUsers` now refuse a caller whose row in the `users` table is not active **and** does not have `isAdmin: 'y'`, with the fixed message key `userNotAdmin`, before anything is read or written (srLog `requireAdmin-error`: function name and user id only). The `users` table of this system is the authority; the `isAdmin` that your `getUserByToken` reports is not used for this check (as for `isAdmin` elsewhere). Until now these functions relied entirely on your `verifyClientUser`; if it let non-administrators in (a read-only viewer, for example), they could write. The read-only functions (`getWebInfor`, `getStaEvent`, `getStaEventTable`) do not change state and are not restricted by this check. The bundled pages are administrator pages and are unaffected. Count `requireAdmin-error` in srLog to see whether anyone was relying on the old behavior.
- **Public entries**: there are none apart from the static front-end files. `/api/getUserByToken` and `/api/getPerm` verify a client user, `/api/getPermUserInfor` and `/syncAndReplaceTabs` verify an application user (`verifyAppUser`); the data channel only offers `select` on the tables (all writes go through the four functions above).

## Upgrade Notes

### Unreleased: external import is a `srcKey` difference sync, identity declarations are mandatory (2026-10-23, perm-run03, ADR-038) — two breaking changes

**1. `POST /syncAndReplaceTabs` is now a difference sync keyed by `srcKey` (breaking; no compatibility with the old call)**
- **What the caller must do**: every row of `rows` carries `srcKey`, a string chosen by the source, unique **within the `from`** and stable (for example an AD objectGUID); a row must **not** carry `id` (the internal primary key is generated by this system). The helper `provideTabs(url, keyTable, from, rows)` (`server/provideTabs.mjs`) now picks `srcKey` instead of `id`; if you build the request yourself, send `srcKey` and drop `id`. A batch is refused as a whole, nothing written, with `idNotAllowed` (any row carries an `id`, even an empty one; checked first), `srcKeyInvalid` (missing, blank, not a string, longer than 1978 bytes in UTF-8, or containing markup that would be rewritten), `srcKeyDuplicate` (same `srcKey` twice in the batch) `invalidRowsInPayload` (`rows` missing, not an array or empty: an empty batch is refused, it never means "delete everything of this `from`"; this key was kept from before) or `invalidRows` (a row that is not an object, a name or login-mapping key that collides with another source, ...). Direct calls with the old shape (`id` and no `srcKey`) get `idNotAllowed`.
- **What the server does now**: inside the table lock it reads the table once and matches the rows of that `from` by `srcKey`: a new `srcKey` is **added** with a new `id`; a known `srcKey` is **updated** in place (the `id` stays; a changed `name` is a rename and the references to it follow, see `opt.cascadeRename`); a stored row of that `from` whose `srcKey` is not in the batch is **deleted** and the references to it are cleaned; an equal row is left alone (**no write at all**). It returns `{ nAdd, nUpdate, nDel, nSame }`. Sending the same batch twice changes nothing the second time (`nSame` = all, same ids, same table digest). It no longer deletes the whole `from` and inserts again, so ids no longer change on every push and administrators' open pages are no longer invalidated by a push that changes nothing. Rows of other `from` values and admin rows (`from` empty) are never touched, and the `srcKey` namespace is per `from`.
- **Fields**: provided fields are owned by the source (a missing key means empty); the assignment fields `users.cgrups`, `grups.cpemis` and `pemis.crules` are optional (sent: written; missing: the stored value is kept, as before — except that with `mappingBy` `email` or `name` the value of `users.cgrups` is kept only while the login-mapping key of that `srcKey` is unchanged; if the key was changed, or the new key value is held by another stored row, nothing is carried over (the field becomes empty) and `syncAndReplaceTabs-keepAssign-skip` is logged with reason `identityConflict`, so that a login value can never inherit another person's authorization); `userId`, `timeCreate`, `userIdUpdate` and `timeUpdate` are never taken from the batch. `id`, `srcKey` and `from` are identity fields: the admin pages and `updateXxx` cannot set or change `srcKey` (a new admin row must have an empty `srcKey`; the "copy" button resets it; `saveFromNotAllowed` / `saveExternalRowChanged`, whatever `lockExternalRows` says).
- **Targets**: the `id` of a target is its name (permissions refer to it by that name), so it cannot be a generated value: for `targets` the `id` is the `srcKey` (send the target name as `srcKey`, never `id`). A `srcKey` that is already the `id` of a row of another source or of an admin row is refused (`invalidRows`, nothing written). Renaming a target is still "delete the old one, add the new one", as before.
- **One-time migration (first import after the upgrade)**: stored external rows written by the old synchronization have no `srcKey`. A row of the batch whose **`srcKey` equals the stored `id`** is taken to be that row: the server writes the `srcKey` into it in place (counted in `nUpdate`, the `id` and everything that refers to it stay), and from then on only `srcKey` counts. So the first import after the upgrade should send the **old `id` values as `srcKey`**; rows that find no partner are deleted and added as new rows (their references are cleaned, as for any other deletion). If the stored rows of one source contain a duplicate `srcKey`, or a `srcKey` claimed twice (one stored row has it, another row has it as its `id`), the batch is refused (`srcKeyConflict`); clean the source with `g_purgeFrom.mjs` and import again.
- **If a write fails halfway** the server restores the table and the referencing table to their previous content and answers `saveWriteFail` (if restoring fails as well it answers `saveWriteFail` and logs `syncAndReplaceTabs-restore-error`).
- **Warning about renumbered keys**: the page banner / `getWebInfor().syncWarns` and the log `syncAndReplaceTabs-srcKeyRenumber` now mean "same name, different `srcKey`" (a source that renumbers its keys deletes and adds every row, which cleans the references every time); a rename under the same `srcKey` is not a warning. The old `syncAndReplaceTabs-idRenumber` event no longer exists.
- **Known gap (needs a decision)**: the login mapping `mappingBy: 'id'` (the default) compares the `id` of the user your `getUserByToken` returns with the `id` of the row in the `users` table. Users imported **after** this upgrade get a generated `id`, so with `mappingBy: 'id'` they cannot be found by the id of the source system (rows migrated as above keep their `id` and still work). Until it is decided how `'id'` should relate to `srcKey`, use `mappingBy: 'email'` or `'name'` for externally imported users, or create the users who must log in in the admin pages.
- **New message keys**: `idNotAllowed`, `srcKeyInvalid`, `srcKeyDuplicate`, `srcKeyConflict` (in `server/procLang.mjs`, eng and cht). `buildSyncRowsNew` (`server/cascadeWrite.mjs`) and `countIdRenumber` (`server/syncKeep.mjs`) no longer exist; the implementation lives in `server/syncCore.mjs`.

**2. The identity of every referenced entity must be declared by the caller (breaking; the "compatibility" of the previous section is withdrawn)**
- **What changed**: `updateUsers`, `updateGrups` and `updatePemis` used to accept a save without the `refs` / `subject` declaration described below (references by name, no identity check). A save that **changes references** — adds or removes an active entry (`isActive: 'y'`) in the assignment field of any row (`cgrups`, `cpemis`, `crules`) compared with the stored row, or adds a row that carries references — now needs a declaration for every name involved, otherwise the whole save is refused, nothing is written, with the new message key `saveIdentityRequired` ("the data was updated or this page is out of date ... reload the page"). Saves that do not change references (renaming, other fields, a change of `mode`, deleting rows) need no declaration. Removing a reference is declared like adding one (the `ids` of the entity the administrator removed it from; `[]` for a dangling reference).
- **Custom clients must send it**: `refs: [{ name, ids }]` in the same options object as `baseline` / `returnRows` (see the previous section for the exact contract; the names to list are now the active entries added **and removed**), or `subject` for a dialog-style save that only changes the entries for one group / permission (the declared `subject.name` is the only name that may change then; another changed name is `saveRefChanged`). An incomplete declaration is still `saveRefChanged`, a declaration that does not match the stored entities is `saveRefChanged` / `saveSubjectChanged`, a malformed one `saveIdentityFormat`. **Pages opened before the upgrade must be reloaded** (they do not send the declaration for removals and, in older versions, not at all).
- **No extra lock without a declaration**: a save without a declaration is decided without reading or locking the referenced table. With a declaration the lock order is unchanged (referenced table first, then the table being saved).
- Count the srLog event `updateTabItems-identity-error` by `reason`; `identityRequired` is new (with `keyTable`, `userId`, `n` = number of names, never a name or an id).

**3. Caller identity** — see "Security: caller identity" above (the body token is verified like the header token; the four write functions need `isAdmin: 'y'` in the `users` table: `userNotAdmin`).

### Unreleased: a saved reference must still point to the entity that was selected, checked by the page and by the server (2026-10-23, perm-run02, ADR-037 Update)
- **Behavior change (the whole save is refused, nothing is written)**: authorization refers to other entities by **name** (users' `cgrups` to a group name, groups' `cpemis` to a permission name, permissions' `crules` to a target id). If the group / permission / target that the administrator has just assigned, or the group / permission a "belongs to" dialog was opened for, is **deleted, or deleted and re-created under the same name (a different `id`)**, before the save reaches the database, the save used to write the authorization onto the new entity without a word (it is a different entity that merely shares the name). Now the save is refused as a whole: the server answers `saveSubjectChanged` (dialogs) or `saveRefChanged` (list pages), and the page's own earlier check shows `relSubjectChangedGrup` / `relSubjectChangedPemi` (dialogs) or the same `saveRefChanged` (list pages); reload the page (close the dialog first) and redo the edit. Also refused: on a list page, another entity with the assigned name has been **added** since the selection; in a dialog, a **rename** of its group / permission (same `id`, another name, as before), or, when the group / permission was still unsaved in the list when the dialog was opened, another entity that has taken its name since. The check is made twice: by the page against its data store before it sends, and, as the final decision, **by the server inside the lock of the referenced table** (`grups` for users, `pemis` for groups, `targets` for permissions), so a delete-and-re-create that the page has not received by push yet no longer slips through. Before this release the dialogs' check was made by the page only, and the assignment columns of the list pages were not checked at all.
- **What is checked**: only references that **this save newly activates** (an entry with `isActive: 'y'` that was not active in the stored row), compared with the entity the administrator selected **at the moment of selecting it in the editor** (not at the time the page was loaded: an entity that someone else created after the page was loaded, and that the administrator then assigned, is not refused). Unchanged old references, disabled entries, removed entries and a change of `mode` are not checked (they are existing relations; deleting an entity already removed the references to it). A name that matched nothing when it was selected (a dangling reference) is still allowed, unless an entity of that name has appeared since. If several entities carried the name when it was selected (historical duplicates), the save is refused when that set of entities is not exactly the same any more.
- **Targets are identified by their `id`**: a target's primary key is its name and the external synchronization rewrites target rows under the same `id` every time, so for `crules` only "the target has been deleted" is detected; a target that is deleted and re-created under the same `id` is the same entity by definition (this is a design fact, not a defect; telling them apart by creation time would need a separate decision, and the creation time is not stable under the synchronization).
- **RPC contract (optional, only tightens)**: `updateUsers`, `updateGrups` and `updatePemis` take two more optional keys in the same options object as `baseline` and `returnRows` (optional third argument of the server function, second argument of the client call):
  - `subject: { id, name, saved }` for the "belongs to" dialogs: `updateUsers` (the group the dialog was opened for) and `updateGrups` (the permission). `id` and `name` are non-empty strings and `saved` is a boolean (the group / permission already existed in the page's data when the dialog was opened). Inside the lock of the referenced table the server reads it afresh and requires the same `id` with the same name (when `saved` is `false`: no other entity with that name); otherwise `saveSubjectChanged` (reason `gone`, `renamed` or `taken` in the log). It is checked before the baseline comparison, so "the group was replaced" is reported instead of the generic `saveStale`.
  - `refs: [{ name, ids }]` for the assignment columns of the list pages (`updateUsers` → `grups`, `updateGrups` → `pemis`, `updatePemis` → `targets`): one element for every reference the save newly activates, `name` being the referenced name (for `crules` the target id) and `ids` the array of entity ids (strings) that carried that name when the administrator selected it (`[]` when none did). The server requires that the ids of the entities carrying each declared name are, right now, exactly the declared ones (a deleted entity, a re-created one with another `id`, an additional entity with the same name all differ), and that no newly activated reference is missing from `refs` (`saveRefChanged`, reason `refChanged` or `refIncomplete`). Declaring a name that this save does not activate is harmless when it still matches.
  - **A malformed value is refused, never ignored**: a `subject` that is not an object, lacks `id` or `name` (or has an empty one), or has a `saved` that is not a boolean; a `refs` that is not an array, has more than 5000 elements, more than 1000 ids for one name, a duplicate name, a non-string name or a non-string id; `subject` sent to `updatePemis`; or either key sent to `updateTargets` (targets have no authorization column): all are answered with `saveIdentityFormat` before anything is read or written. The referenced table and its lock are chosen by the server from the table being saved; the client cannot name them, and the declared values are never trusted without the comparison above.
- **(Withdrawn in perm-run03, see the section above: a save that changes references without a declaration is now refused with `saveIdentityRequired`.) External callers and old pages are unaffected (compatibility)**: a call without `subject` / `refs` (or with `null`) behaves exactly as before: references by name, no identity check, the lock of the referenced table is not even taken; it never allows more than before. A page opened before the upgrade does not send them and keeps the old behavior until it is reloaded. The bundled pages send them (the three list pages send `refs`, the two dialogs send `subject`; the targets page sends neither). Making them mandatory for every write, as `requireBaseline` would for the baseline, is left for a later version.
- **It only takes back, never gives more**: the only saves that are newly refused are those that would have written a reference onto an entity other than the one selected; no save that was refused before is accepted now. To see how often it happens, count the srLog events `updateTabItems-identity-error` by `reason`: `gone`, `renamed`, `taken` (dialogs), `refChanged`, `refIncomplete` (list pages) and `format` (malformed value); the event carries `keyTable`, `userId`, `msg` (the message key) and `n` (how many names), and never a name, an id or a declared value.
- **Locks**: with `subject` / `refs` the save takes the lock of the referenced table first (outermost) and the lock of the table being saved inside it; this follows the same order as before (`targets` → `pemis` → `grups` → `users`: referenced table first), so it cannot deadlock with the external synchronization or the rename / delete cascade (a random concurrent test over the four tables, 60 rounds, is part of `test/unit-procCore-identity.test.mjs`). A save without `subject` / `refs` does not take it.
- **New message keys**: `saveSubjectChanged`, `saveRefChanged`, `saveIdentityFormat` (in `server/procLang.mjs`, eng and cht, fixed texts that contain no name). `relSubjectChangedGrup` / `relSubjectChangedPemi` stay as the page's own message (they name the group / permission).
- **Known limitations of this check**: (1) a row that the administrator copies or pastes carries no "selected in the editor" record, so its declaration is taken from the page's data at the moment of sending; that only covers the time between sending and writing, not the time between copying and sending. (2) A caller that sends no `subject` / `refs` still refers by name and gets no protection (see compatibility above). (3) Targets are identified by `id` (see above). (4) The page's own check uses its data store, which can be one push interval old; the server's check is the final decision.

### Unreleased: shared multi-user editing core (`w-serv-orm` 1.1.17), self-conflicts fixed (2026-10-23, perm-run01, ADR-037 Update)
- **Reload the admin pages once after the upgrade (behavior change)**: a page that was opened *before* the upgrade carries a baseline in the old fingerprint format. Its next save is refused with the new message `saveBaselineFormat` ("this page was opened with a different version of the system ... reload the page"), nothing is written, and the draft stays on screen. A custom client that builds its baseline with the old `makeBaseline(rows, keys)` must call `makeBaseline(rows, '<table name>')` (or use `buildBaseline` of `w-serv-orm/src/baseline.mjs` with the contract in `src/schema/contracts/`); a baseline in any unknown format is refused and never treated as "no baseline". Clients that send no baseline are unaffected.
- **Dependency**: `w-serv-orm` is now `^1.1.17` (the shared baseline functions, the per-instance table lock `withTabLocks`, `guardWrite`, and the `mustExist` option of `procOrm`). The backend no longer builds its own mutex.
- **What is compared now**: the digest of a row follows the table's write contract (the four contracts in `src/schema/contracts/`: client-written fields, server-managed fields, rank field `order`). Compared with the previous fingerprint: (1) `undefined`, `null` and `''` are the same empty value (a field cleared by one administrator no longer collides with a field that was already empty); (2) **the rank of the rows is part of the baseline**: another administrator who only reorders the rows (drag and drop) makes a save from an older view fail with `saveStale`, which was not a conflict before (the later save's order won); renumbering `order` without changing the rank, which is what every save and a synchronization of external rows do, is not a conflict; (3) numbers and strings are never converted into each other.
- **Your own save no longer blocks your next save (fixed gap)**: `updateXxx(rows, { baseline, returnRows: true })` returns the rows as they are stored after the write (read back inside the table lock), and the four list pages and the two "belongs to" dialogs put them into their data store at once; the baseline of the next edit is built from them. Before, saving again within about two seconds (before the next push) was refused as a conflict with yourself. The push that arrives later carries the same content and is not treated as someone else's update. Without `returnRows` the call still returns the plain message key `'saveTabItemsSuccess'`.
- **The "belongs to" dialogs follow the data (fixed gap)**: a dialog that is open and has no unsaved edit is rebuilt from a push that changes the table (and its baseline is renewed), so a later save is not refused for data the dialog never showed. With unsaved edits the dialog keeps its draft and its baseline and shows the notice, as before.
- **A cell editor that is still open counts as a draft (fixed gap)**: text typed into a cell but not yet committed with Enter used to be lost when a push arrived; now the page does not rebuild, keeps the baseline, shows the "data was updated" banner, and rebuilds once the editor is closed without a change (Esc or no edit). The "belongs to" dialogs have no cell editors.
- **The dialogs check that their group / permission is still the same one (new check, behavior change)**: the dialogs refer to the group (users' `cgrups`) or the permission (groups' `cpemis`) by **name**. If that group / permission is deleted, renamed, or deleted and re-created under the same name (a different `id`) while the dialog is open, the dialog shows the "data was updated" notice and its save is refused (`relSubjectChangedGrup` / `relSubjectChangedPemi`, nothing is written); close the dialog, reload the page and try again. A group / permission that is still unsaved in the list when its dialog is opened keeps the old behavior unless an entity with the same name appears meanwhile. (Since perm-run02 the server repeats this check; see the section above.)
- **Only-modify writes and server-managed fields**: updates and deletes carry `{ mustExist: true }` (a row that vanished is reported as `saveStale` and never re-created); `userId`, `timeCreate`, `userIdUpdate` and `timeUpdate` of an existing row are no longer taken from the client for admin rows (they already were not for external rows). The external synchronization keeps its semantics (`delAll({ from })` plus insert); only its lock is now the shared one.
- **New message keys**: `saveBaselineFormat`, `relSubjectChangedGrup`, `relSubjectChangedPemi` (in `server/procLang.mjs`, eng and cht).

### Unreleased: external rows are protected from the admin pages, and saves carry a load baseline (2026-10-22, F-23 / F-26, ADR-037)
- **External rows are protected from the admin pages (behavior change, `opt.lockExternalRows`, default `'y'`)**: a row whose `from` is a non-empty string is an *external row* (normally written by an application through `/syncAndReplaceTabs`, which only accepts a non-empty `from`); a row whose `from` is `''`, missing, or not a string (`null`, number, boolean) is an *admin row*. With `lockExternalRows: 'y'` the server enforces the following for the admin pages and for direct `updateTargets` / `updatePemis` / `updateGrups` / `updateUsers` calls alike. The whole save is refused, nothing is written and nothing is silently ignored: (1) a **new** row must have `from === ''` (a copy of an external row, a re-created row and a typed value are all refused), and an admin row cannot be turned into a row with a non-empty `from`: `saveFromNotAllowed`; (2) an external row cannot be **deleted**, cannot change its `from`, and cannot change any identity / structure field (every schema field except `id`, `from`, `order`, the assignment field and the server-managed fields `userId` / `timeCreate` / `userIdUpdate` / `timeUpdate`; for `users` this includes `name`, `email`, `isAdmin` and `isActive`): `saveExternalRowChanged`. The **assignment fields** (`users.cgrups`, `grups.cpemis`, `pemis.crules`; targets have none) stay writable from the admin pages ("Lv1"), but changing one on an external row needs the load baseline described below. The `order` of an external row belongs to the external source (a save does not renumber it), and an external row that differs from the stored one only in server-managed fields counts as unchanged. `opt.lockExternalRows: 'n'` restores the old behavior (only the `from` type check of the next item remains). The setting is returned by `getWebInfor()` as `lockExternalRows` (`'y'` / `'n'`).
- **The admin pages show external rows as read-only**: a lock icon with a tooltip in the first column, a banner above the list (rendered only when the table has external rows or there is a synchronization warning; otherwise the page is exactly as before), the `from` column read-only on every row (also with `lockExternalRows: 'n'`; before this release it could be edited in the list pages), the `isAdmin` / `isActive` check boxes of an external user disabled, "delete" skipping external rows with a notice, and "copy" resetting `from` to `''`. This is a convenience: the server is the enforcer (a paste into a read-only cell, see the known limitations below, is stopped by the page before sending and by the server anyway).
- **An administrator cannot disable or delete an external user (policy)**: identity fields, including `isActive` and `isAdmin`, belong to the external source. To disable an external user urgently, do it at the source (push the source's rows without that user, or with `isActive: 'n'`, and wait for the next synchronization) or remove the source's rows offline with `g_purgeFrom.mjs` (see the upgrade steps below). There is no local "disable override" on purpose (the next synchronization would overwrite it), and no way to "claim" an external row as an admin row (the source would then be refused for that id, `idOtherFrom`).
- **`from` must be a string (behavior change)**: whatever `lockExternalRows` says, a save that adds a row with a non-string `from` (`null`, number, boolean, ...) or changes the `from` of a stored row to a non-string is refused with `saveFromNotAllowed`. A historical row whose `from` is `null` and which is sent back unchanged is not refused, so a database that still holds such rows can be saved.
- **`updateXxx(rows, { baseline, returnRows })` (RPC contract, optional third argument of the server function, second argument of the client call)**: `updateTargets`, `updatePemis`, `updateGrups` and `updateUsers` accept `{ baseline }`, where `baseline` is `[[id, digest], ...]` describing the rows the edit is **based on**. Since 2026-10-23 (perm-run01) the baseline is the shared **`h1`** baseline of `w-serv-orm` (`buildBaseline` of `w-serv-orm/src/baseline.mjs`; each digest is `'h1:'` plus 14 lowercase hex digits; the **order of the array is the rank** of the row, by `order` then primary key) and the digest is computed from the table's **write contract** (`src/schema/contracts/{users,grups,pemis,targets}.mjs`: `fields` is the list of client-written fields, `serverOnly` the four server-managed fields, `orderKey` is `order`). Build it with `makeBaseline(rows, 'users')` of `src/js/rowDigest.mjs` (the second argument is now the table name, not a key list). The digest ignores `order` itself and the server-managed fields (a synchronization rewrites the time fields of every row of its source, and a save renumbers `order`, so neither may invalidate a draft); `undefined`, `null` and `''` are the same empty value. Inside the table lock the server compares the **whole table** with the baseline: if any stored row has a different digest from the one the baseline lists for its `id`, a row was added or removed, **or the rank of the rows is different (someone only reordered them)**, the whole save is refused with `saveStale` (reload the page and redo the edit) and nothing is written, whether or not that row is one the save would write. Renumbering `order` without changing the rank (a save of the table, a synchronization that shifts the `order` of its own rows) is not a change. A baseline in any other format (not an array, a duplicate `id`, a version other than `h1`, **or the fingerprint format of releases before this one**) is refused with `saveBaselineFormat` (reload the page) before anything is read or written; it is never treated as "no baseline". Every other key of the client's second argument is ignored (only `baseline`, `returnRows` and, since 2026-10-23, `subject` and `refs` are taken — see "Upgrade Notes: a saved reference must still point to the entity that was selected" — and nothing of it is passed on to the ORM). **With `returnRows: true` a successful call returns `{ msg: 'saveTabItemsSuccess', rows, others }` instead of the plain message key**: `rows` are the rows of the table as read back inside the same table lock after the write (sorted by `order`), `others` holds the rows of the referencing table when the save rewrote it (rename / delete cascade, keyed by table name, otherwise `{}`). The bundled pages use it to refresh their data and baseline at once instead of waiting for the next push. **A custom client that sends no baseline keeps the old behavior for admin rows (last writer wins, ADR-013), but cannot change the assignment fields of an external row: it gets `saveBaselineRequired`.**
- **[Updated in perm-run03: the external synchronization is no longer `delAll({ from })` plus insert; it is a `srcKey` difference sync, see the first section of these notes. The lock sharing described here is unchanged.]** **One lock manager, only-modify writes, server-managed fields are not taken from the client (2026-10-23, perm-run01)**: the backend takes the lock of every table from the `w-serv-orm` instance (`withTabLocks` / `guardWrite`, `^1.1.17`); the admin saves, the external synchronization and the cascade write to the referencing table share the same lock per table (acquisition order: referenced table first, referencing table inside: `targets` → `pemis` → `grups` → `users`). Updates and deletes written by a save carry the server-composed option `{ mustExist: true }`: a row that is no longer there is never re-created (`rowNotFound`, reported as `saveStale`). `userId`, `timeCreate`, `userIdUpdate` and `timeUpdate` of an existing row are never taken from the client any more (for admin rows as well as for external rows); a row that differs only in those fields is not written.
- **The bundled pages bind the baseline when the edit draft is created, never at save time**: the four list pages compute it where they rebuild their rows from the data store (so a push from the server replaces draft and baseline together when there are no unsaved edits; with unsaved edits the draft and its baseline are kept, see the next item), and the two "belongs to" dialogs compute it when they open and keep it until they are opened again. A baseline taken at save time would only prove that the store is new, not that the edited content is. The "belongs to" dialogs (group page "users", permission page "groups") also changed how they save: they send the whole table as the store snapshot taken **at save time** and change only the one entry of the rows the administrator actually changed (`src/js/relDialogSend.mjs`); every other row goes back unchanged, so a user or group that someone else, or an external synchronization, added while the dialog was open is no longer deleted by the save.
- **[Updated in perm-run03: external sources no longer push `id`s (an `id` is refused); the stability that matters is the `srcKey`, and an unchanged push no longer writes at all. Note (1) below is superseded.]** **Concurrent editing: first writer wins, and the page no longer drops a draft silently (behavior change, 2026-10-22, run11; ADR-037 Update)**: when the stored table differs in **any** row (content, ignoring `order` and the server-managed fields), or in the set of rows (a row added or removed), from the table the administrator's draft was loaded from, the whole save is refused with `saveStale` and nothing is written: no partial save, no lock; the first writer wins and the other must reload. Before this change only the rows the save would write were compared, so another administrator's edit of a *different* row did not make a save fail; now it does. The comparison is by content: an external synchronization that rewrites its rows without changing their content (the creator / time fields and `order` change) does not change the table digest, so it does not block an administrator; one that really changes a row does (the external source is the master). A save from a client that sends no baseline is not compared (admin rows: the later write wins, ADR-013; changing the assignment fields of an external row: `saveBaselineRequired`). **The bundled list pages keep an unsaved draft**: when a push brings new data while the page has unsaved edits, the draft and the baseline it was loaded with are kept (nothing is rebuilt), and, if the table now differs from that baseline, a banner explains that the data was updated by someone else or by a synchronization, that saving will be rejected, and offers a "Reload" button that discards the draft and reloads the table (`staleDraftNotice` / `staleDraftReload`); a page without unsaved edits is rebuilt from the push as before. The two "belongs to" dialogs show `staleDraftNoticeDialog` when a push arrives while they hold unsaved edits and the table differs from the one they were opened with (close and reopen to reload). Notes: (1) an external source that pushes rows **without `id`** gets new random primary keys on every push, which changes the set of rows and therefore the digest every time; keep `id` stable (as already advised) or administrators' open pages will be refused after each synchronization; (2) *changed in 2026-10-23, perm-run01*: the rank of the rows is part of the baseline now, so another administrator who only changes the order of rows (drag and drop) **does** make a save from an older view fail, while a pure renumbering of `order` that keeps the rank (a save of the table, an external source shifting its own rows) does not; (3) `saveStale` text and the position of the reload button are covered by `test/e2e-external-rows.test.mjs` E2E-016 to E2E-024.
- **[Updated in perm-run03: rows are matched by `srcKey` (not by `id`, `email` or name), the matching rules for rows "without `id`" below no longer apply; keeping a missing assignment key, the `cascadeRename` behavior and the not-keepable skip still hold.]** **External synchronization keeps the assignments made in the admin pages**: a `users` row pushed to `/syncAndReplaceTabs` **without a `cgrups` key** keeps the `cgrups` stored for the matching row of the same `from` (matched by `id`; a row without `id` is matched by `email` / `name` when `mappingBy` is `'email'` / `'name'` and exactly one stored row of that source has the value; no match gives `''`); a pushed `cgrups` key, even `''`, is taken as given. When `mappingBy` is `'email'` / `'name'`, a row matched by `id` keeps its assignment only if its `email` / `name` is unchanged (an `id` that now points to a different login identity is treated as a different user: the assignment is cleared rather than moved), and a stored value that could not pass the normal pre-write validation is not kept either (logged as `syncAndReplaceTabs-keepAssign-skip`). `grups.cpemis` and `pemis.crules` are treated the same way (all three are assignment fields that the admin pages may write): a `grups` row without a `cpemis` key, or a `pemis` row without a `crules` key, keeps the stored value of the same entity of the same `from`; a pushed key, even `''`, is taken as given. Groups and permissions have no login key, so the entity is identified by `id`; a row without `id` (the server gives it a new random primary key) is matched by name and exactly one stored row of that source must have that name. A rename under the same `id` keeps the value while `opt.cascadeRename` is on (the references are rewritten to the new name, so it is the same entity); with `cascadeRename: false` the references do not follow, the name is the identity, and the value is not moved to the new name (logged as `syncAndReplaceTabs-keepAssign-skip` with `reason: 'identityConflict'`, as is a row without `id` that matches several stored rows with the same name). An `id` that is not stored for that source is a new entity (`''`). Stored values that could not pass the normal pre-write validation are not kept (`reason: 'notKeepable'`). **Behavior change for `cpemis` / `crules`**: before this release a push without these keys cleared what the admin pages had assigned, on every push; now it is kept. If your application relied on the push to reset the assignments, send the key explicitly (for example `cpemis: ''`). Renumbered ids are covered by the next item.
- **[Superseded in perm-run03: the warning now means the same name under a different `srcKey`; the log event is `syncAndReplaceTabs-srcKeyRenumber`. The advice "keep ids stable or omit ids" is replaced by "keep `srcKey` stable". The wording of the page banner (`syncWarnIdRenumber`) still says "ids" because changing it would change two standard images.]** **Warning when an external source seems to renumber its ids**: when a push for `grups` or `pemis` contains, for one `from`, a row whose name belonged to a stored row of that source with an id that is not in the push (the same name under a different id), the server logs `syncAndReplaceTabs-idRenumber` (table, source and count only) and lists `{ keyTable, from, n, time }` in `getWebInfor().syncWarns`; the admin page shows a banner, and the entry is removed by the next push of that source without the pattern. It is kept in memory only (a restart clears it) and does not change what the push does: the advice "keep ids stable (or push without ids)" above still applies, because a vanished id is a deletion and removes the references to it.
- **Two new confirmations in the admin pages**: saving a new group, permission or target whose name is still referenced by active entries (users' `cgrups`, groups' `cpemis`, permissions' `crules`; the reference was dangling until now) asks first, and says how many users (groups, permissions) will get, or be limited by, the new entity and how many of them refer to it with `AND` (a target's rule entries have no mode, so no `AND` sentence); adding it is allowed, saving only continues after "Yes". When a duplicate name involves an external row, the warning icon of the name cell says that the external source already uses the name (the server still refuses an admin row whose name an external row has, and an external push whose name an admin row has, as before).
- **Upgrade steps (stop the backend first)**: after the upgrade every row whose `from` is a non-empty string is an external row and becomes read-only in the admin pages, including rows that were typed or inherited by "copy" in the admin pages in the past. The development seed now writes `from: ''` for the users `peter`, `mary` and `john` (it was `teamA`; `g_initialData.mjs`, `src/schema/tables/users.mjs`), so **they are admin rows, not external rows**; a database created with the earlier seed still carries `teamA` on them and should be rebuilt with `g_initialData.mjs`. There is no tool that turns an external row into an admin row: rows that were created in the admin pages with a non-empty `from` have to be purged and re-created, or keep the old behavior with `opt.lockExternalRows: 'n'`. **Running the tools from the installed package**: `g_fixFromType.mjs`, `g_purgeFrom.mjs` and `g_authRefsClean.mjs` and their cores (`server/tools/fromTools.mjs`, `server/tools/authRefsClean.mjs`, `server/tools/authRefsAudit.mjs`, `server/tools/nameDupReport.mjs`) are part of the npm package (they do not depend on `test/`, which the package does not ship). Run them with the **working directory set to the project root of your deployment**, using the path inside `node_modules`, for example `node node_modules/w-web-perm/g_purgeFrom.mjs` or `node node_modules/w-web-perm/g_fixFromType.mjs --apply`. The data folder is relative to the working directory (`g_getSettings.mjs`: `dbUrl: './db'`, database name `wperm`, so the data lives in `./db/wperm` of the folder you run it in; use `--db <folder>` for another location; the tools stop with an error when `<folder>/wperm` does not exist, but they do not check that it already holds your data, so point them at the right folder), and the backup files they write (`backup-<time>.json`, `purgeFrom-backup-<time>.json`, `authRefsClean-backup-<time>.json`) also land in the working directory. The packages they import (`w-orm-lmdb`, `w-serv-orm`, `wsemi`) are resolved from the installed package location, so they must be installed in your project. The offline audit helpers that read an export file, `server/tools/authRefsAudit.mjs` and `server/tools/nameDupReport.mjs`, are run the same way (`node node_modules/w-web-perm/server/tools/nameDupReport.mjs <export.json>`). ### Unreleased: objects carrying a numeric `length` key, and non-array `rows` (2026-10-20)
- **`rows` must be an array (behavior change)**: `updateTargets`, `updatePemis`, `updateGrups` and `updateUsers` now reject a `rows` argument that is not an array (a string, number, `null`, `undefined`, a plain object, or an object carrying a numeric `length` key), or whose elements are not non-empty objects (`[null]`, `[{}]`, `[""]`, `[[]]`), with `saveRowFieldInvalid` and leave the table unchanged. Previously such input was treated as an empty table: the whole table was cleared and the call reported success (in the `modeEditUsers: 'for:grups'` mode it was silently ignored). An empty array `[]` is still accepted (it clears the table). The bundled front end and `/syncAndReplaceTabs` (which already required a non-empty array) are not affected.
- **Objects are iterated by their own keys**: a field or key named `length` is an ordinary key everywhere user-supplied objects are walked (write validation, the `cgrups` / `cpemis` / `crules` JSON strings evaluated by `getPerm` / `getPermUserInfor`, and the list pages). Before, lodash treated such an object as an array-like of that length: real keys were skipped (for example a group listed next to `"length": 0` was ignored, so its rules evaluated to `n`) and a huge `length` made the call spin or run out of memory.
- **`/syncAndReplaceTabs` rows must be non-empty objects (behavior change)**: every element of `rows` must be an object with at least one key. A push containing a string, number, `null`, array, boolean or an empty object `{}` is rejected as a whole with `invalidRows` before anything is deleted. Before, a non-object element made the call fail with an engine message (for example `Cannot create property 'from' on string 'abc'`) that was returned to the application, and an empty object in a multi-row push was written as a blank row with a generated id. A row that carries no schema field at all (for example `{"foo":1}`; it would map to an all-empty row) is rejected the same way.
- **Authorization lookups use the exact id, not a lodash path (behavior change, tightening)**: `getUserRules` (used by `getPerm` / `getPermUserInfor`), the SDK `perm().active(name)` and the edit dialogs of user groups, group permissions and permission rules now look a target, group or permission up by its exact name as an own property. Before, a name containing `.` or `[` was resolved as a path: when only `A` was granted, targets `A.0` and `A[0]` evaluated to `y` (and `A.length` to `1`), and inherited names such as `toString` could be returned. Names that are themselves keys (for example a target called `A.0` granted by a rule named `A.0`, or one called `constructor` / `__proto__`) are granted as usual. In the admin session of `modeEditUsers: 'for:grups'`, a database id containing `.` or `[` can no longer be taken over by another row's nested field. The edit dialogs also keep an item named `__proto__` when saving (before, it was shown as enabled but silently dropped from the saved JSON).
- **Object-form entries are named by their key (behavior change, tightening)**: in the `cgrups` / `cpemis` / `crules` JSON of the form `{"<name>": …}`, an inner `name` field no longer renames the entry (before, `{"A":{"name":"B","isActive":"y"}}` granted `B` while the edit dialogs showed `A`). The array form `[{"name":"A","isActive":"y"}]` is unchanged. The permission-rule edit dialog also reads object-form values (`{"A":{"isActive":"y"}}`) the same way as the server, so such a rule is no longer shown as disabled (and revoked on save).
- **`/syncAndReplaceTabs` blank rows**: a row that carries no content outside the server-managed fields is rejected with `invalidRows`. Server-managed fields are `from`, `userId`, `timeCreate`, `userIdUpdate` and `timeUpdate` (the server overwrites them); a field value counts as content when it is a non-empty string, a finite number (`0` included) or a boolean (`""`, `null`, `[]` and `{}` do not).
- **Field values must be scalar (behavior change)**: every field of a row written by `updateTargets`, `updatePemis`, `updateGrups`, `updateUsers` or `/syncAndReplaceTabs` must be a string, number, boolean, `null` or absent. An object, array or other non-scalar value is rejected as a whole before anything is deleted (`saveRowFieldInvalid` for the admin pages, `invalidRows` for `/syncAndReplaceTabs`; the existing rows stay unchanged). No table has an object-typed field: `cgrups`, `cpemis` and `crules` are JSON **strings**. Before, a nested string such as `{ "description": { "value": "<script>" } }` slipped past the write validation and was silently rewritten when stored.
- **Edit dialogs decode authorization data exactly like the server (behavior change, tightening)**: `cgrups` / `cpemis` / `crules` may also be written in the array form `[{ "name": "A", "isActive": "y" }]` (an external application writing directly; `getPerm` / `getPermUserInfor` already honor it). The edit dialogs for user groups, group permissions and permission rules (and the two "belongs to" dialogs) used to look entries up by name, showed such entries as disabled, and saving revoked the authorization. They now decode both forms with the same function as the server, so what a dialog shows matches what is authorized, and saving keeps the authorization unchanged. Details: (1) in `cgrups` / `cpemis`, an entry with `isActive: "y"` but a missing or invalid `mode` (anything other than `"OR"` / `"AND"`) is not honored by the server; the dialogs now show it as disabled (before, object-form entries like that were shown as enabled and saving filled in `OR`, silently granting it) **[superseded on 2026-10-21 by the "Conflicting or ambiguous authorization data" item below: such an entry is now honored by the server as a restriction (it only intersects with the other entries and never grants on its own), and the dialogs show it as an enabled `AND` entry]**; (2) in the object form `{ "<name>": { "name": …, … } }` the outer key is the name and an inner `name` is ignored, also in the "belongs to" dialogs (before, saving there re-pointed the grant to the inner name); (3) the three direct editors always save the object form `{ "<name>": … }`, the two "belongs to" dialogs rewrite the stored string only when its decoded content changes; (4) see the next two items for the new merge rule (order independent) and for the case the object form cannot hold (the same name active as both `AND` and `OR`).
- **The result of merging `AND` entries no longer depends on their order (behavior change, 2026-10-21, ADR-033)**: in `cgrups` / `cpemis` / `crules` an entry that is **not listed counts as `n`**. For each target the result is: `y` ⇔ (if any active `OR` entry exists: at least one `OR` entry gives `y`) and (every active `AND` entry gives `y`); a level with no active entry at all gives `n`. Before, with no `OR` entry the first `AND` entry was the base and the other `AND` entries only constrained the targets they listed, so the stored order of two partial `AND` entries decided the result; with an `OR` entry present an `AND` entry that did not list a target did not constrain it. The same rule applies to the permissions inside a group and to the groups of a user, and the order of entries, object keys or array elements never matters. Two consequences follow (they were not spelled out in the ruling and need your confirmation): (1) repeating the same rule name inside one array-form `crules` now gives `y` only if every repeated entry is `y` (before the last entry won); (2) an `AND` group or permission that holds no rules at all counts as "all `n`": it removes every target granted by the `OR` entries (before it was ignored or zeroed everything depending on its position). **It can only take authorization away, never add it**, compared with the old rule (verified over 223,384 exhaustive cells). Users whose authorization used to rely on "an `AND` permission does not list this target" lose that target. **Before upgrading, audit your data**: export `{ users, grups, pemis, targets }` as JSON and run `node test/tools/authMergeReport.mjs --audit <export.json>`; it lists, per user, the targets the new rule takes away (`被收回`), whether the old result depended on the stored order, and groups/permissions with duplicate names. (Limitation: a rule whose name cannot be used as a property key, e.g. `{ "toString": null }`, made the old rule throw, so such a user effectively had **no** authorization; the audit skips that rule like the new server does, so those users' `被收回` figures are not the old server's real result.) The permission-rule edit dialog stays two-state (checked / unchecked): unchecking a target (stored as `n`) is the same as not listing it, and saving a dialog that wrote unlisted targets as explicit `n` no longer changes anything (under the old rule such a save could silently revoke access).
- **Data that the object form cannot hold is not rewritten (behavior change, fail-closed)**: when a `cgrups` / `cpemis` array (written directly by an external application) has the same name active as both `OR` and `AND`, the edit dialogs refuse to write it (the object form holds one mode per name, and keeping either side would add or remove authorization). One more case is refused the same way (2026-10-21, ADR-035): an active entry without a usable name. (A level whose active entries **all** have a missing or invalid `mode` was refused too, but since 2026-10-22 it can be saved: the dialogs write unchanged entries back with their original `mode`, so nothing more is granted; see the item on the edit dialogs below.) A direct editor with changes, or a "belongs to" dialog with a change on such a row, is not saved and shows a fixed message naming the affected names; the stored string is left untouched, and a dialog opened and saved without changes returns the original string. The data has to be corrected at its source. Data written by the dialogs themselves (the object form) is never affected. The dialogs no longer keep the order of the stored entries and no longer refuse an integer-like name such as a group called `1` (those protections only existed because the order used to matter; see the previous item).
- **List pages decode like the server**: the user, group and permission lists count and name the groups, permissions and rules of an array-form `cgrups` / `cpemis` / `crules` the same way as the server (before, the user list used the array index as the group name and the permission list counted 0 rules). Display only; nothing is written.
- **`/syncAndReplaceTabs` requires non-empty string names and ids (behavior change)**: for `grups` and `pemis` the `name` of every row, and for `targets` the `id` of every row, must be a non-empty string (as the admin pages already required). A missing value, an empty string, or a non-string (number, boolean, `null`) rejects the whole push with `invalidRows` before anything is deleted. Before, a group or permission with `name: ""` was stored and honored by `getPerm` / `getPermUserInfor`, but the edit dialogs treated it as invalid and removed it on the next save. `users` rows are not affected.
- **"Belongs to" dialogs open after adding a row, and pair rows by identity (bug fix, 2026-10-21)**: a user or group added in the admin pages starts with an empty `cgrups` / `cpemis` string. The two "belongs to" dialogs (group page "users", permission page "groups") decoded every row of the table and failed on the empty string, so as soon as one newly added row existed none of those dialogs could be opened. An empty or unparsable string is now treated as "no memberships" (the same as the server does); a row whose string was unparsable and whose membership you did not change is saved back unchanged (as long as that stored string was not changed by someone else while the dialog was open; the dialogs write the whole table back, so the usual last-writer-wins applies). In addition, when such a dialog saves, each of its rows is now matched to the stored user / group by its `id` (a group must also still have the same `name`) instead of by its position in the list, so a list that was re-ordered while the dialog was open can no longer write a membership to the wrong user or group. If a user or group shown in the dialog has been deleted (or a group renamed) in the meantime, nothing is saved and a message asks you to reload the page. The same re-matching by `id` applies when the direct editors (user groups, group permissions, permission rules) hand their result back to the list page, and the "select all / none / invert" buttons of the group page's user dialog now address rows by user `id` (user names may repeat). Note that these dialogs still write the whole table back: a user or group that someone else adds while the dialog is open is not part of the dialog and is removed by that save. **[Superseded on 2026-10-22: the dialogs now send the store snapshot taken at save time and change only the rows the administrator changed, and they carry a load baseline; see the item "The bundled pages bind the baseline when the edit draft is created" of the 2026-10-22 section above.]**
- **A rule name that cannot be a property key no longer fails the whole query (bug fix, 2026-10-21)**: `crules` is valid JSON even when an element of the array form has a `name` such as `{"toString": null}`, which JavaScript cannot turn into a key. Before, `getPerm` / `getPermUserInfor` threw for every user holding that permission and returned the engine message (`Cannot convert object to primitive value`) to the calling application. Now that element is ignored (it matches no target) and the rest of the rules are evaluated as usual; the same holds for the permission-rule edit dialog and the list pages. Any other failure while evaluating a user's rules is logged and answered with the fixed key `cannotGetUserRules`, never with the engine message.
- **Group and permission names must be unique (behavior change, 2026-10-21, F-02)**: authorization looks groups and permissions up by name (the server takes the first row with that name), so two rows with the same name made the result depend on the database row order. The admin pages already rejected duplicates; `/syncAndReplaceTabs` now rejects a push for `grups` or `pemis` with `invalidRows` (before anything is deleted, nothing changes) when two rows of the push share a `name`, or when a `name` is already used by a row of another `from` (rows of the same `from` are replaced by the push and do not count). Names are compared exactly: `Admin`, `admin` and `Admin ` are different names. The admin lists reject duplicates with the new key `nameDuplicate` (before: `saveRowFieldDuplicate`; users' `email` and targets' `id` are unchanged), and the server only refuses when the save creates or touches the duplicate (duplicates already in the database do not make a save sent to the API fail, so they can be repaired), and a save now always matches the stored rows of groups and permissions by `id` (before, by `name` unless the database already held two rows with the same name): a rename is an update that keeps the creator and creation time, and these single saves, which used to report success while leaving two rows with the same name or losing the rename, now give the intended result: renaming a row and adding a new row with its old name, deleting a row and adding a new row with the same name, and a chain of renames (`A`→`B` and `B`→`C`). Two rows of the submitted table with the same `id` are refused with `saveRowFieldDuplicate`. **Cleaning up existing duplicates** (nothing is deleted or renamed automatically): run `node server/tools/nameDupReport.mjs <export.json>` (read-only; the file is `{ users, grups, pemis, targets }`, each an array of rows) to list every same-name group and which `users.cgrups` / `grups.cpemis` refer to it; then rename or delete one of the rows in the admin pages. **References are matched by name and renaming does not update them (F-07 is not implemented)**: renaming or deleting one row makes every reference to that name point to the remaining row or to nothing, so list the references with the tool first and check each user's authorization afterwards (`getPermUserInfor` / `getPerm`). **The admin pages are stricter than the server**: the group / permission lists still mark every duplicate name and refuse to send the save until one of the rows is renamed or deleted, so with duplicates already in the database nothing else can be saved from the admin page until the duplicates are fixed (known gap, listed for a decision) **[resolved on 2026-10-21: the lists now use the same rule as the server — see the "Conflicting or ambiguous authorization data" item below]**.
- **The user mapping key must identify one user (behavior change, 2026-10-21, F-14)**: with `mappingBy: 'email'` or `'name'`, a login looks the user up in the permission system by that field. Before, when several active users matched, the first one in the database was taken, so the signed-in identity depended on the row order. Now more than one active match is refused (`ambiguousUserFromPerm`, logged with `mappingBy` and the number of matches but not the value; the login page redirects as for any refused login, and the data channel answers `permission denied`); no match still gives `cannotGetUserFromPerm`. To keep the key unique, `/syncAndReplaceTabs` for `users` now rejects the whole push with `invalidRows` when `mappingBy` is `'email'` or `'name'` and an active (`isActive: 'y'`) row has an empty or blank value in that field, repeats the value of another active row of the push, or uses a value held by an active row of another `from` (inactive rows are ignored; values are compared exactly). With the default `mappingBy: 'id'` nothing changes for `/syncAndReplaceTabs` (emails may stay empty or repeated there) — but note that the admin user list itself still requires a non-empty, unique email on **every** row (active or not), so such rows have to be corrected before the admin page can save users **[superseded on 2026-10-21: only an email that the current save creates or touches is checked, see the "Conflicting or ambiguous authorization data" item below]**. **If you run with `mappingBy: 'email'` or `'name'`**, run `node server/tools/nameDupReport.mjs <export.json> --mapping-by email` (or `name`) first: users that are active with an empty or repeated key cannot sign in until fixed, and the next push from the owning application is rejected until the data is corrected. The backend `updateUsers` API only checks `email` (not `name`); the admin user list page itself also rejects duplicate names before saving, so only a direct API write can store two users with the same name, and with `mappingBy: 'name'` such users are refused at login rather than at save **[superseded on 2026-10-21: with `mappingBy: 'name'` or `'email'` the save now also checks that field of the active users, see below]**.
- **Same-table writes are serialized; two small fixes (2026-10-21)**: `/syncAndReplaceTabs` and the admin pages' whole-table save now take the same per-table lock, so the checks that keep group / permission names and the user mapping key unique can no longer be interleaved with the other writer (before, each took its own lock: a push and a save landing between each other's check and write could both succeed and leave two rows with the same name; a save made while a large push is running now waits for it). In `modeEditUsers: 'for:grups'`, a user row sent with a numeric id (for example `7` for the stored id `'7'`) used to have its group assignment silently skipped while the call reported success; it is now matched. A group / permission whose name is the **empty string** (only writable by `/syncAndReplaceTabs` before 2026-10-20) is still honored by the server, but the edit dialogs treat an empty name as invalid, so saving a dialog drops it and, if it was an `AND` limit, adds authorization: `node test/tools/authMergeReport.mjs --audit <export.json>` now lists such rows ("名稱為空字串或非字串之群組／權限") — rename them in the admin pages before relying on the dialogs **[superseded on 2026-10-21: the dialogs now keep such an entry as it is instead of dropping it, see below; renaming is still advisable]**.
- **Conflicting or ambiguous authorization data is resolved strictly, and the admin pages flag it (behavior change, tightening, 2026-10-21, ADR-035)**: when stored data contradicts itself or cannot be read in a single way, the server takes the strictest reading, and the admin pages show a warning icon (a triangle with an exclamation mark) at the left of the affected cell, with a tooltip that says exactly what is wrong and what the system does about it. Three cases change what a user is authorized for:
  1. **A reference to a group or permission that does not exist** (deleted, renamed or misspelled) used to be ignored. It is now still counted with the `mode` it was written with, but grants nothing: an `OR` reference adds nothing, an `AND` reference leaves the result empty. Example: a user whose `cgrups` lists group `G1` as `OR` and group `G2` as `AND` is authorized by what both groups share; before, deleting `G2` made the user keep everything `G1` grants (the `AND` limit silently disappeared); now the user has **nothing** until the reference is removed or `G2` is restored.
  2. **A reference whose name matches several rows** (duplicate group or permission names stored before duplicates were rejected, see F-02 above) used to use the first row in the table, so the result depended on the database row order. It now uses only what all the matching rows grant in common (the intersection), whatever the order.
  3. **An entry of `cgrups` / `cpemis` whose `mode` is missing or is not exactly `"OR"` or `"AND"`** (for example `"or"`, `"XOR"`, a number, or the short form `{"G1": "y"}`) used to be ignored. It is now a **restriction entry**: it still takes part, but only as an `AND`-style limit. It is intersected with the other entries of the same level and **never grants anything on its own** (it is never the base of the intersection). When the level also has an entry with a valid `mode`, a restriction entry behaves exactly like an `AND` entry (for example, a user who has `G1` as `OR` and `G2` with a missing `mode` is authorized by what `G1` and `G2` grant in common; before, `G2` was ignored and the user kept everything `G1` grants). When the level has **no** entry with a valid `mode` (every active entry has a missing or invalid `mode`, or the level has no active entry at all), the level grants **nothing**, the same as before (for example a `cgrups` that holds only `{"G1": {"isActive": "y"}}` or only the short form `{"G1": "y"}`).

  Compared with the previous release these rules **only take authorization away, with no exception** (the audit below lists any user who would be granted something new under `多給`; it is expected to be empty). One detail differs from the literal wording of the rule "treat it as `AND`": if the only active entry of a level (the groups of a user, or the permissions of a group) has a missing or invalid `mode`, reading it literally as `AND` would make it the base of the intersection and grant its content where the previous release granted nothing. The stricter reading was chosen instead (restriction entry, above), by the maintainer's own decision under the rule "when a datum can be read in several ways, take the intersection of the readings"; this one case is **pending confirmation by the project owner** and is tracked in `spec/設計要點與取捨.md` (ADR-035, decision e and Consequences). Because the edit dialogs show such an entry as an enabled `AND` entry, saving a level whose active entries **all** have a missing or invalid `mode` would turn the entry into the sole base and grant more than before; the dialogs write such an entry back with its original `mode` when the administrator did not change it, so that case can be saved without granting more (before 2026-10-22 it was refused; the warning icon stays). The same warning icons also mark: a group listed twice with both `OR` and `AND` (the editors refuse to save it), a `crules` array that lists one target twice with both checked and unchecked (it is treated as unchecked, see the item on `AND` ordering above), an empty name, and an entry without a usable name.
- **Audit your data before upgrading (nothing is changed by these commands)**: export `{ users, grups, pemis, targets }` as JSON (each an array of rows, for example the result of `select` on the four tables) and run `node test/tools/authMergeReport.mjs --audit <export.json>` (add `--json` for a machine-readable result). For every user it lists the targets taken away compared with the previous release (`被收回`), the references that cause the new rules to take something away (`觸發`: a reference that does not exist `懸空`, several rows with the same name `同名多列`, a missing or invalid mode `mode 非法`), the users who would be granted something they did not have (`多給`, expected to be empty; a non-empty result means the rules or the data need a report), the groups / permissions with duplicate names, and the groups / permissions with an empty name. Then run `node server/tools/nameDupReport.mjs <export.json> [--mapping-by id|email|name]` (read-only) to list every same-name group or permission together with the users or groups that refer to it, and the users whose mapping key is empty or repeated. If you run with `mappingBy: 'email'` or `'name'`, check the mapping field first (an active user with an empty or repeated key cannot sign in, and a later push from the owning application is rejected). Nothing is deleted or renamed automatically; clean the data in the admin pages, then check each user's authorization (`getPermUserInfor` / `getPerm`).
- **The edit dialogs no longer drop what they cannot show (behavior change, 2026-10-21)**: saving a dialog used to rewrite the stored JSON from the rows it displayed, so an active reference to a group or permission that no longer exists (which is now an `AND` limit that leaves the result empty) was silently removed and the limit with it. Now: (1) the user-groups and group-permissions dialogs list such a reference as an extra row after the normal rows (the name cannot be edited; the mode and "use" check box can, so an administrator can disable the reference to resolve it) and write it back on save; a disabled reference of that kind is not shown and is not kept. (2) An entry with a missing or invalid `mode` (including the short form `{"G1": "y"}`) is shown as an enabled `AND` entry; **if the administrator does not change that row it is written back with its original `mode` (missing stays missing)**, so saving never turns a restriction entry into a real `AND` base and what the user is authorized for does not change (even when the administrator disables the only entry with a valid `mode` in the same edit). Changing the row's mode or "use" check box writes what the dialog shows. When **every** active entry of the level has a missing or invalid `mode`, the dialog can still be saved (since 2026-10-22; it was refused before): unchanged entries are written back as they were, so nothing more is granted, and the warning icon stays. Limitation: re-selecting `AND` on such a row is treated as unchanged (it is already shown as `AND`), so an administrator cannot turn it into a real `AND` entry that way; choose `OR`, or fix the data at its source. (3) An entry whose name is the empty string is kept as it is. (4) An active entry without a usable name (for example an array element without `name`) cannot be written in the object form, so saving is refused with the fixed message of the earlier item "Data that the object form cannot hold is not rewritten" (now also covering this case), and a line at the top of the dialog points at it. (5) When several rows of the group or permission table share one name (historical duplicates), the dialog lists each row, switches all rows of that name together (they are one reference), and refuses to save if they are nevertheless not set identically; saving writes the entry once. The "belongs to" dialog of a permission locates group rows by id (not by name). (6) The "belongs to" dialogs (group page "users", permission page "groups") change only the one entry that belongs to the group or permission being edited and leave every other entry of the user / group, including the references above, exactly as they were.
- **Historical duplicates no longer block saving; users are checked only where the save creates the problem (behavior change, 2026-10-21)**: the group / permission lists used to mark every duplicate name and refuse to send the save, although the server already accepted duplicates that were already in the database (see F-02 above). They now use the server's rule: a duplicate that the current save creates or touches (a new row, a rename onto an existing name, a third row with the same name) is refused as before, while a duplicate that was already stored is only marked with the warning icon and does not stop the save, so it can be repaired. For users, the same rule applies to `email` and `name` in the list page, and the server no longer checks `email` on the **whole** table: it checks only new rows and rows whose `email` changed (non-empty and unique), so historical empty or repeated emails no longer make every save fail (also in `modeEditUsers: 'for:grups'`). With `mappingBy: 'name'` or `'email'` the server additionally checks that field of the **active** users, again only where the save creates or touches the problem (a new row, a changed value, or an inactive user turned active: non-empty after trimming, and unique among active users); with the default `mappingBy: 'id'`, `name` is still not checked. A refused save returns the usual `saveRowFieldInvalid` / `saveRowFieldDuplicate`, changes nothing, and the log records the reason but never the email or name.
- **Deleting a group or permission that others refer to with `AND` asks first (2026-10-21)**: in the group list, deleting a group that at least one user lists with `AND` (an entry whose mode is missing or invalid is a restriction entry and is counted too; the count is an upper bound) opens a confirmation box that says how many users lose their authorization; "No" keeps the group. The permission list does the same for groups that refer to the deleted permission with `AND`. Deleting one of several same-named rows (historical duplicates) can also widen what the referring users or groups are authorized for, because the result for such a name is the intersection of its rows; the same box then says how many referrers may gain authorization. Deleting a group or permission that nobody refers to with `AND`, and that is not one of several same-named rows referred to by anybody, behaves as before and shows no box. *Superseded on 2026-10-22: the box text and the behavior of a deletion changed, and a rename now updates the references; see the next two items.*
- **Renaming a group or permission updates the references to it (behavior change, 2026-10-22, F-07 phase 1)**: when `updateGrups` / `updatePemis` (the admin pages) or `/syncAndReplaceTabs` renames a group or permission, the `cgrups` of the users (or the `cpemis` of the groups) that list the old name are rewritten to the new name in the same write, so authorization is unchanged (before, the references silently became dangling: an `AND` reference that stopped matching could even widen a user's authorization). A rename is recognised by the row id (same id, different name); swaps (`A`↔`B`) and chains (`A`→`B`, `B`→`C`) are applied simultaneously. The save is refused as a whole, changing nothing (fixed message keys `renameCascadeDupGroup`, `renameCascadeNameInUse`, `renameCascadeConflict`, `renameCascadeUnsupported`; `/syncAndReplaceTabs` answers `invalidRows`, the reason is in the log) when: the renamed row shares its old name with other rows (historical duplicates) and that name is still referenced; the new name is still referenced by active entries but no group / permission carries it; one stored string contains both the old and the new name; or a string that would have to be rewritten contains a value that cannot be re-encoded safely (a JSON5 `Infinity` / `NaN` number, which `JSON.stringify` would turn into `null`). **Set `opt.cascadeRename: false` to keep the old behavior** (references are not updated and become dangling, which stays strict and flagged as above). The admin pages show a confirmation box before saving a rename with the number of users (groups) whose references will be updated; users whose `from` is not empty belong to an external application and their `cgrups` may be overwritten again by that application's next synchronization **[since 2026-10-22 only when that push carries a `cgrups` key; a push without the key keeps the stored value, see the 2026-10-22 section above]**. Rewritten strings are re-encoded as JSON (comments and quoting style are not kept; strings that need no change are untouched); the object form stays an object and the array form stays an array. The rewrite is written by the acting admin (`userIdUpdate` / `timeUpdate` of the rewritten rows).
- **Deleting a group, permission or target removes the references to it (behavior change, 2026-10-22)**: deleting a group removes it from the `cgrups` of every user, deleting a permission removes it from the `cpemis` of every group, and deleting a target (or changing its id, which is a delete plus an add) removes it from the `crules` of every permission, in the same write (admin pages and `/syncAndReplaceTabs`). Before, the references were kept and ignored ("not found, ignored"), and a group re-created with the same name silently took them over; now a re-created name starts with no references. **A reference to a deleted `AND` group is removed together with its restriction, so the referring users may gain authorization**; the confirmation box before the delete (group list, permission list) and before saving a target change says how many users / groups / permissions lose the reference and how many of them referred to it with `AND`. Deleting one of several same-named rows (historical duplicates) keeps the references (the name still resolves) and still asks as described above. "Delete only if nobody refers to it" is not implemented on purpose (it could involve many accounts, each to be fixed by hand).
- **Rows written without an `id` are matched by name (`updateGrups`, `updatePemis`, `/syncAndReplaceTabs`)**: a row with no `id` gets a new random id on every write (the old row is deleted and a new one added), so, for the purpose of references only, it is matched to an existing row of the same name (within the same source for `/syncAndReplaceTabs`): same name means the same group or permission and its references are kept; a row whose name matches no existing row is a new group or permission (and an existing row that nothing matches is a deletion, so references to it are removed).
- **Within one source (`from`), `/syncAndReplaceTabs` identifies groups and permissions by id**: a pushed row with the same id and a different name is a rename (references follow); an id that is no longer pushed is a deletion (references are removed). Rows pushed without an `id` (the server then generates a random id on every push) are matched to the source's existing rows by name, so a push that keeps the same names removes nothing; but a rename without ids cannot be recognised and counts as delete plus add. **If your application renumbers its ids on every push, references to the renumbered groups / permissions will be removed on each push, so keep ids stable** (or push without ids).
- **Cleaning up references that are already dangling (one-off, run it once when upgrading)**: `node g_authRefsClean.mjs` lists them (nothing is changed); `node g_authRefsClean.mjs --apply` backs up the database and the three tables that hold references (`--backup <file>`), then removes the dangling entries, with the same effect as the old "not found, ignored" (an `AND` reference to a missing group no longer empties the result). The offline version for an export file is `node server/tools/authRefsAudit.mjs <export.json> [--json] [--clean-out <file>]`. Dangling references that remain stay strict (counted with their `mode`, granting nothing) and flagged with the warning icon.
- **Locks**: saving groups, permissions or targets that renames or deletes something now also waits for the write lock of the table that refers to them (`users`, `grups`, `pemis`), always taken in the order targets, permissions, groups, users (one function, `withTabLocks`); saves that rename or delete nothing take only their own table's lock, as before.

### Upgrading to w-serv-orm 1.1.11 / w-syslog 1.0.33 (2026-10-14)
- **Numeric ids are stored as strings**: a numeric row id sent to `/syncAndReplaceTabs` (or to `updatePemis`, `updateGrups`, `updateUsers`) is stored as its string form (`123` is stored as `'123'`) and the success response lists it as a string. Before, the number was replaced by a generated id while the response still showed the number. A number and its string form are the same id; `NaN` and `Infinity` count as no id (a new id is generated). `updateTargets` still accepts string ids only and rejects other ids with `saveRowFieldInvalid`.
- **Ids owned by another source are rejected**: if an id pushed to `/syncAndReplaceTabs` already belongs to another `from`, the whole push is rejected with `invalidRows` before anything is deleted (before, the row was skipped while the push still returned success). External applications must use ids that do not overlap with other sources.
- **Logging**: with w-syslog 1.0.33, a log write failure no longer terminates the process (it is reported on stderr), and `WWebPerm` throws at construction when `opt.logFd` cannot be created.
- **Bundled usage**: the statistics worker file is located on first use from the installed package (`server/staLogs/staLogsCore.shellWorker.mjs`), so `dist/w-web-perm.umd.js` and downstream bundles can run the statistics; the package must be installed with its `server` folder.

### Upgrading to w-serv-orm 1.1.10 / w-serv-hapi 1.1.6 (2026-10-14)
- **Removed options**: `opt.useCheckUser`, `opt.getUserById` and `opt.useExcludeWhenNotAdmin` were removed together with w-serv-orm 1.1.9. Passing any value other than `undefined`, `null` or `false` now throws when constructing `WWebPerm` (the message comes from w-serv-orm `checkOptRemoved`) and is logged to srLog. Delete these keys; users of the data channel are authorized by `verifyConn` (`verifyClientUser`), no replacement option is needed.
- **Data channel is select-only (behavior change)**: only `<table>.select` of `targets`, `pemis`, `grups` and `users` is exposed (`methodsExec: ['select']`, and `authorizeExec` allows select only). Calling raw `insert`, `save`, `del` or `delAll` now returns `invalid func[<table>.<method>]`. Clients that wrote tables directly must call `updateTargets`, `updatePemis`, `updateGrups` or `updateUsers`, which apply the save lock, serialization, validation and whole-table diff.
- **Write validation**: rows to be written are validated before anything is deleted or written. A string value that XSS cleaning would rewrite (for example `<` followed by a letter) is rejected with `htmlMarkupNotAllowed`; an id longer than 1978 UTF-8 bytes is rejected with `saveRowFieldInvalid` (admin lists) or `invalidRows` (`syncAndReplaceTabs`). Unexpected database write failures return `saveWriteFail`; the ORM messages are written to srLog only.
- **Process-level errors**: w-serv-hapi 1.1.6 no longer registers `unhandledRejection` or `uncaughtException` handlers, and `WWebPerm` does not register them either; the deployment decides its own process policy.
