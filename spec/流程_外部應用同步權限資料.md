# 外部應用同步權限資料流程

## 觸發

外部應用程式（node 端，非瀏覽器使用者）以 app token 對伺服器發起 `POST /syncAndReplaceTabs`，將其本地維護的某一張權限表（`targets` / `pemis` / `grups` / `users` 四選一）的整批列資料推送至伺服器，由伺服器於該表之表鎖內以「依來源鍵 `srcKey` 差異同步」方式，把庫內該來源（`from`）的列同步成與批次一致：新增、修改、刪除（庫有批次無，引用連帶清理）、不變（零寫入）四類，只寫有差異者，成功時回傳 `{ nAdd, nUpdate, nDel, nSame }`（`server/syncCore.mjs:syncAndReplaceTabs`；跨套件規格 `C:\opensrcOper\dspec\外部匯入之定義與機制.md` 第 3～10 節，規則帳本 R-IMPORT-01）。每列須帶外部自訂之來源鍵 `srcKey`（同一 `from` 內唯一且穩定），**不得帶 `id`**（內部主鍵由本系統產生；`targets` 例外：其 `id` 即標的名稱，由 `srcKey` 衍生，見〈已知落差〉）；不提供呼叫端相容（使用者 2026-10-23 裁示：呼叫方還沒改送 `srcKey` 就不支援）。〔2026-10-23 perm-run03：原載「由伺服器以『依來源 `from` 全量取代』方式覆寫該應用在該表中的資料」不成立——不再先 `delAll({ from })` 再整批 insert，改為依 `srcKey` 差異同步；逐條原載與改為見〈已知落差〉首條。〕

`provideTabs(url, keyTable, from, rows)`（`server/provideTabs.mjs:provideTabs`）為外部應用端的呼叫輔助函式：依 `keyTable` 取對應欄位白名單 `ks_*`（`server/provideTabs.mjs:ks_targets` / `ks_pemis` / `ks_grups` / `ks_users`；perm-run03 起白名單以 `srcKey` 取代 `id`，**不送出 `id`**，列內即使夾帶 `id` 也被挑欄剝除，見 E2E-037），以 `ltdtpick` 僅保留白名單欄位（`server/provideTabs.mjs:provideTabs`），組成 `{ from, rows }` payload，再以內建 fetch（`src/fetchJson.mjs`）POST 至 `url`（範例 `http://localhost:11006/syncAndReplaceTabs?keyTable={keyTable}&token={token}`，`server/provideTabs.mjs:provideTabs`）。`keyTable` 與 `token` 由 query 帶入，`from` / `rows` 由 JSON body 帶入。連線失敗 / 非 2xx / 非 JSON 時 reject `{ kind, status, message }`，`message` 只含例外名稱與代碼（不含網址，網址內有 token；2026-09-25 起，見 ADR-023）。

伺服器端點僅以 query `token` 經 `getAndVerifyAppUser`（`server/WWebPerm.mjs:getAndVerifyAppUser`）守門，且**先驗身分再驗參數**（2026-10-24 perm-run01 本輪 P-5：身分驗證通過後才讀 `keyTable`、白名單與 payload；未通過驗證者之回應與 srLog 皆與 `keyTable` 無關，不得由參數錯誤鍵之差異探測表名）：以 `getUserByToken` 由 token 取出使用者，**套件自行要求管理員等級**（P-1、R-APP-TOKEN-01：呼叫者在 perm `users` 表者以該列為準，須有效且 `isAdmin='y'`〔含綁定該使用者之使用者用途應用系統 token〕；不在表者須為系統服務用途，即 `getUserByToken` 轉傳 `isApp='y'` 且 `isAdmin='y'`；一般使用者、綁一般使用者之應用系統 token、`isApp` 未轉傳之虛擬帳號皆拒，`msg` 為 `userNotAdmin`），再以部署方提供的 `verifyAppUser(user, from)` 判定（只能再收緊；否決 `userNoPermission` 先於等級不足 `userNotAdmin`）；任一步失敗即 reject、回傳 `state='error'`。部署方注入之 `getUserByToken` / `verifyAppUser` 拋錯或 reject 分別視同取不到使用者 / 未通過（W 契約，ADR-023），`msg` 為自家 key（`cannotFindUserFromToken` / `userNoPermission`），上游錯誤原文不回應、不入 log；路由失敗之 `msg` 一律為已知語系鍵，其餘原文（ORM／I/O 錯誤）改回 `anUnexpectedErrorOccurred` 並只入 srLog（R-ROUTE-MSG-01）。稽核欄 `userId` 記呼叫者 id（系統服務用途如 `app:<金鑰主鍵>`，`api-callerMatrix` MX-H5）。〔原載「僅以 token 取出使用者再以 `verifyAppUser` 判定是否為合法 app 使用者」於 2026-10-24 不成立（套件未要求管理員等級；先驗 `keyTable` 再驗身分）。〕

## 重要流程

本流程為 server-side app API，**回傳結構為 `{ state, msg }`（`state='success'` / `'error'`），無 UI 終態、無 baseline 圖**；成功時 `msg` 為 `{ nAdd, nUpdate, nDel, nSame }`。E2E 案例皆為 API 斷言，驗端點回傳值與四表 DB 的差異同步副作用。〔2026-10-23 perm-run03：原載「驗…四表 DB 的全量取代副作用」→ 改為差異同步副作用。〕

案例夾具慣例（perm-run03 起）：推送列一律帶 `srcKey`、不帶 `id`；「預置舊列」一律經同步端點建立，內部 `id` 由系統配發（`targets` 例外：`id` 即 `srcKey`），驗證以 `srcKey` 取列。測試對應：行為已由 `test/unit-syncCore.test.mjs`（64 案：SC-I1…SC-I15、SC-W1、SC-R1～5；替身資料表＋真鎖／真 procOrm；主責 agent 於 2026-10-23 回報 64 案全綠，本文件撰寫時未重跑）驗證；HTTP 層（守門、payload、語系鍵、真後端）由 `test/api-syncAndReplaceTabs.test.mjs`（API-sync-001～038）、`test/api-refCascade.test.mjs`（API-RC-040～047）、`test/api-externalRows.test.mjs`、`test/api-mapKey.test.mjs` 承擔——上述 api 測試檔已依新協定改寫，**本文件撰寫時尚未實跑（api／e2e 共用後端 port 與資料庫，由主責 agent 序列執行），實跑結果與案例編號對照〔待實測回填，結案前歸零〕**。

- **E2E-001**
  - title: 合法 app token 推送 users 表整批列依 srcKey 差異同步成功
  - description: 驗證外部應用以合法 app token 對 `keyTable=users` 推送一批 rows（每列帶 `srcKey`、不帶 `id`）後，伺服器於該表表鎖內以 `srcKey` 比對庫內該 `from` 的既有列，分為新增、修改、刪除、不變四類並只寫有差異者，回傳 `state='success'`、`msg` 為 `{ nAdd, nUpdate, nDel, nSame }`；DB `users` 表中該 `from` 的列等於推送內容，既有列的 `id` 不變、新增列的 `id` 由系統配發，且新增列的稽核欄位由後端自動補實值。屬差異同步 golden 成功案例。
  - flow:
    - 測試資料：base seed 四表；本案以特定 `from`（如 `appA`）經同步端點預置 3 筆 users 舊列（`srcKey` 為 `a1`、`a2`、`a3`），再推送同 `from` 的新批 rows：`a1` 內容不變、`a2` 改 `description`、`a3` 不再推送、新增 `a4`。
    - 操作：以合法 app token 對 `/syncAndReplaceTabs?keyTable=users&token=<appToken>` POST `{ from:'appA', rows:[...] }`（每列帶 `srcKey`、不帶 `id`）。
    - 驗證：
      1. 語意：回傳 `state='success'`、`msg` 為 `{ nAdd:1, nUpdate:1, nDel:1, nSame:1 }`。
      2. 語意：DB `users` 表 `from='appA'` 的列之 `srcKey` 集合為 `{a1, a2, a4}`；`a1`、`a2` 的 `id` 與預置時相同；`a1` 整列逐位元不動；`a2` 的 `description` 為新值、`userId`／`timeCreate` 保留預置時之值、`userIdUpdate` 為 app 使用者 id；`a4` 為新列，`id` 由系統產生（不等於 `a4`）、`userId` 為 app 使用者 id、`timeCreate` 已補實值；後台列與其他 `from` 的列不受影響。
    - 雙語：本案為 API 回傳值斷言，回傳 `state` / `msg` 為機器可讀值（`msg` 於錯誤時為 `procLang` 語系鍵，端點不翻譯成語系文字），單輪即可。
    - 清理：刪除本案 `from='appA'` 推送的列，還原 base seed。
    - 備註：配對與分類見 `server/syncCore.mjs:syncAndReplaceTabs`（`oldBySrc` 配對、`adds`／`upds`／`dels`／`nSame` 分類，比較用 `eqV`）。測試：`api-syncAndReplaceTabs` API-sync-001；`unit-syncCore` SC-I2（新增配新 `id`、其餘逐位元不動）、SC-I3（少一列刪除）、SC-I4（修改保留建立者與建立時間、更新者為 app）、SC-I6-server。
    - 修改留痕（2026-10-23 perm-run03）：原載「伺服器先依 payload 的 `from` 刪除該應用既有 users 列、再整批 insert 推送資料，回傳 `state='success'`，DB `users` 表中該 `from` 的列被替換為推送內容」「屬全量取代 golden 成功案例」→ 改為上述差異同步（不再 `delAll({ from })`，既有列 `id` 保留，成功 `msg` 為四類計數）。

- **E2E-002**
  - title: 推送空 rows 被拒（不支援以空集合清源）
  - description: 驗證以合法 app token 推送 `rows=[]`（空陣列）時，伺服器於 `parsePayload`（payload 層）的 rows 檢查（`isearr`，要求**非空**陣列，`WWebPerm.mjs:parsePayload`）即 reject，回傳 `state='error'`、`msg` 為 `invalidRowsInPayload`，**不進入差異同步**（未讀庫、零寫入），故該 `from` 既有列不被清空。差異同步下空批次會被解讀為「庫內該 `from` 的列全數刪除」，因此此 `isearr` 檢查為「防外部應用誤送空陣列而整批清空資料」之安全閘，**不支援「以空集合清源」**（清源走離線 `g_purgeFrom.mjs`，ADR-037 決定 13）。核心層 `syncCore.syncAndReplaceTabs` 另有同判準（空批次回 `invalidRows`），經 HTTP 端點時被 payload 層先攔而見不到。屬 payload rows 非空驗證之邊界案例。
  - flow:
    - 測試資料：base seed；以特定 `from` 經同步端點預置 2 筆 grups 舊列（`srcKey` 為 `g1`、`g2`）。
    - 操作：以合法 app token 對 `/syncAndReplaceTabs?keyTable=grups&token=<appToken>` POST `{ from, rows:[] }`。
    - 驗證：
      1. 語意：回傳 `state='error'`、`msg` 為 `invalidRowsInPayload`；DB `grups` 表該 `from` 的列**未被清空**（`srcKey` 集合、`id` 與全部欄位皆不變）；其他 `from` 的列不受影響。
      2. 語意（核心層，單元）：直接呼叫 `syncAndReplaceTabs(userId, { from, rows: [] }, 'grups')` 亦被拒，錯誤鍵為 `invalidRows`，四表逐位元不變且零寫入呼叫（`unit-syncCore` SC-I7-grups「空批次」）。
    - 雙語：API 回傳值斷言，單輪即可。
    - 清理：本案被拒未寫 DB，無需額外清理。
    - 備註：測試：`api-syncAndReplaceTabs` API-sync-002（HTTP 路徑；其檔頭註明 `syncCore` 內空批次檢查為縱深防禦、HTTP 不可達）。
    - 修改留痕（2026-10-23 perm-run03）：原載「**不進入全量取代（未 delAll）**」→ 改為「不進入差異同步（未讀庫、零寫入）」；原載僅 payload 層一道 → 改為 payload 層（`invalidRowsInPayload`）與核心層（`invalidRows`）兩層，依碼區分。

- **E2E-003**
  - title: 無效或缺 token 被守門拒絕
  - description: 驗證未帶 token、或帶不存在 / 無法經 `verifyAppUser` 通過的 token 時，端點於 `getAndVerifyAppUser` 守門階段 reject，回傳 `state='error'`、`msg` 為權限相關字串，DB 四表均不變動。屬 app token 守門拒絕案例。
  - flow:
    - 測試資料：base seed；不預置特化列。
    - 操作：對 `/syncAndReplaceTabs?keyTable=users` 不帶 token（或帶無效 token）POST 合法 `{ from, rows }`（rows 每列帶 `srcKey`、不帶 `id`）。
    - 驗證：
      1. 語意：回傳 `state='error'`，`msg` 為權限相關 key（如未帶 token 時為 `tokenNoPermission`；帶無效 token 經 `getAndVerifyAppUser` 拒絕時為 `cannotFindUserFromToken` 或 `userNoPermission`；部署方注入函數拋錯 / reject 時亦為此二 key，不含上游原文）；DB `users` 表無任何新增 / 修改 / 刪除（2026-10-23 perm-run03：原載「無任何刪除 / 新增」，差異同步多一類修改）。
    - 雙語：API 回傳值斷言，`msg` 為語系鍵、端點不翻譯，單輪即可。
    - 清理：本案被拒未寫 DB，無需清理。

- **E2E-005**

- **E2E-006**
  - title: 推送 targets 表依 srcKey 差異同步成功（標的 id 即 srcKey）

    - 驗證：

- **E2E-007**
  - title: srcKey 含 HTML 標記之推送被拒且該來源資料不變
  - description: 外部應用以應用程式令牌推送某張表時，若任一列的 `srcKey` 含有會被當成 HTML 標記之寫法（例如「<」後接英文字母），伺服器於讀取庫內資料與寫入任何資料之前即拒絕整批推送，回傳 state 為「error」、msg 為「srcKeyInvalid」，該來源原有之資料維持不變，其他來源亦不受影響。標的（`targets`）的 `id` 即 `srcKey`，故標的路徑含標記同此；其他欄位含標記則見 E2E-008（回傳「htmlMarkupNotAllowed」）。外部應用收到此訊息時，應移除該字樣後重新推送整批資料。
  - flow:
    - 測試資料：base seed；以獨立來源（`appTest-7`）先推送 targets 兩列（路徑式 `srcKey`，無標記）作為既有資料。
    - 操作：以合法 app token 對 `/syncAndReplaceTabs?keyTable=targets&token=<appToken>` POST `{ from:'appTest-7', rows:[一般路徑一列, `srcKey` 路徑含「<」後接字母之一列] }`。
    - 驗證：
      1. 語意：回傳 `state='error'`、`msg` 為 `srcKeyInvalid`；DB `targets` 表 `from='appTest-7'` 之列仍為先前兩列（`id` 與全部欄位不變，新列未寫入）；四表其餘列不變。

## 執行流程

端點 handler 以 `pm2resolve(core)()` 將 `core()` 的 resolve / reject 轉為 `{ state, msg }` 回傳（`state='success'` 對應 resolve，`'error'` 對應 reject）；`core()` 內任一 `Promise.reject` 即短路後續、不進入差異同步。〔2026-10-23 perm-run03：原載「不進入全量取代」→ 改為「不進入差異同步」；下方 041 起之步驟全數改寫為 `syncCore` 之差異同步，001～040（端點守門與 payload 解析）不變。〕

位置標註為符號錨 `[檔名:符號]`（函式或變數名；2026-10-21 起取代行號，行號會隨改版漂移）：`apis(/syncAndReplaceTabs)` 指 `server/WWebPerm.mjs` 內 `apis` 陣列中 `path: '/syncAndReplaceTabs'` 之項目，`.core` 為其 handler 內的 `core()`；`syncCore.mjs:syncAndReplaceTabs` 指 `server/syncCore.mjs` 內 `syncCore()` 回傳之 `syncAndReplaceTabs`（perm-run03 起原內嵌於 `WWebPerm.mjs` 之實作移至此檔，符號同名）。

`syncAndReplaceTabs`（`server/syncCore.mjs`）內之守門順序（先到先拒，皆在表鎖內、任何寫入之前；除 `select` 失敗外亦皆在讀庫之前者以〔讀庫前〕標示）：`from` 為有效字串（`invalidFrom`）〔讀庫前〕→ `rows` 為非空陣列（`isearr`，`invalidRows`）〔讀庫前〕→ 每列為非空物件（`isRowObj`，`reason:'rowInvalid'`）〔讀庫前〕→ 任一列帶有 `id` 鍵（`idNotAllowed`）〔讀庫前〕→ 每列 `srcKey` 為合規非空字串（`srcKeyInvalid`）〔讀庫前〕→ 同批 `srcKey` 不重複（`srcKeyDuplicate`）〔讀庫前〕→ `ltdtmapping` 對齊 schema 欄位（`targets` 之 `id` 取 `srcKey`）→ `grups`／`pemis` 之 `name` 為非空字串（`nameInvalid`）→ `grups`／`pemis` 之 `name` 批內不重複（`nameDuplicate`）→ `users` 於 `mappingBy` 為 `email`／`name` 時之對應鍵批內非空且不重複（`mapKeyInvalid`／`mapKeyDuplicate`）→ `validateRowsBeforeWrite`（`invalidRows`／`htmlMarkupNotAllowed`）〔以上皆讀庫前〕→ 表鎖內新鮮讀庫（`select`；失敗回 `anUnexpectedErrorOccurred` 等，尚未寫入）→ 跨 `from` 同名／同對應鍵（`nameOtherFrom`／`mapKeyOtherFrom`）→ `users` 於 `mappingBy` 為 `id` 時本批外部列之 `srcKey` 不得等於後台列之 `id`、也不得等於他來源任一既有列之登入識別值（他來源外部列之 `srcKey`，舊外部列為其 `id`），不論 `isActive`（`loginIdCollision`；2026-10-24 perm-run04，perm-run05 擴及他來源與停用列）→ 依 `srcKey` 配對（庫內重複 `srcKey` 或一個 `srcKey` 被兩列主張 → `srcKeyConflict`）→ `targets` 之 `id`（＝`srcKey`）已被庫內任何其他列占用（`idTaken`，回 `invalidRows`）→ 差異分類 → 引用連帶預檢（改名或刪除時，`renameCascade*` 一律回 `invalidRows`）→ 寫入（刪除→新增→修改，失敗補償還原）。除 `invalidFrom`、`idNotAllowed`、`srcKeyInvalid`、`srcKeyDuplicate`、`srcKeyConflict`、`loginIdCollision`、`htmlMarkupNotAllowed` 外，其餘拒收之 `msg` 皆為 `invalidRows`，細部原因 `reason` 僅入 srLog。〔2026-10-23 perm-run03：原載守門順序中的 `rowBlank`、同步端專屬 `idInvalid`、跨 `from` 同鍵 `idOtherFrom`、`delAll` + `insert` 不成立，逐條見〈已知落差〉首條。〕

## 欄位邊界

| 概念 | 處理 |
|---|---|
| `keyTable` | query 帶入；須屬白名單 `[targets, pemis, grups, users]`，否則 reject（`WWebPerm.mjs:apis(/syncAndReplaceTabs).core`） |
| `token` | query 帶入；經 `getAndVerifyAppUser` 守門（`getUserByToken` + `verifyAppUser`），非經 verifyConn / Bearer（`WWebPerm.mjs:getAndVerifyAppUser`） |
| `from` | payload 帶入；須為有效字串。`syncAndReplaceTabs` 以 `from` 為差異同步的範圍：配對、修改與刪除只及庫內 `from` 相同的列，後台列（`from` 為空字串）與他 `from` 的列永不被觸及；寫入前逐列複寫 `from`（`syncCore.mjs:syncAndReplaceTabs`）。〔原載「以 `from` 為全量取代的範圍鍵：`delAll({ from })` 只刪該 `from` 的列、insert 前逐列複寫 `v.from = from`」2026-10-23 起不成立。〕 |
| `rows` | payload 帶入；須為**非空**陣列（`isearr`），空陣列被拒（`parsePayload` reject `invalidRowsInPayload`，`WWebPerm.mjs:parsePayload`；核心層同判準回 `invalidRows`），不支援以空陣列清空該 `from`。通過後各列須為非空物件（`isRowObj`，違者 `invalidRows`），再依序檢查 `id`（`idNotAllowed`）與 `srcKey`（`srcKeyInvalid`／`srcKeyDuplicate`），經 `ltdtmapping` 對齊 `ds[keyTable].keys`（`syncCore.mjs:syncAndReplaceTabs`）。〔原載「映射後除伺服器管理欄外至少一欄帶有內容（`rowBlank`，違者 `invalidRows`）」2026-10-23 起不成立：每列必有非空 `srcKey`，映射後恆有內容。〕 |
| `srcKey` | 每列必填；須為非空白字串、UTF-8 ≤ 1978 位元組（`validateRows.mjs:maxIdBytes`）、不含會被 `clearXSS` 改寫之標記（`syncCore.mjs:isSrcKey`），否則 `srcKeyInvalid`；同批精確 `===` 重複 → `srcKeyDuplicate`；同一 `from` 內唯一且穩定。為差異同步的配對鍵；後台不可新增帶值之列、不可改既有列之值（`src/js/externalRows.mjs:checkExternalWrite`，reason `addSrcKey`／`srcKeyChanged`）。 |
| `id` | 外部不得帶：任一列帶 `id` 鍵（含空值）整批拒收 `idNotAllowed`，先於 `srcKey` 檢查。新增列由系統配發（`genIDSeq`，不撞庫內任何既有 `id`）；修改列沿用庫內 `id`；`targets` 例外：`id＝srcKey`（標的名稱；被庫內任何其他列占用 → `invalidRows`，reason `idTaken`）。 |
| 欄位歸屬 | **外部擁有**：批次提供之欄位，缺鍵視為空值（含 `order`、`name`、`description`、`email`、`isAdmin`、`isActive`）；**外部可選**：指派欄 `users.cgrups`／`grups.cpemis`／`pemis.crules`，有帶鍵才寫、缺鍵保留庫內值（`syncKeep.mjs`）；**本系統擁有**：`userId`／`timeCreate`／`userIdUpdate`／`timeUpdate`，一律不採批次值。`id`、`srcKey`、`from` 為身分欄，由匯入端點寫入、後台不可改。 |
| 欄位白名單（端側） | `provideTabs` 以 `ks_targets` / `ks_pemis` / `ks_grups` / `ks_users` 白名單 `ltdtpick` 列資料（`server/provideTabs.mjs:ks_targets` / `ks_pemis` / `ks_grups` / `ks_users`、`provideTabs`）：四表共有 `srcKey` / `order` / `description` / `from`；`pemis` 多 `name` / `crules`；`grups` 多 `name` / `cpemis`；`users` 多 `name` / `email` / `cgrups` / `isAdmin` / `isActive`；稽核欄位（`userId` / `time*`）一律被白名單排除（端側白名單 `ks_*` 內以註解停用 `userId` / `time*`，與此對齊，由後端 `procOrm` 補）。〔原載「四表共有 `id` / `order` / `description` / `from`」2026-10-23 起不成立：以 `srcKey` 取代 `id`，不送 `id`。〕 |
| `name`（`grups`／`pemis`） | 須為非空字串（`nameInvalid`），本批內不得重複（`nameDuplicate`），不得已為其他 `from` 之既有列使用（`nameOtherFrom`）；精確 `===` 比對（`syncCore.mjs:syncAndReplaceTabs`、`keyCheck.mjs`） |
| 對應鍵（`users` 之 `email`／`name`，依 `mappingBy`） | `mappingBy` 為 `'email'`／`'name'` 時，啟用列（`isActive==='y'`）該欄位須非空且本批與他 `from` 之啟用列皆不重複（`mapKeyInvalid`／`mapKeyDuplicate`／`mapKeyOtherFrom`）；`'id'`（預設）不檢查 email／name，但外部列之 `srcKey` 不得等於後台列之 `id` 或他來源任一既有列之登入識別值，不論 `isActive`（`loginIdCollision`，E2E-041；perm-run05 由「僅有效列」改為「不論 isActive、含他來源」）（`syncCore.mjs:syncAndReplaceTabs`、`keyCheck.mjs:checkMapKeyBatch`／`findLoginIdClashDetail`） |
| 稽核欄位 | `userId` / `timeCreate` / `userIdUpdate` / `timeUpdate` 不由 payload 帶入（帶了也不採納），由後端 `procOrm` 於 insert／save 時自動補：新增列為匯入者（app 使用者 id）與現在時間，修改列保留建立者與建立時間、更新者記匯入者（`syncCore.mjs:syncAndReplaceTabs`；E2E-018） |

## i18n 訊息粒度規則

本端點為 server-side app API，回傳 `{ state, msg }` 為**機器可讀值**：`state` 為 `'success'` / `'error'`、`msg` 於錯誤時為 camelCase 錯誤 key（如 `tokenNoPermission` / `invalidKeyTable` / `cannotFindUserFromToken` / `userNoPermission` / `invalidPayload` / `invalidFromInPayload` / `invalidRowsInPayload` / `invalidFrom` / `invalidRows` / `htmlMarkupNotAllowed` / `saveWriteFail`，以及 2026-10-23 perm-run03 新增之 `srcKeyInvalid` / `srcKeyDuplicate` / `idNotAllowed` / `srcKeyConflict`；`htmlMarkupNotAllowed`、`saveWriteFail` 為 2026-10-14 起，ADR-026），成功時為 `{ nAdd, nUpdate, nDel, nSame }`。上述 key 於 `server/procLang.mjs` 皆有 eng + cht 定義，由呼叫端（外部應用）以 key 查 lang 決定如何呈現。故本流程訊息粒度即「一個 reject key 對應一條 procLang 雙語訊息」。

## spec 規則摘要

- **權限**：`/syncAndReplaceTabs` 守門完全由端點 handler 內 `getAndVerifyAppUser`（query `token` → `getUserByToken` → 管理員等級〔2026-10-24 perm-run01 本輪 P-1：在 perm 表者以列為準、不在表者須 `isApp='y'` 且 `isAdmin='y'`〕→ `verifyAppUser`）負責，且先於 `keyTable` 等參數檢查（P-5）；此自訂端點直接 `server.route` 註冊，**不經 verifyConn / Bearer header 通道**（verifyConn 僅守 orm exec 通道）。token 缺 / 無效 / 取不到使用者 / `verifyAppUser` 回 false 一律 reject；部署方注入之 `getUserByToken` / `verifyAppUser` 拋錯或 reject 視同取不到 / 回 false（W 契約，ADR-023），回應不含上游原文，srLog 另記 warn `inject-<函數名>-fail`。
- **同步模型**：本端點為「依來源鍵 `srcKey` 差異同步」——`syncAndReplaceTabs`（`server/syncCore.mjs`）於該表表鎖內新鮮讀取庫內全表，依 `srcKey` 配對該 `from` 之列，分為新增（配新 `id`；`targets` 例外：`id＝srcKey`）、修改（保留 `id`，只寫外部擁有欄位與有帶鍵之指派欄）、刪除（庫有批次無，引用連帶清理）、不變（零寫入）四類，只寫有差異者，回 `{ nAdd, nUpdate, nDel, nSame }`。各應用以各自 `from` 隔離，互不影響彼此資料；後台列（`from` 為空）與他 `from` 之列永不被觸及。grups／pemis／targets 於寫入之前另判定同一 `from` 內之改名與刪除，並於同一次寫入內連帶更新或清理引用它之授權字串（2026-10-22 run06 起，ADR-036，見〈同步之引用連帶〉）；引用端之寫入先於主體寫入，失敗時補償還原。〔2026-10-23 perm-run03：原載「本端點為『依來源 `from` 全量取代』——`syncAndReplaceTabs` 先 `delAll({ from })` 刪該應用既有列，再整批 `procOrm insert`，**非逐列 diff（無 ltdtDiffByKey、無 ckKey 去重）**」「寫入面仍為全量取代」不成立——不再 `delAll({ from })` 加 insert，改依 `srcKey` 配對差異同步（配對與比對在 `syncCore`，仍不走後台之 `ltdtDiffByKey`／`ckKey` 路徑）。〕
- **名稱／識別碼須為非空文字**（規則帳本 R-SYNC-NAME-01，ADR-031，2026-10-20 起；主控複審 R2）：比照後台整表寫入之 `ckKey`（`isestr`），`grups`／`pemis` 之 `name` 缺漏、空字串、非字串（數字、布林、null）一律整批拒收（`invalidRows`，srLog 記 `reason:'nameInvalid'`），於任何寫入之前，該 `from` 與他 `from` 之既有列不變；`targets` 之標的名稱即 `srcKey`（`id＝srcKey`），缺漏、空字串、非字串同樣整批拒收但回 `srcKeyInvalid`（E2E-012、E2E-036）；`users` 不在範圍（名稱可重複、可省略）；〔2026-10-23 perm-run03：原載「`targets` 之 `id` 缺漏、空字串、非字串…（`invalidRows`，srLog 記 `reason:'idInvalid'`）」不成立：外部不送 `id`，識別碼由 `srcKey` 衍生並由 `srcKeyInvalid` 檢查，同步端專屬之 `idInvalid` 已不存在。〕〔原載「不比照 `ckKey` 之重複名稱偵測」2026-10-21 起不成立：重複名稱改由下一條規範，見 E2E-019～022〕。修正前 `name:''` 之群組／權限可入庫，伺服端 `arrFinder` 以 `===` 採納而編輯器視為無效，存檔即移除其授權。（2026-10-21 run05，ADR-035 決定 f：升級前已存在之空字串名稱列，伺服端仍以 `findRefRows` 精確 `===` 比對〔取代 `arrFinder`；列無 `name` 欄視為 `''`〕，編輯器改為原樣保留空字串名稱之引用〔物件鍵 `''`〕、不再於存檔時丟棄，故上述『存檔即移除其授權』不再發生；新寫入仍被本條拒收。）
