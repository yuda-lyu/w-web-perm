# 外部應用同步權限資料流程

## 觸發

外部應用程式（node 端，非瀏覽器使用者）以 app token 對伺服器發起 `POST /syncAndReplaceTabs`，將其本地維護的某一張權限表（`targets` / `pemis` / `grups` / `users` 四選一）的整批列資料推送至伺服器，由伺服器以「依來源 `from` 全量取代」方式覆寫該應用在該表中的資料。

`provideTabs(url, keyTable, from, rows)`（`server/provideTabs.mjs:provideTabs`）為外部應用端的呼叫輔助函式：依 `keyTable` 取對應欄位白名單 `ks_*`（`server/provideTabs.mjs:ks_targets` / `ks_pemis` / `ks_grups` / `ks_users`），以 `ltdtpick` 僅保留白名單欄位（`server/provideTabs.mjs:provideTabs`），組成 `{ from, rows }` payload，再以內建 fetch（`src/fetchJson.mjs`）POST 至 `url`（範例 `http://localhost:11006/syncAndReplaceTabs?keyTable={keyTable}&token={token}`，`server/provideTabs.mjs:provideTabs`）。`keyTable` 與 `token` 由 query 帶入，`from` / `rows` 由 JSON body 帶入。連線失敗 / 非 2xx / 非 JSON 時 reject `{ kind, status, message }`，`message` 只含例外名稱與代碼（不含網址，網址內有 token；2026-09-25 起，見 ADR-023）。

伺服器端點僅以 query `token` 經 `getAndVerifyAppUser`（`server/WWebPerm.mjs:getAndVerifyAppUser`）守門：以 `getUserByToken` 由 token 取出使用者，再以部署方提供的 `verifyAppUser(user, from)` 判定是否為合法 app 使用者；任一步失敗即 reject、回傳 `state='error'`。部署方注入之 `getUserByToken` / `verifyAppUser` 拋錯或 reject 分別視同取不到使用者 / 未通過（W 契約，ADR-023），`msg` 為自家 key（`cannotFindUserFromToken` / `userNoPermission`），上游錯誤原文不回應、不入 log。

## 重要流程

本流程為 server-side app API，**回傳結構為 `{ state, msg }`（`state='success'` / `'error'`），無 UI 終態、無 baseline 圖**。E2E 案例皆為 API 斷言，驗端點回傳值與四表 DB 的全量取代副作用。

- **E2E-001**
  - title: 合法 app token 推送 users 表整批列全量取代成功
  - description: 驗證外部應用以合法 app token 對 `keyTable=users` 推送一批 rows 後，伺服器先依 payload 的 `from` 刪除該應用既有 users 列、再整批 insert 推送資料，回傳 `state='success'`，DB `users` 表中該 `from` 的列被替換為推送內容、且稽核欄位由後端自動補實值。屬全量取代 golden 成功案例。
  - flow:
    - 測試資料：base seed 四表；本案以特定 `from`（如 `appA`）預置數筆 users 舊列，再推送同 `from` 的新批 rows（與舊列不同）。
    - 操作：以合法 app token 對 `/syncAndReplaceTabs?keyTable=users&token=<appToken>` POST `{ from:'appA', rows:[...] }`。
    - 驗證：
      1. 語意：回傳 `state='success'`；DB `users` 表 `from='appA'` 的列等於推送 rows 集合（舊列已不存在）；其他 `from` 的列不受影響；新列 `userId` / `timeCreate` 已由後端補實值。
    - 雙語：本案為 API 回傳值斷言，回傳 `state` / `msg` 為機器可讀值（`msg` 為 `procLang` 語系鍵，端點不翻譯成語系文字），單輪即可。
    - 清理：刪除本案 `from='appA'` 推送的列，還原 base seed。

- **E2E-002**
  - title: 推送空 rows 被拒（不支援以空集合清源）
  - description: 驗證以合法 app token 推送 `rows=[]`（空陣列）時，伺服器於 `parsePayload` 的 rows 檢查（`isearr`，要求**非空**陣列，`WWebPerm.mjs:parsePayload`）即 reject，回傳 `state='error'`、`msg` 為 `invalidRowsInPayload`，**不進入全量取代（未 delAll）**，故該 `from` 既有列不被清空。此 `isearr` 檢查為「防外部應用誤送空陣列而整批清空資料」之安全閘，故**不支援「以空集合清源」**。屬 payload rows 非空驗證之邊界案例。
  - flow:
    - 測試資料：base seed；以特定 `from` 預置數筆 grups 舊列。
    - 操作：以合法 app token 對 `/syncAndReplaceTabs?keyTable=grups&token=<appToken>` POST `{ from, rows:[] }`。
    - 驗證：
      1. 語意：回傳 `state='error'`、`msg` 為 `invalidRowsInPayload`；DB `grups` 表該 `from` 的列**未被清空**（仍為先前列數）；其他 `from` 的列不受影響。
    - 雙語：API 回傳值斷言，單輪即可。
    - 清理：本案被拒未寫 DB，無需額外清理。

- **E2E-003**
  - title: 無效或缺 token 被守門拒絕
  - description: 驗證未帶 token、或帶不存在 / 無法經 `verifyAppUser` 通過的 token 時，端點於 `getAndVerifyAppUser` 守門階段 reject，回傳 `state='error'`、`msg` 為權限相關字串，DB 四表均不變動。屬 app token 守門拒絕案例。
  - flow:
    - 測試資料：base seed；不預置特化列。
    - 操作：對 `/syncAndReplaceTabs?keyTable=users` 不帶 token（或帶無效 token）POST 合法 `{ from, rows }`。
    - 驗證：
      1. 語意：回傳 `state='error'`，`msg` 為權限相關 key（如未帶 token 時為 `tokenNoPermission`；帶無效 token 經 `getAndVerifyAppUser` 拒絕時為 `cannotFindUserFromToken` 或 `userNoPermission`；部署方注入函數拋錯 / reject 時亦為此二 key，不含上游原文）；DB `users` 表無任何刪除 / 新增。
    - 雙語：API 回傳值斷言，`msg` 為語系鍵、端點不翻譯，單輪即可。
    - 清理：本案被拒未寫 DB，無需清理。

- **E2E-004**
  - title: 不在白名單的 keyTable 被拒絕
  - description: 驗證 query `keyTable` 不屬 `targets` / `pemis` / `grups` / `users` 四者之一時，端點於 keyTable 白名單檢查階段 reject，回傳 `state='error'`、`msg` 為 keyTable 無效字串，不進入任何表的刪除 / 新增。屬 keyTable 白名單守門案例。
  - flow:
    - 測試資料：base seed；不預置特化列。
    - 操作：以合法 app token 對 `/syncAndReplaceTabs?keyTable=foobar&token=<appToken>` POST 合法 `{ from, rows }`。
    - 驗證：
      1. 語意：回傳 `state='error'`，`msg` 為 `invalidKeyTable`；DB 四表均無變動。
    - 雙語：API 回傳值斷言，`msg` 為語系鍵、端點不翻譯，單輪即可。
    - 清理：本案被拒未寫 DB，無需清理。

- **E2E-005**
  - title: payload 缺 from 或 rows 非陣列被拒絕
  - description: 驗證 payload 缺 `from`（或 `from` 非有效字串）、或 `rows` 非陣列時，端點於 `parsePayload` 解析階段 reject，回傳 `state='error'`、`msg` 為 payload 欄位無效 key，不進入全量取代。屬 payload 結構驗證守門案例。
  - flow:
    - 測試資料：base seed；不預置特化列。
    - 操作：以合法 app token 對 `/syncAndReplaceTabs?keyTable=users&token=<appToken>` POST 缺 `from` 的 body（如 `{ rows:[...] }`）；另一輪 POST `rows` 非陣列的 body（如 `{ from:'appC', rows:'x' }`）。
    - 驗證：
      1. 語意：兩輪皆回傳 `state='error'`，`msg` 分別為 `invalidFromInPayload` / `invalidRowsInPayload`（缺 payload 物件時為 `invalidPayload`）；DB 四表均無變動。
    - 雙語：API 回傳值斷言，`msg` 為語系鍵、端點不翻譯，單輪即可。
    - 清理：本案被拒未寫 DB，無需清理。

- **E2E-006**
  - title: 推送 targets 表全量取代成功（驗四表共用同一路徑）
  - description: 驗證以合法 app token 對 `keyTable=targets` 推送一批 rows，伺服器以與 users 相同的「依 from 全刪後整批 insert」路徑覆寫該應用既有 targets 列，回傳 `state='success'`。本案與 E2E-001 對照，確認四表共用同一全量取代邏輯、僅欄位 schema（`ds[keyTable].keys`）不同。
  - flow:
    - 測試資料：base seed；以特定 `from`（如 `appD`）預置數筆 targets 舊列。
    - 操作：以合法 app token 對 `/syncAndReplaceTabs?keyTable=targets&token=<appToken>` POST `{ from:'appD', rows:[...] }`。
    - 驗證：
      1. 語意：回傳 `state='success'`；DB `targets` 表 `from='appD'` 的列等於推送 rows 集合；推送列僅保留 `targets` schema 欄位（`ltdtmapping` 對齊）。
    - 雙語：API 回傳值斷言，單輪即可。
    - 清理：刪除本案 `from='appD'` 推送的列，還原 base seed。

- **E2E-007**
  - title: 主鍵含 HTML 標記之推送被拒且該來源資料不變
  - description: 外部應用以應用程式令牌推送某張表時，若任一列之主鍵含有會被當成 HTML 標記之寫法（例如「<」後接英文字母），伺服器於刪除該來源之既有資料之前即拒絕整批推送，回傳 state 為「error」、msg 為「htmlMarkupNotAllowed」，該來源原有之資料維持不變，其他來源亦不受影響。外部應用收到此訊息時，應移除該字樣後重新推送整批資料。
  - flow:
    - 測試資料：base seed；以獨立來源（`appTest-7`）先推送 targets 兩列（路徑式 id，無標記）作為既有資料。
    - 操作：以合法 app token 對 `/syncAndReplaceTabs?keyTable=targets&token=<appToken>` POST `{ from:'appTest-7', rows:[一般路徑一列, 路徑含「<」後接字母之一列] }`。
    - 驗證：
      1. 語意：回傳 `state='error'`、`msg` 為 `htmlMarkupNotAllowed`（語系鍵，非 ORM 英文原文）；DB `targets` 表 `from='appTest-7'` 之列仍為先前兩列（未被清空、新列未寫入）。
    - 雙語：API 回傳值斷言，單輪即可。
    - 清理：刪除 `from='appTest-7'` 之列（`api-syncAndReplaceTabs` 之 after）。
    - 備註：寫入前驗證 `server/validateRows.mjs:validateRowsBeforeWrite` 於 `delAll({ from })` 之前（`server/WWebPerm.mjs:syncAndReplaceTabs`，ADR-026）。修正前之實測見〈已知落差〉。測試：`api-syncAndReplaceTabs` API-sync-007。

- **E2E-008**
  - title: 欄位含 HTML 標記之推送被拒且不改寫
  - description: 外部應用推送之資料列，除主鍵外之任一文字欄位（名稱、說明、email 等）若含有會被當成 HTML 標記之寫法，伺服器同樣於刪除既有資料之前拒絕整批推送，回傳 msg 為「htmlMarkupNotAllowed」，不會把該值改寫後存入，該來源原有之資料維持不變。單獨使用之「<」「>」（例如「a < b」）與允許之粗體、斜體標記照常寫入。
  - flow:
    - 測試資料：base seed；以獨立來源（`appTest-8`）先推送 grups 一列作為既有資料。
    - 操作：以合法 app token 對 `keyTable=grups` POST 一列說明為「x<y」之群組。
    - 驗證：
      1. 語意：回傳 `state='error'`、`msg` 為 `htmlMarkupNotAllowed`；DB `grups` 表 `from='appTest-8'` 仍只有先前一列且其說明未變（修正前存為 `x&lt;y`）。
    - 雙語：API 回傳值斷言，單輪即可。
    - 清理：刪除 `from='appTest-8'` 之列。
    - 備註：測試：`api-syncAndReplaceTabs` API-sync-008。

- **E2E-009**
  - title: 主鍵過長之推送被拒且該來源資料不變
  - description: 外部應用推送之資料列，若任一列之主鍵以 UTF-8 計超過 1978 位元組（資料庫之主鍵長度上限），伺服器於刪除既有資料之前拒絕整批推送，回傳 msg 為「invalidRows」，該來源原有之資料維持不變。
  - flow:
    - 測試資料：base seed；以獨立來源（`appTest-9`）先推送 users 一列作為既有資料。
    - 操作：以合法 app token 對 `keyTable=users` POST 一列主鍵為 1979 位元組之使用者。
    - 驗證：
      1. 語意：回傳 `state='error'`、`msg` 為 `invalidRows`；DB `users` 表 `from='appTest-9'` 仍為先前一列（修正前被清空，且 msg 為資料庫之英文原文）。
    - 雙語：API 回傳值斷言，單輪即可。
    - 清理：刪除 `from='appTest-9'` 之列。
    - 備註：主鍵型別錯誤（非字串非數字）與批內主鍵重複同回 `invalidRows`（`unit-validateRows` VR-003／VR-005）。數字主鍵存為其字串形式（`123` 存為 `'123'`、回應之 id 為 `'123'`，w-serv-orm 1.1.11 起）；`NaN`、`±Infinity` 視為未給主鍵（由資料庫補主鍵）；本批有給之主鍵已屬其他來源者（含數字與其字串形式）亦回 `invalidRows`（E2E-011）。測試：`api-syncAndReplaceTabs` API-sync-009。
    - 修改留痕（2026-10-14 run05）：備註補數字主鍵與跨來源同鍵之句（依 w-serv-orm 主責 agent 之建議書，w-serv-orm 1.1.11 發布後）。

- **E2E-010**
  - title: 數字主鍵存為其字串形式且重送不增列
  - description: 外部應用推送之資料列若以數字為主鍵（例如流水號 1010），伺服器把它存為其字串形式「1010」，成功回應中列出之 id 也是字串；同一批資料重送時，該列仍只有一筆。數字與其字串形式視為同一個主鍵，外部應用比對回應時請以字串比對。
  - flow:
    - 測試資料：base seed；以獨立來源（`appTest-10`）推送 users 一列 `id: 1010`（數字）。
    - 操作：以合法 app token 對 `keyTable=users` POST `{ from:'appTest-10', rows:[{ id: 1010, … }] }`，再以同一包重送一次。
    - 驗證：
      1. 語意：第一次回傳 `state='success'`、`msg` 為 `[{ id: '1010' }]`；重送亦 success；DB `users` 表 `from='appTest-10'` 之 id 為 `['1010']`（一列、字串）。
    - 雙語：API 回傳值斷言，單輪即可。
    - 清理：刪除 `from='appTest-10'` 之列（`api-syncAndReplaceTabs` 之 after）。
    - 備註：w-serv-orm 1.1.11 起之上游行為（1.1.10 時數字主鍵被換成隨機主鍵、回應卻列數字）；本套件之守護測試。測試：`api-syncAndReplaceTabs` API-sync-010；相關單元 `unit-validateRows` VR-EQ-003（真 procOrm 存為字串並回報字串）。

- **E2E-011**
  - title: 主鍵已屬其他來源之推送被拒且兩來源不變
  - description: 外部應用推送之資料列，若任一列之主鍵已經屬於另一個來源（另一個外部應用以其 from 推送過的資料），伺服器於刪除任何資料之前拒絕整批推送，回傳 msg 為「invalidRows」，兩個來源原有之資料都維持不變。數字主鍵與其字串形式（例如 1011 與「1011」）視為同一個主鍵。各外部應用之主鍵須彼此不重疊，例如在主鍵前加上應用之代號。
  - flow:
    - 測試資料：base seed；以來源 `appTest-11` 先推送 users 一列 `id: 1011`。
    - 操作：以合法 app token 以來源 `appTest-11b` 依序推送 `id: 1011`（數字）與 `id: '1011'`（字串）各一次。
    - 驗證：
      1. 語意：兩次皆回 `state='error'`、`msg` 為 `invalidRows`；DB `from='appTest-11'` 仍為 `['1011']`、`from='appTest-11b'` 無列。
    - 雙語：API 回傳值斷言，單輪即可。
    - 清理：刪除 `from='appTest-11'`、`'appTest-11b'` 之列。
    - 備註：跨來源同鍵檢查於寫入前驗證之後、`delAll({ from })` 之前（`server/WWebPerm.mjs:syncAndReplaceTabs`，規則帳本 R-SYNC-01）；以 `String(id)` 直查資料表；srLog 記 `reason:'idOtherFrom'`。同來源之既有列不算衝突（隨後被全量取代）。修正前（w-serv-orm 1.1.11 下）回 success 而該列未寫入（見〈已知落差〉）。測試：`api-syncAndReplaceTabs` API-sync-011。

- **E2E-012**
  - title: 名稱或標的識別碼為空之推送被拒且資料不變
  - description: 外部應用推送權限群組或權限時，每一列都必須有名稱；推送標的時，每一列都必須有識別碼；名稱與識別碼都必須是不為空的文字。任何一列缺少、為空字串或不是文字（例如數字、true、null），伺服器於刪除任何資料之前拒絕整批推送（同批其他合法的列也不寫入），回傳 msg 為「invalidRows」，該來源與其他來源原有之資料都維持不變。使用者清單的推送不受此限，名稱可以重複或省略。外部應用請確認每一列都帶有名稱或識別碼。
  - flow:
    - 測試資料：base seed；以來源 `appTest-20`（grups、pemis）與 `appTest-21`（targets）先各推送一列合法舊列。
    - 操作：以合法 app token 對 `keyTable=grups`、`pemis` 推送 `name` 缺漏、空字串、數字 5、true、null 之列（單獨一列，或與合法列同批）；對 `keyTable=targets` 推送 `id` 缺漏、空字串、數字 5、true、null 之列。另以來源 `appTest-22` 推送合法的非空名稱（含中文與內嵌空白）與識別碼，以及 users 不帶名稱與名稱重複之列。
    - 驗證：
      1. 語意：違規推送皆回 `state='error'`、`msg` 為 `invalidRows`；該來源之全部欄位（含稽核時間）與其他來源之全部列拒收前後逐位元不變，只剩舊列。
      2. 語意：合法推送回 `state='success'`；users 不帶名稱、名稱重複亦成功。
    - 雙語：API 回傳值斷言，單輪即可。
    - 清理：刪除 `from='appTest-20'`、`'appTest-21'`、`'appTest-22'` 之列（`api-syncAndReplaceTabs` 之 after）。
    - 備註：檢查置於寫入前驗證之前、`delAll({ from })` 之前（`server/WWebPerm.mjs:syncAndReplaceTabs`，規則帳本 R-SYNC-NAME-01）；比照後台 `ckKey`（`procCore.mjs`）之 `isestr`；targets 仍只收字串識別碼（數字識別碼拒收，與後台一致）。測試：`api-syncAndReplaceTabs` API-sync-020～022（另 API-sync-017 之「僅 order:0 之列」改以 users 驗）。

  - title: 對應鍵重複之啟用使用者推送被拒
  - description: 權限系統以電子郵件或名稱對應外部系統的使用者時，啟用中的使用者之該欄位不得重複：同一批中兩位啟用中的使用者該欄位相同（逐字比對），或該欄位已被其他來源的啟用中使用者（含系統預設資料）使用，伺服器於刪除任何資料之前拒絕整批推送，回傳 msg 為「invalidRows」，本來源與其他來源原有之資料都維持不變。對應鍵重複時，登入會無法確定是哪一位使用者，因此必須事先避免。僅大小寫不同的值視為不同。自己這個來源先前推送過的同值列不算衝突。
  - flow:
    - 測試資料：base seed；後端以臨時設定重啟為 `mappingBy: 'email'`（另輪為 `'name'`）；來源 `appMk-6b`（`appMk-8`）先推送一位啟用中的使用者；來源 `appMk-3`（`appMk-7`）先推送一列合法舊列。
    - 操作：以合法 app token 對 `keyTable=users` 推送：同批兩位電子郵件相同之使用者（夾在合法列之間）；電子郵件取其他來源已有之值；電子郵件取 base seed 使用者 `peter@example.com`；僅大小寫或尾端空白不同之電子郵件；`mappingBy='name'` 時同批同名、取其他來源已有之名稱、取 base seed 之名稱 `admin`。
    - 驗證：
      1. 語意：同值者皆回傳 `state='error'`、`msg` 為 `invalidRows`，兩個來源與其他來源之全部列逐位元不變；僅大小寫或空白不同者回傳 `state='success'`。
    - 雙語：API 回傳值斷言，單輪即可。
    - 清理：同 E2E-024。
    - 備註：規則帳本 R-MAPKEY-01；批內重複為 `reason:'mapKeyDuplicate'`（`checkMapKeyBatch`），他來源已用為 `reason:'mapKeyOtherFrom'`（`findKeyOtherFrom`，`onlyActive`），後者位於 `idOtherFrom` 之後、`delAll({ from })` 之前，同樣以 `select()` 比對。測試：`api-mapKey` MK-002、MK-003、MK-006、`unit-keyCheck` KC-MK-004、KC-OF-004。

- **E2E-026**
  - title: 停用之使用者不參與對應鍵檢查
  - description: 權限系統以電子郵件或名稱對應外部系統的使用者時，只有「啟用中」的使用者需要有不重複的對應鍵：已停用的使用者，也就是 isActive 欄位不是 y 的使用者，該欄位可以為空、可以與其他使用者重複；其他來源已停用的使用者也不會造成衝突。這是因為登入時只會比對啟用中的使用者。
  - flow:
    - 測試資料：base seed；後端以臨時設定重啟為 `mappingBy: 'email'`；來源 `appMk-6` 先推送一位已停用之使用者。
    - 操作：以合法 app token 對 `keyTable=users` 以來源 `appMk-4` 推送：已停用且電子郵件為空之列、已停用且電子郵件與 base seed 啟用中使用者相同之列、啟用中之一位與已停用之一位電子郵件相同、`isActive` 為空字串之列；另以來源 `appMk-5` 推送一位啟用中使用者，電子郵件與 `appMk-6` 已停用之使用者相同；再以 `appMk-4` 重送同一電子郵件。
    - 驗證：
      1. 語意：皆回傳 `state='success'`；最後 DB 中 `appMk-4` 只剩重送之一列。
    - 雙語：API 回傳值斷言，單輪即可。
    - 清理：同 E2E-024。
    - 備註：規則帳本 R-MAPKEY-01；「啟用」判準為 `isActive==='y'`（與登入查找之 `isActive:'y'` 一致）。測試：`api-mapKey` MK-004、MK-005、`unit-keyCheck` KC-MK-005、KC-OF-004。

## 執行流程

端點 handler 以 `pm2resolve(core)()` 將 `core()` 的 resolve / reject 轉為 `{ state, msg }` 回傳（`state='success'` 對應 resolve，`'error'` 對應 reject）；`core()` 內任一 `Promise.reject` 即短路後續、不進入全量取代。

位置標註為符號錨 `[檔名:符號]`（函式或變數名；2026-10-21 起取代行號，行號會隨改版漂移）：`apis(/syncAndReplaceTabs)` 指 `server/WWebPerm.mjs` 內 `apis` 陣列中 `path: '/syncAndReplaceTabs'` 之項目，`.core` 為其 handler 內的 `core()`。

`syncAndReplaceTabs` 內之守門順序（先到先拒，皆在 `delAll` 之前）：`from` 為有效字串（`invalidFrom`）→ `rows` 為非空陣列（`isearr`，`invalidRows`）→ 每列為非空物件（`isRowObj`，`reason:'rowInvalid'`）→ `ltdtmapping` 對齊 schema 欄位 → 映射後非空白列（`rowBlank`，`reason:'rowBlank'`）→ `grups`／`pemis` 之 `name`、`targets` 之 `id` 為非空字串（`nameInvalid`／`idInvalid`）→ `grups`／`pemis` 之 `name` 批內不重複（`nameDuplicate`；2026-10-21 起）→ `users` 於 `mappingBy` 為 `email`／`name` 時之對應鍵批內非空且不重複（`mapKeyInvalid`／`mapKeyDuplicate`；2026-10-21 起）→ `validateRowsBeforeWrite`（`invalidRows`／`htmlMarkupNotAllowed`）→ 跨 `from` 同鍵（`idOtherFrom`）→ 跨 `from` 同名／同對應鍵（`nameOtherFrom`／`mapKeyOtherFrom`；2026-10-21 起）→ `delAll` + `insert`。除 `invalidFrom`（`from` 檢查）與 `htmlMarkupNotAllowed`（欄位含標記）外，其餘拒收之 `msg` 皆為 `invalidRows`，細部原因 `reason` 僅入 srLog。

## 欄位邊界

| 概念 | 處理 |
|---|---|
| `keyTable` | query 帶入；須屬白名單 `[targets, pemis, grups, users]`，否則 reject（`WWebPerm.mjs:apis(/syncAndReplaceTabs).core`） |
| `token` | query 帶入；經 `getAndVerifyAppUser` 守門（`getUserByToken` + `verifyAppUser`），非經 verifyConn / Bearer（`WWebPerm.mjs:getAndVerifyAppUser`） |
| `from` | payload 帶入；須為有效字串。`syncAndReplaceTabs` 以 `from` 為全量取代的範圍鍵：`delAll({ from })` 只刪該 `from` 的列、insert 前逐列複寫 `v.from = from`（`WWebPerm.mjs:syncAndReplaceTabs`） |
| `rows` | payload 帶入；須為**非空**陣列（`isearr`），空陣列被拒（`parsePayload` reject `invalidRowsInPayload`，`WWebPerm.mjs:parsePayload`），不支援以空陣列清空該 `from`。通過後各列須為非空物件（`isRowObj`，違者 `invalidRows`），再經 `ltdtmapping` 對齊 `ds[keyTable].keys`，映射後除伺服器管理欄外至少一欄帶有內容（`rowBlank`，違者 `invalidRows`）（`WWebPerm.mjs:syncAndReplaceTabs`） |
| 欄位白名單（端側） | `provideTabs` 以 `ks_targets` / `ks_pemis` / `ks_grups` / `ks_users` 白名單 `ltdtpick` 列資料（`server/provideTabs.mjs:ks_targets` / `ks_pemis` / `ks_grups` / `ks_users`、`provideTabs`）：四表共有 `id` / `order` / `description` / `from`；`pemis` 多 `name` / `crules`；`grups` 多 `name` / `cpemis`；`users` 多 `name` / `email` / `cgrups` / `isAdmin` / `isActive`；稽核欄位（`userId` / `time*`）一律被白名單排除（端側白名單 `ks_*` 內以註解停用 `userId` / `time*`，與此對齊，由後端 `procOrm` 補） |
| `name`（`grups`／`pemis`） | 須為非空字串（`nameInvalid`），本批內不得重複（`nameDuplicate`），不得已為其他 `from` 之既有列使用（`nameOtherFrom`）；精確 `===` 比對（`WWebPerm.mjs:syncAndReplaceTabs`、`keyCheck.mjs`） |
| 對應鍵（`users` 之 `email`／`name`，依 `mappingBy`） | `mappingBy` 為 `'email'`／`'name'` 時，啟用列（`isActive==='y'`）該欄位須非空且本批與他 `from` 之啟用列皆不重複（`mapKeyInvalid`／`mapKeyDuplicate`／`mapKeyOtherFrom`）；`'id'`（預設）不檢查（`WWebPerm.mjs:syncAndReplaceTabs`、`keyCheck.mjs:checkMapKeyBatch`） |
| 稽核欄位 | `userId` / `timeCreate` / `userIdUpdate` / `timeUpdate` 不由 payload 帶入，由後端 `procOrm` 於 insert 時自動補（`WWebPerm.mjs:syncAndReplaceTabs`） |
| `order` | `syncAndReplaceTabs` 路徑**不重給** order（`WWebPerm.mjs:syncAndReplaceTabs` 內註「order 大部分由外部給予, 不能複寫」），沿用 payload 帶入值 |

## i18n 訊息粒度規則

本端點為 server-side app API，回傳 `{ state, msg }` 為**機器可讀值**：`state` 為 `'success'` / `'error'`、`msg` 為 camelCase 錯誤 key（如 `tokenNoPermission` / `invalidKeyTable` / `cannotFindUserFromToken` / `userNoPermission` / `invalidPayload` / `invalidFromInPayload` / `invalidRowsInPayload` / `invalidFrom` / `invalidRows` / `htmlMarkupNotAllowed` / `saveWriteFail`；後兩者 2026-10-14 起，ADR-026）。上述 key 於 `server/procLang.mjs` 皆有 eng + cht 定義，由呼叫端（外部應用）以 key 查 lang 決定如何呈現。故本流程訊息粒度即「一個 reject key 對應一條 procLang 雙語訊息」。

## spec 規則摘要

- **權限**：`/syncAndReplaceTabs` 守門完全由端點 handler 內 `getAndVerifyAppUser`（query `token` → `getUserByToken` → `verifyAppUser`）負責；此自訂端點直接 `server.route` 註冊，**不經 verifyConn / Bearer header 通道**（verifyConn 僅守 orm exec 通道）。token 缺 / 無效 / 取不到使用者 / `verifyAppUser` 回 false 一律 reject；部署方注入之 `getUserByToken` / `verifyAppUser` 拋錯或 reject 視同取不到 / 回 false（W 契約，ADR-023），回應不含上游原文，srLog 另記 warn `inject-<函數名>-fail`。
- **取代模型**：本端點為「依來源 `from` 全量取代」——`syncAndReplaceTabs` 先 `delAll({ from })` 刪該應用既有列，再整批 `procOrm insert`，**非逐列 diff（無 ltdtDiffByKey、無 ckKey 去重）**。各應用以各自 `from` 隔離，互不影響彼此資料。
- **名稱／識別碼須為非空文字**（規則帳本 R-SYNC-NAME-01，ADR-031，2026-10-20 起；主控複審 R2）：比照後台整表寫入之 `ckKey`（`isestr`），`grups`／`pemis` 之 `name`、`targets` 之 `id` 缺漏、空字串、非字串（數字、布林、null）一律整批拒收（`invalidRows`，srLog 記 `reason:'nameInvalid'`／`'idInvalid'`），於 delAll 之前，該 `from` 與他 `from` 之既有列不變；`users` 不在範圍（名稱可重複、可省略）；〔原載「不比照 `ckKey` 之重複名稱偵測」2026-10-21 起不成立：重複名稱改由下一條規範，見 E2E-019～022〕。修正前 `name:''` 之群組／權限可入庫，伺服端 `arrFinder` 以 `===` 採納而編輯器視為無效，存檔即移除其授權。（2026-10-21 run05，ADR-035 決定 f：升級前已存在之空字串名稱列，伺服端仍以 `findRefRows` 精確 `===` 比對〔取代 `arrFinder`；列無 `name` 欄視為 `''`〕，編輯器改為原樣保留空字串名稱之引用〔物件鍵 `''`〕、不再於存檔時丟棄，故上述『存檔即移除其授權』不再發生；新寫入仍被本條拒收。）
- **群組／權限名稱須唯一**（規則帳本 R-NAME-UNIQ-01，ADR-034，F-02，2026-10-21 起）：`grups`／`pemis` 之 `name` 於本批內不得精確 `===` 重複（`nameDuplicate`），亦不得已被其他 `from` 之既有列使用（`nameOtherFrom`），整批 `invalidRows`，於 delAll 之前，兩個 `from` 與其他來源之既有列不變；同 `from` 之既有列不算衝突（隨後被全量取代）；僅大小寫或空白不同視為不同名稱（精確比對，不正規化）。授權依名稱查找、`arrFinder` 取第一個同名列，同名並存即授權取決於資料庫列序〔2026-10-21 run05 更正：查找現為 `findRefRows`，同名並存時內容取各筆之交集，與列序無關，並於引用處顯示警告圖示，ADR-035 決定 d；本規則仍用以防止新增同名〕。本端點仍為全量取代，**不是**逐列 diff／`ckKey`，此規則由 `server/keyCheck.mjs` 之同判準實現。`targets` 之 `id` 為主鍵（批內重複由 `validateRowsBeforeWrite` 擋、他來源由 `idOtherFrom` 擋），`users` 之名稱允許重複。**已存在之同名資料不被追溯拒絕**：清理見 README Upgrade Notes 與稽核工具 `test/tools/nameDupReport.mjs`（唯讀；改名級聯 F-07 未實作，改名或刪除其一須先盤點引用者）。
- **使用者對應鍵須非空且唯一**（規則帳本 R-MAPKEY-01，ADR-034，F-14，2026-10-21 起）：依部署之 `mappingBy`——`'id'`（預設）不另檢查；`'email'`／`'name'` 時，`users` 每個 `isActive==='y'` 之列該欄位須為非空文字（`trim()` 後長度 > 0；缺漏／空白／非文字 → `mapKeyInvalid`），本批內不得重複（`mapKeyDuplicate`），亦不得已被其他 `from` 之既有啟用列使用（`mapKeyOtherFrom`），整批 `invalidRows`，於 delAll 之前；比對用原值精確 `===`（與登入查找 `getTokenUser` 之 `select` 一致）；`isActive` 非 `'y'` 之列不參與（登入只比對啟用列）。**取捨**：不一律檢查 email——預設 `'id'` 之既有部署其 email 可空／可重複，新規則不應使其推送全部失敗；只有「對應鍵」才是登入查找之鍵。登入端相對規則見 `流程_查詢使用者權限.md` E2E-007（多筆命中拒絕）。
- **寫入前驗證**（ADR-026）：全量取代為「先 delAll 再 insert」且無交易；可預判之寫入失敗（主鍵非字串或數字、UTF-8 超過 1978 位元組、批內重複、本批有給之主鍵已屬其他 from（以 `String(id)` 比對，2026-10-14 run05 起）、任一欄位值為物件／陣列等非純量（四表欄位型別只有字串、整數、文字，`cgrups`／`cpemis`／`crules` 為 JSON 字串而非物件，2026-10-20 起，規則帳本 R-FIELD-SCALAR-01）→ `invalidRows`；任一字串欄位會被 XSS 清除改寫 → `htmlMarkupNotAllowed`）一律於 delAll 之前擋下，該 `from` 既有列不變；delAll／insert 之 ORM／I/O 失敗回 `saveWriteFail`（部分變更可能已生效），原文只入 srLog。
- **空陣列語意**：`rows=[]` **被拒**（`parsePayload` 以 `isearr` 要求非空陣列，`WWebPerm.mjs:parsePayload`），回 `state='error'`、`msg` 為 `invalidRowsInPayload`，**未進 delAll**，故不支援「以空集合清源」；此為防外部應用誤送空陣列而整批清空資料之安全閘。
- **欄位**：
  - 四表共用同一全量取代路徑，差別僅 `ds[keyTable].keys`（schema）與端側白名單 `ks_*`。
  - 端側 `provideTabs` 以白名單 `ltdtpick` 過濾欄位，稽核欄位（`userId` / `time*`）一律排除、由後端 `procOrm` 補。
  - `order` 在此路徑沿用外部帶入值，不重給（與後台瀏覽器寫入路徑會重給 order 不同）。
- **回傳**：成功 resolve → `{ state:'success', msg }`，`msg` 為 insert 之回報 `[{ id }]`，id 一律為字串（數字主鍵以其字串形式回報，w-serv-orm 1.1.11 起；修改留痕 2026-10-14 run05）；任一檢查 / 守門 reject → `{ state:'error', msg }`（`msg` 為 camelCase 錯誤 key，如 `tokenNoPermission` / `invalidKeyTable` / `invalidFromInPayload` / `invalidRowsInPayload` / `invalidPayload`），於 `procLang.mjs` 皆有 eng + cht 定義，由呼叫端以 key 查 lang 呈現。
- **契約**：handler 採 `pm2resolve(core)()` 統一將 core 的 resolve / reject 轉 `{ state, msg }`；core 內各檢查階段以 `Promise.reject` 短路後續，僅全部通過才進入全量取代。
