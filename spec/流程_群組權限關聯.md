# 群組權限關聯流程

## 觸發

管理員（瀏覽器使用者，經 w-ui-loginout 登入取得有效 token、後端 `verifyConn` 守門）進入後台後，可由兩個入口進入「群組與權限的關聯」編輯。兩入口操作的是同一份資料 `grups.cpemis`（一個 JSON5 字串，結構為 `{ 權限名: { mode: 'OR'|'AND', isActive: 'y'|'n' } }`），差別只在切入角度：

- **群組清單頁入口**：於 `LayoutContentGrups.vue` 列出 `grups` 表，`cpemis` 欄渲染為一顆按鈕（顯示已啟用權限數量）；點該按鈕呼叫 `showVeCpemisById(id)`（`LayoutContentGrups.vue:showVeCpemisById`），開啟群組權限關聯對話框 `VeCpemis`。此對話框以「該群組擁有哪些權限」為視角，逐列權限可勾選啟用（`enable`）、選 OR / AND 合併模式（`mode`）。

- **權限清單頁入口**：於 `LayoutContentPemis.vue` 列出 `pemis` 表，`belongGrups` 欄（表頭「管控所屬權限群組」）渲染為一顆按鈕（顯示隸屬群組數量）；點該按鈕呼叫 `showVePemiBlngGrupsById(id)`（`LayoutContentPemis.vue:showVePemiBlngGrupsById`），開啟權限隸屬群組對話框 `VePemiBlngGrups`。此對話框以「該權限被哪些群組使用」為視角，欄位依序為「權限群組名稱、是否使用、所屬權限名稱」（本列自己可改的在左、由其他權限帶來的在右）；勾選「是否使用」即把此權限掛入該群組，合併模式不另設欄，而是併入右欄代表本權限的那顆標籤（`VePemiBlngGrups.vue` template 之 `RelationChips`），點該標籤左段即展開 OR / AND 清單。

兩入口的對話框是否可編輯，皆由各自清單頁的編輯模式 `isEditable` 決定並隨 `show()` 傳入（`LayoutContentGrups.vue:showVeCpemisById`、`LayoutContentPemis.vue:showVePemiBlngGrupsById`）：`isEditable=true` 顯示「群組權限編輯」/「權限隸屬群組編輯」標題與功能列、可勾選與存檔；`isEditable=false` 顯示「（檢視）」標題（`grupEditCpemisForDisplay` / `pemiBlngEditGrupsForDisplay`），模式控制項與 checkbox 一律不可操作、隱藏功能列與 Save 按鈕，僅供唯讀檢視。

兩入口的存檔落點不同（皆寫入同一張 `grups` 表）：

- **VeCpemis（群組頁入口）**：對話框 Save 不直接打 API，而是把編輯後的 `cpemis` 字串 resolve 回群組頁；群組頁於 `showVeCpemisById.then` 寫回該列 `opt.rows[kr].cpemis` 並設 `isModified=true`（`LayoutContentGrups.vue:showVeCpemisById`），真正寫入 DB 延到管理員按群組頁工具列的 `saveGrups` 按鈕 → `updateGrups`。
- **VePemiBlngGrups（權限頁入口）**：對話框 Save 自帶存檔，於 `clickSave`（把按鈕鎖 `msg.pm` 交給 `doSave`，不於 handler 解鎖）→ `doSave` 以 `$ui.runSubmit('savePemiBlngGrups', …)` 包覆 `core()`，其內直接呼叫 `saveGrups(grupsNew)` → `$fapi.updateGrups(rows)` 即時寫入 DB（`VePemiBlngGrups.vue:clickSave,doSave,saveGrups`），存檔成功即關閉對話框（ADR-025；修改留痕 2026-09-29：原載「`clickSave` 第一行 `pm.resolve()` → fire-and-forget `doSave`」）。

寫入端點 `updateGrups` 經 hapi `verifyConn` 刪 Bearer 取 token → `checkToken(token, apiType)` → `getAndVerifyClientUser` 守門（`server/WWebPerm.mjs:verifyConn`、`p.checkToken`、`getAndVerifyClientUser`）：token 須可由部署方 `getUserByToken` 解出使用者、該使用者須存在於 perm `users` 表且 `isActive='y'`（`server/WWebPerm.mjs:getTokenUser`）、並通過部署方 `verifyClientUser(user, from)`（資料通道之 from 為 apiType，如 `main`），**任一不符即拒絕連線**（ADR-015，2026-09-29 業主裁示資料通道採嚴格預設）；是否限定管理員由 `verifyClientUser` 決定。

## 重要流程

- **E2E-001**
  - title: 管理員從群組頁點 cpemis 按鈕開啟群組權限關聯對話框
  - description: 管理員在權限群組清單頁開啟編輯模式後，點某列「管控使用權限」欄的按鈕，畫面開啟「編輯使用權限」對話框，逐列列出全部權限，每列有權限名稱、「合併權限模式」控制項與「是否使用」勾選框，模式控制項顯示 OR 或 AND 且點開可選；該群組既有的權限設定會回填為對應列的勾選與模式，未勾選的列其模式控制項呈淡色不可點。適合檢視並調整某個權限群組使用哪些權限。
  - flow:
    - 測試資料：base seed 既有 grups / pemis，取一既有群組列作開啟標的，不另建特化資料。
    - 操作：登入後台 → 點「群組」頁籤 → 開啟編輯模式 → 點該列 cpemis 欄按鈕。
    - 驗證：
      1. 語意：對話框出現，標題為 `grupEditCpemis`；表格逐列列出 base seed 各權限名，每列含模式控制項（`ModeSelectChip`，整顆 56×22 落在 27px 儲存格內）與啟用 checkbox；已勾選列之控制項可展開、未勾選列 `editable=false`（透明度 0.6、無展開箭頭、點擊不展開，見 `VeCpemis.vue` template 之 `ModeSelectChip` 欄）。
      2. 視覺：本 case 為多階段截圖，依序與下列 baseline 視覺一致（pixelmatch 容差）：①「來源群組列（點 cpemis 按鈕前）」`test/pics/rela-grup-pemi/rela-grup-pemi-{eng,cht}-E2E-001-1-source-row.png`；②「VeCpemis 對話框初始態」`test/pics/rela-grup-pemi/rela-grup-pemi-{eng,cht}-E2E-001-2-dialog-open.png`。
    - 雙語：eng / cht 各一輪。
    - 清理：關閉對話框、不存檔，DB 不變。

- **E2E-002**
  - title: 管理員於群組頁對話框勾選權限並選 OR/AND 後存檔成功
  - description: 管理員在「編輯使用權限」對話框勾選某個權限的「是否使用」後，該列的模式控制項由淡色轉為可點，點開後可選 OR 或 AND；選 AND 並點對話框的儲存鈕，設定即回填到權限群組清單該列的「管控使用權限」欄，欄內摘要由「使用 2 項權限」改為「使用 3 項權限」；此時再按清單頁工具列的儲存鈕才真正寫入資料庫，完成後顯示「儲存權限群組數據成功」。適合一次調整某個群組的多項權限後再統一存檔。
  - flow:
    - 測試資料：base seed grups / pemis；取一既有群組列、選一原本未啟用的權限作勾選標的。
    - 操作：開啟編輯模式 → 點該列 cpemis 按鈕 → 於對話框勾選某權限 checkbox（該列模式控制項隨即由淡化轉為可點）→ 點該列之模式控制項並選 AND → 點對話框 Save → 點群組頁工具列存檔按鈕。
    - 驗證：
      1. 語意：對話框關閉；群組頁出現 `grupSaveGrupsSuccess` 提示；DB 該群組 `cpemis` 解析後對應權限為 `{ mode: 'AND', isActive: 'y' }`。
      2. **解析後權限樹（權限系統核心，不可省）**：以 `getPermUserInfor` 查屬該群組之 user（peter 屬 M1），其 resolved rules 的 active target 集合須反映此變更的**合併語意**——M1 加 P3 且 mode=AND 後，peter 權限樹由 baseline 4 個（P1∪P2）經 **AND 交集** P3 縮為 2 個（`專案A/頁C`, `專案B/頁A/區塊B`；P3 未列 `專案A/頁A/區塊A`，未列視同 `n`，故 P1 授予的該對象被收回；原載 3 個〔含 `專案A/頁A/區塊A`〕，2026-10-21 起不成立，ADR-033）。**不可只驗 `cpemis` 設定資料存對、須驗其解析後的最終權限樹（外部應用實際查到的、含 OR/AND 合併效果）**。預期值由 `getUserRules` 演算法算出。
      3. 視覺：本 case 為多階段截圖（每步兩張），依序與下列 baseline 視覺一致（pixelmatch 容差），檔名前綴 `test/pics/rela-grup-pemi/rela-grup-pemi-{eng,cht}-`：①「來源群組列 M1（點按鈕前）」`E2E-002-1-source-row.png`；②「對話框初始態（操作前）」`E2E-002-2-dialog-open.png`；③「點擊前框住 權限P3 列之 enable checkbox」`E2E-002-3-click-enable.png`；④「勾選後框住該列（checkbox 已勾、模式控制項轉為可點、Save 鈕現身）」`E2E-002-4-enable-checked.png`；⑤「點擊前框住該列之模式控制項整顆（56×22、方角 4px）」`E2E-002-5-click-mode.png`；⑥「清單展開，框住整份清單（OR / AND 兩列，左緣與控制項外框齊）」`E2E-002-6-list-open.png`；⑦「點擊前框住清單中「AND」項目整顆」`E2E-002-7-click-and.png`；⑧「選取後框住該列（模式控制項顯示 AND）」`E2E-002-8-row-toggled.png`；⑨「點擊前框住對話框 Save 鈕」`E2E-002-9-click-save.png`；⑩「對話框關閉後框 M1 列，cpemis 摘要已回填「使用 3 項權限」、頁面儲存鈕現身」`E2E-002-10-cpemis-filled.png`；⑪「點擊前框住群組頁工具列存檔鈕」`E2E-002-11-click-page-save.png`；⑫「群組頁存檔成功 modal」`E2E-002-12-cpemis-save-ok.png`；⑬「存檔後 M1 列摘要維持「使用 3 項權限」且儲存鈕消失（數據變更證明）」`E2E-002-13-data-changed.png`。
    - 雙語：eng / cht 各一輪。
    - 清理：將該群組 `cpemis` 改回原值並存檔，還原 base seed。
    - 備註：解析後權限樹之數字（2 個）為 2026-10-21 以 `getUserRules` 對種子資料（schema `funTest`）實算，舊規則（ADR-001）實算為 3 個；真後端 `getPermUserInfor` 之 e2e 實測值待回填。

## 執行流程

兩入口的對話框 Save 路徑不同，分別 trace。位置標註為符號錨 `[檔名:符號]`（函式名；2026-10-21 起取代行號，行號會隨改版漂移）；步驟編號於同日重排。兩入口寫入 `cpemis` 前皆經 `cvKpToObj`（解碼）、`getKpLossy`（無法無損表示之判定，2026-10-21 起為「同名同時為有效 OR 與 AND」、「啟用而名稱非字串之項目」及「該層啟用項皆 mode 缺或不合法」三格，ADR-033、ADR-035；第三格為同日主控裁決之限制項語意的連帶，E2E-010；第三格已於 2026-10-22 run06 放寬而不再判有損，現為前兩格）與拒存分支（`authLossyBlocked`，ADR-030／031）。授權合併與項目之儲存順序、物件鍵序、陣列元素序無關（`R-AUTH-MERGE-00` 第 4 條，ADR-033），故編輯器不再保留原鍵序（`keepKeyOrder`）、不再判定鍵序易位（`getKpWriteLost`、`getKeyOrderLost`），三者及其拒存分支已於 2026-10-21 刪除，步驟編號於同日再次重排（群組頁入口由 071 步縮為 069 步、權限頁入口由 047 步縮為 045 步）；見各路徑對應步驟。

## spec 規則摘要

- **權限**：兩入口存檔皆經 `verifyConn → checkToken → getAndVerifyClientUser` 守門（token 須有效、其使用者須在 perm `users` 表且 `isActive='y'`、並通過部署方 `verifyClientUser` 才可寫；ADR-015 嚴格預設；是否限管理員由 `verifyClientUser` 決定）；後端確保 `grups` name 不可空、本次寫入不得造成或觸及同名（`ckKey('name')` 驗空值／非字串、`findTouchedDup` 驗唯一，歷史既有同名原樣送回不拒；ADR-034、ADR-035 決定 g；原載『`ckKey('name')` 確保 name 不可重複』自 ADR-034 起不成立）。
  - 修改留痕（2026-09-29）：原載「經 `verifyConn → checkToken` 守門（有效 token 才可寫）」、觸發段引 `WWebPerm.mjs` 之舊行號——行號已漂移（2026-10-21 起本 spec 全面改用符號錨），且未載 perm `users` 表／`isActive` 與 `verifyClientUser` 之要求；ADR-015 業主裁示資料通道維持嚴格預設後，依現行碼（`WWebPerm.mjs:p.checkToken` → `getAndVerifyClientUser`）改寫本段、觸發段與執行流程之守門行。
- **同源異視角**：群組頁入口（VeCpemis）與權限頁入口（VePemiBlngGrups）編輯的是同一份 `grups.cpemis`，僅切入視角不同——前者以「群組擁有哪些權限」逐列權限，後者以「權限被哪些群組使用」逐列群組。
- **存檔落點差異**：
  - VeCpemis（群組頁入口）Save **不即時打 API**，只把 `cpemis` 字串 resolve 回群組頁該列並設 `isModified=true`；真正 DB 寫入延到群組頁工具列 `saveGrups → updateGrups`。
  - VePemiBlngGrups（權限頁入口）Save **自帶即時 DB 寫入**，於 `core() → saveGrups → $fapi.updateGrups` 直接落庫、成功後關閉對話框。
- **唯讀檢視**：`isEditable=false` 時兩對話框皆顯示檢視版標題、隱藏功能列與 Save；群組頁入口之模式下拉淡化不可展開、權限頁入口之標籤模式段為純文字，checkbox 一律 disabled，僅供檢視不可改。
- **粒度**：對話框內切換防呆（無 name / 無目標）走 `$alert`；存檔結果（成功 / 失敗 / 空）一律走 `showCheckYes` DOM 模態；群組 name 錯誤 Save 擋存彙整為 `errInNames`。
- **容錯與列身分配對（權限頁入口，ADR-032）**：①`genItems`／`revRows`／`doSave` 對每個群組之 `cpemis` 解碼失敗（空字串即後台新增群組之預設值、壞 JSON）一律視為空容器，不使對話框打不開、不使存檔拋例外（R-REL-PARSE-01）；壞 JSON 列之本權限歸屬未變時其字串逐字不動；②對話框之列帶群組 `id`，`revRows` 與 `doSave` 一律以 `id`（並驗 `name` 相同——群組被改名視為過期；不以列索引）配對 store 中之群組（`pairRowsToSnapshot.mjs:pairRowsToSnapshot`），開框後他人重排 `order` 或增刪其他群組不影響配對；對話框之某列所對應的群組已被刪除或改名 → 整次拒存並顯示 `relationRowsStale`（R-REL-PAIR-01）。
- **授權不變與合併規則（`R-AUTH-MERGE-00`，ADR-033，2026-10-21）**：伺服端合併結果與 `cpemis` 之鍵序、陣列元素序無關（先對全部 OR 項聯集、再與全部 AND 項交集，未列之管理對象視同 `n`），故兩入口存檔皆不保留原鍵序、也不判定鍵序易位；拒存為「原字串（陣列形式）含同名同時為有效 OR 與 AND」一格（物件形式一個名稱只有一個 `mode`，無法無損表示），另自 2026-10-21 run05（ADR-035 決定 f）起增「啟用而名稱非字串之項目」一格，同日主控裁決限制項（決定 e）後再增「該層啟用項皆 mode 缺或不合法」一格（`getKpLossy` 第三格，物件與陣列形式皆然，E2E-010；理由：編輯器解碼為 AND，存檔後該項成為唯一基底而授予內容，比存檔前多給；**2026-10-22 run06 使用者裁示放寬，該格不再拒存**：存檔時未被管理者改動之限制項原樣寫回其原始 mode〔方案 A〕，授權不多給，見 ADR-035 Update），群組頁入口另增「權限表同名多列設定不一致」一格（與有損判定無關、由對話框之列判定；行為同 `流程_使用者群組關聯.md` E2E-013、E2E-014）：群組頁入口列內容有任何變更即拒存、權限頁入口有損群組列之本權限歸屬或模式有變更即整次拒存。兩入口皆為兩態（勾／不勾）：未勾選之權限在群組頁入口寫為 `isActive:'n'`、在權限頁入口不寫入，該項不參與合併，與原本未列等價。原載「兩個以上 AND 權限時合併依鍵序、存檔須保序、AND 名稱易位須拒存」自 2026-10-21 起不成立。
- **遇衝突或歧義一律收嚴並於引用處提示（ADR-035，2026-10-21 run05，使用者原則「收嚴＋增加提示」）**：伺服端對引用查無（懸空）者以其模式參與、內容全 `n`（AND 使該群組授權為空），對同名多筆取交集，對模式缺或非法者視為「限制項」——只當 AND 交集項、不單獨成為基底，該層沒有任何 mode 合法之啟用項時該層結果全 `n`（`流程_權限規則合併計算.md` E2E-017～019；此細節與帳本 R-AUTH-MERGE-00 第 5 條『視為 AND』字面不同之一格，為主控依原則 3 取較嚴者，待主控／使用者確認）；編輯器同步：①存檔**不丟棄啟用中的引用**——懸空引用以額外列保留（可改為停用，E2E-008）、名稱 `''` 原樣寫出、模式缺或非法之啟用項顯示並存為 AND（該層另有 mode 合法之啟用項時存檔後授權不變）；②**無法保留者拒存**——啟用而名稱非字串之項目、權限表同名多列設定不一致（行為同 `流程_使用者群組關聯.md` E2E-013、E2E-014）；該層啟用項皆 mode 缺或不合法者**可存**（2026-10-22 run06 放寬：未被管理者改動之限制項原樣寫回其原始 mode、授權不變，警告圖示保留，E2E-010、`流程_使用者群組關聯.md` E2E-016；原載列為拒存之一不成立）；③權限頁入口改寫另一個群組之字串時只動本權限一項，其餘引用原樣保留（E2E-009）；④有衝突之引用於名稱儲存格（群組頁入口）、「所屬權限名稱」儲存格（權限頁入口）、群組清單頁 `cpemis` 欄左側顯示警告圖示，tooltip 見〈i18n 訊息粒度規則〉；**無衝突之資料列畫面與修改前逐像素相同**（既有標準圖不變）。
- **契約**：兩入口之打 API 存檔鈕 handler（VePemiBlngGrups `clickSave` / 群組頁 `saveGrups`）把按鈕鎖 `msg.pm` 交給各自之 `doSave` / `doSaveGrups`、不於 handler 解鎖；`doSave` / `doSaveGrups` 以 `$ui.runSubmit('savePemiBlngGrups' / 'saveGrups', …)` 包覆 `core() + .then/.catch/.finally`，`finally` 一處關 loading；`updateGrups` 失敗由 `okSave` 旗標短路後續、走 `grupSaveGrupsFail` 失敗提示。VeCpemis 之 Save 不打 API（只 resolve 回群組頁），刻意保留第一行 `pm.resolve()`、不套 runSubmit。（修改留痕 2026-09-29：原載兩入口皆「第一行 `pm.resolve()` 後 fire-and-forget」，已由 ADR-025 改寫。）
- **送出入口與連按**（ADR-025）：兩對話框之 Save 為 WDialog 內建鈕（promiseUnlock），全頁 loading 與訊息框（WDialog）只擋滑鼠、不搶焦點；打 API 者之按鈕鎖涵蓋請求期間，流程狀態涵蓋至結果訊息框關閉，期間再觸發即略過；後端同一操作者並行寫 `grups` 之第 2 次回 `saveInProgress`。對話框為單例：開啟中再次 `show()`（如焦點留在開啟鈕時按 Enter）時，舊階段之等待者視同關閉（`reject('close window')`，同按 Close），不再永久懸置。
