# 多人同時編輯流程

## 觸發

管理員（瀏覽器使用者，經 w-ui-loginout 登入取得有效 token、`connState='csLogin'`）進入後台後，於 `LayoutContent.vue` 左側導覽點「管理使用者」（`mmUsers`）、「管理權限群組」（`mmGrups`）、「管理權限」（`mmPemis`）、「管理對象」（`mmTargets`）進入四個清單頁（`LayoutContentUsers.vue`、`LayoutContentGrups.vue`、`LayoutContentPemis.vue`、`LayoutContentTargets.vue`；各以 ag-grid〔`WAggridVue`〕列出其表之全部列，預設為編輯模式），並於群組頁各列「管控所屬使用者」欄之按鈕開啟「編輯所屬使用者」對話框（`VeGrupBlngUsers.vue`）、於權限頁各列「管控所屬權限群組」欄之按鈕開啟「編輯所屬權限群組」對話框（`VePemiBlngGrups.vue`）。本文件涵蓋 2026-10-23 perm-run01（改用 w-serv-orm 1.1.17 共用核心之多人同時編輯寫入契約；使用者 2026-10-22 裁示原則 10；`spec/設計要點與取捨.md` ADR-037 Update〔perm-run01〕決定 32～39）後使用者可觀察之行為：自己存檔後立即再存、對話框開而未編輯時收到他人變更而重建、儲存格編輯器開啟中視為草稿、反向對話框主體被取代而拒存、他人只重排被偵測、舊格式基準被拒、前端基準與伺服端同構；另涵蓋 2026-10-23 perm-run02（正反關聯與主體身分檢查前後端都做；使用者 2026-10-23 裁示「正反關聯與主體身份檢查,應該是前後端都要做」；`spec/設計要點與取捨.md` ADR-037 Update〔perm-run02〕）後使用者可觀察之行為：反向對話框主體被取代時，即使畫面尚未收到更新，伺服端仍於主體表鎖內拒收；清單頁新指派之群組、權限、對象被同名取代或被刪除時，前端先攔下，前端未攔到時由伺服端於被引用表鎖內拒收；被引用實體正常時存檔成功且隨請求送出引用身分宣告；對象刪除後以同路徑重建視為同一實體。另涵蓋 2026-10-23 perm-run03（宣告強制必帶；使用者 2026-10-23 裁示「這本來就該強制必帶吧? 要不然怎麼確認與驗證調用者身份?」；`spec/設計要點與取捨.md` ADR-038）後之行為：凡存檔「改變了引用」（新增或移除啟用之引用項、新增列帶引用；整列刪除不算）而請求未附被引用實體之身分宣告，伺服端整次拒收（`saveIdentityRequired`，零寫入）；前端清單頁與反向對話框恆隨請求送出宣告（本輪起清單頁之宣告另納入被移除之名稱，正向路徑見 E2E-038），故使用者於畫面上不會遇到此拒收，僅繞過前端之直打 RPC 與未附宣告之舊版頁面可觸發；另涵蓋寫入類 RPC 之呼叫者身分驗證（資料通道執行身分須完整驗證、`updateTargets`／`updatePemis`／`updateGrups`／`updateUsers` 須為 perm users 表中有效之管理員，API 層、無 UI 案例，見〈規則摘要〉）。〔2026-10-23 perm-run03：原載之「未帶宣告者維持名稱引用原行為」相容已取消，逐處標原載不成立。〕他人改列、增列、刪列之先動先贏與橫幅、提示本身之畫面見姊妹文件 `流程_外部列保護與過期快照.md`。

名詞：**他人**＝另一位管理員（e2e 以管理者寫入 RPC 模擬）或外部來源（e2e 以外部同步端點 `/syncAndReplaceTabs` 模擬）；**推播**＝伺服端表異動後客戶端重抓整表並以新陣列取代 store 該表（約 2 秒輪詢，見 `src/js/draftSync.mjs` 檔頭註解）；**基準**＝編輯草稿所依據之整表之有序摘要 `[[id, 'h1:…'], …]`，隨存檔請求送出，伺服端於表鎖內與庫內整表比對；**名次**＝列依（`order` 數值，主鍵碼元序）排序之次序；**主體**＝反向對話框所編輯其歸屬之群組（`VeGrupBlngUsers`）或權限（`VePemiBlngGrups`）；**主體摘要**＝反向對話框開框時記下之 `{ id, name, saved }`，存檔前由前端對 store 自檢，並隨存檔請求（`opt.subject`）送伺服端，於主體表鎖內以新鮮讀取再驗；**引用身分宣告**＝清單頁存檔時隨請求送出之 `opt.refs`＝`[{ name, ids }]`，列出本次新增或移除之啟用引用項（`users.cgrups` 之群組、`grups.cpemis` 之權限、`pemis.crules` 之對象）名稱，各附使用者於編輯器選取當時（移除者為編輯器開啟當下）該名稱對應之被引用實體 id 陣列，伺服端於被引用表鎖內以新鮮讀取重算比對；改變引用之存檔**必須**附宣告，否則 `saveIdentityRequired`（perm-run03 起；〔原載「列出本次新增之啟用引用項」「未帶者維持名稱引用原行為」2026-10-23 起不成立：移除亦須宣告、未帶者拒收〕）；**被引用實體被取代**＝被引用實體被刪除，或刪除後以同名重建（id 不同）；對象之 id 即路徑（名稱），其身分定義即 id。

版面分區：清單頁為標題區、功能區工具列（`data-fmid="<表>-toolbar"`）、橫幅區（外部列提示、同步警示、資料已被更新；`data-fmid="<表>-banner-stale"` 等，無內容時不渲染任何節點）、表格；進入後預設狀態為編輯模式開、無列被勾選、無儲存鈕（儲存鈕只在編輯模式且有未存變更時渲染）。反向對話框為標題列（儲存鈕只在可編輯且有變更時渲染，關閉鈕恆渲染）、工具列、過期提示區（`grup-blng-users-banner-stale`／`pemi-blng-grups-banner-stale`，無提示時不渲染任何節點）、表格（名稱、「是否使用」核選方塊、關聯 chip 三欄）；對話框列內無可編輯儲存格（`kpCellEditable` 皆為 false，「是否使用」為即時提交之核選方塊）。

案例檔為 `test/e2e-concurrent-edit.test.mjs`：38 案（E2E-001～038）× eng／cht ＝ 76 個 `it`，全為語意案例，無標準圖、無 `--baseline` 模式。〔2026-10-23 perm-run02: 原 24 案 48 個 `it`，新增 E2E-025～037 共 13 案 26 個 `it`（E2E-037 為外審 sol#1 補之同名跨列選取衝突案）。〕〔2026-10-23 perm-run03: 新增 E2E-038（取消勾選既有引用後存檔，驗「移除亦須宣告」之正向路徑）1 案 2 個 `it`，共 38 案 76 個 `it`；原載「案數不變（仍 37 案、74 個 `it`）」不成立。`it` 數依檔內結構靜態計數、未跑測試：檔內 `it(` 字面僅 1 處（位於「語系 × 案例」迴圈），實際個數＝案例 38 × 語系 2 × 重複次數 1（環境變數 `CE_REPEAT` 預設 1）；案例 38 ＝ 單點案例 15（`nm(` 於迴圈外 15 處）＋ 迴圈生成 23（`PAGES` 四頁 × 3 個迴圈＝12、users／grups 兩頁 × 1 個迴圈＝2、`REF_PAGES` 三頁 × 3 個迴圈＝9）。E2E-019 之外部列夾具改依 `srcKey` 差異同步（見該案例留痕）；E2E-025～037 因前端恆送宣告，行為與斷言不變；「宣告強制必帶」之拒收 `saveIdentityRequired` 與「呼叫者身分驗證／管理員角色檢查」之拒收 `userNotAdmin` 等 UI 不可達或本檔帳號恆為管理員，不設 e2e 案例，由單元／API 層涵蓋，見〈訊息對照〉〈規則摘要〉〈已知落差〉。〕

## 重要流程

- **E2E-001**
  - title: 使用者頁存檔成功後立即再存仍成功
  - description: 管理員從左側選單點選「管理使用者」進入使用者清單頁，雙擊某位使用者的「說明」欄輸入新內容，點擊「儲存變更」，出現「儲存使用者數據成功」，點擊「確認」關閉訊息；說明此時已寫入資料庫，清單顯示剛儲存的內容，儲存鈕消失，清單上方沒有「資料已被他人或外部同步更新」橫幅。管理員不必等系統約 2 秒一次的資料更新，可立刻再雙擊同一位使用者的「說明」欄輸入第二次內容並再次儲存，同樣出現「儲存使用者數據成功」，不會被自己上一次的存檔擋下。若第二次儲存跳出「儲存使用者數據失敗」接「未儲存：載入此頁面後資料已被他人或外部同步更新。資料未變更，請重新整理頁面後再操作。」，表示確有他人改過資料，請重新整理頁面後再編輯。便於連續修改同一筆資料。
  - flow:
    - 測試資料：base seed（B-U2 mary，`id-for-mary`）；第一次說明 `CE-a1-users`，第二次說明 `CE-a2-users`。登入身分為管理員 token `sys`。
    - 操作：登入後台 → 點「管理使用者」頁籤，等 store 載入 4 筆 →（測試端開始攔住網路推播，見〈規則摘要〉手段說明）→ 雙擊 mary 之說明儲存格輸入第一次說明（Enter）→ 點「儲存變更」→ 結果訊息框點「確認」→（推播仍被攔住）立即再雙擊 mary 之說明儲存格輸入第二次說明（Enter）→ 點「儲存變更」→ 結果訊息框點「確認」→（測試端放行被攔住之推播）→ 觀察 1.5 秒。
    - 驗證：
      1. 語意：第一次存檔出現 `userSaveUsersSuccess`（文字見〈訊息對照〉）；點「確認」後 store 內 mary 之說明已等於第一次說明（網路推播仍被攔住，更新來自存檔回傳之寫入後之列）、儲存鈕消失、`users-banner-stale` 為 0 節點。
      2. 語意：立即再存之第二次存檔出現 `userSaveUsersSuccess`，不出現失敗框（不被自己上一次之存檔誤擋為 `saveStale`）。
      3. 語意：放行被攔住之推播並觀察 1.5 秒後，`users-banner-stale` 仍為 0 節點、儲存鈕不出現（其後抵達之同內容推播不視為他人更新）。
      4. 語意：庫內 mary 之說明等於第二次說明。
      5. 視覺：無標準圖（純語意案例，理由見〈規則摘要〉標準圖通則）。
    - 雙語：eng / cht 各一輪（成功訊息文字語系不同）。
    - 清理：案例結束以 `createIsolation().restore()` 還原——先以 `purgeExternalRows` 刪外部列夾具（本案無），再經管理者寫入 RPC 把 users、grups、pemis 整表寫回案前快照；回驗三表筆數等於快照且無外部列殘留。mary 之說明由整表寫回復原。
    - 備註：存檔 RPC 帶 `{ baseline, returnRows:true }`，成功回 `{ msg, rows, others }`（`server/procCore.mjs:updateTabItems` 之 `readAfter`）；`LayoutContentUsers.vue:saveUsers` 於 `isModified=false` 與 `syncMark.dirty=false` 之後呼叫 `applySavedRows`（`src/js/applySaved.mjs`）以 `source:'savedRows'` commit，清單頁依既有 `changeParams` 流程以之重建畫面與基準。測試端攔網路推播時放行此 commit，故驗得到「不待推播」。操作者點「確認」後才再編輯，是真實使用者之最快路徑。與 E2E-002～004 為四清單頁之對稱案例（`PAGES` 組態），與 E2E-005／006 為對話框之對稱路徑。
