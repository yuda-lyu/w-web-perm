# 多人同時編輯流程

## 觸發

管理員（瀏覽器使用者，經 w-ui-loginout 登入取得有效 token、`connState='csLogin'`）進入後台後，於 `LayoutContent.vue` 左側導覽點「管理使用者」（`mmUsers`）、「管理權限群組」（`mmGrups`）、「管理權限」（`mmPemis`）、「管理對象」（`mmTargets`）進入四個清單頁（`LayoutContentUsers.vue`、`LayoutContentGrups.vue`、`LayoutContentPemis.vue`、`LayoutContentTargets.vue`；各以 ag-grid〔`WAggridVue`〕列出其表之全部列，預設為編輯模式），並於群組頁各列「管控所屬使用者」欄之按鈕開啟「編輯所屬使用者」對話框（`VeGrupBlngUsers.vue`）、於權限頁各列「管控所屬權限群組」欄之按鈕開啟「編輯所屬權限群組」對話框（`VePemiBlngGrups.vue`）。本文件涵蓋 2026-10-23 perm-run01（改用 w-serv-orm 1.1.17 共用核心之多人同時編輯寫入契約；使用者 2026-10-22 裁示原則 10；`spec/設計要點與取捨.md` ADR-037 Update〔perm-run01〕決定 32～39）後使用者可觀察之行為：自己存檔後立即再存、對話框開而未編輯時收到他人變更而重建、儲存格編輯器開啟中視為草稿、反向對話框主體被取代而拒存、他人只重排被偵測、舊格式基準被拒、前端基準與伺服端同構；他人改列、增列、刪列之先動先贏與橫幅、提示本身之畫面見姊妹文件 `流程_外部列保護與過期快照.md`。

名詞：**他人**＝另一位管理員（e2e 以管理者寫入 RPC 模擬）或外部來源（e2e 以外部同步端點 `/syncAndReplaceTabs` 模擬）；**推播**＝伺服端表異動後客戶端重抓整表並以新陣列取代 store 該表（約 2 秒輪詢，見 `src/js/draftSync.mjs` 檔頭註解）；**基準**＝編輯草稿所依據之整表之有序摘要 `[[id, 'h1:…'], …]`，隨存檔請求送出，伺服端於表鎖內與庫內整表比對；**名次**＝列依（`order` 數值，主鍵碼元序）排序之次序；**主體**＝反向對話框所編輯其歸屬之群組（`VeGrupBlngUsers`）或權限（`VePemiBlngGrups`）。

版面分區：清單頁為標題區、功能區工具列（`data-fmid="<表>-toolbar"`）、橫幅區（外部列提示、同步警示、資料已被更新；`data-fmid="<表>-banner-stale"` 等，無內容時不渲染任何節點）、表格；進入後預設狀態為編輯模式開、無列被勾選、無儲存鈕（儲存鈕只在編輯模式且有未存變更時渲染）。反向對話框為標題列（儲存鈕只在可編輯且有變更時渲染，關閉鈕恆渲染）、工具列、過期提示區（`grup-blng-users-banner-stale`／`pemi-blng-grups-banner-stale`，無提示時不渲染任何節點）、表格（名稱、「是否使用」核選方塊、關聯 chip 三欄）；對話框列內無可編輯儲存格（`kpCellEditable` 皆為 false，「是否使用」為即時提交之核選方塊）。

案例檔為 `test/e2e-concurrent-edit.test.mjs`：24 案 × eng／cht ＝ 48 個 `it`，全為語意案例，無標準圖、無 `--baseline` 模式。

## 重要流程

- **E2E-001**
  - title: 使用者頁存檔成功後立即再存仍成功
  - description: 管理員從左側選單點選「管理使用者」進入使用者清單頁，雙擊某位使用者的「說明」欄輸入新內容，點擊「儲存變更」，出現「儲存使用者數據成功」，點擊「確認」關閉訊息；說明此時已寫入資料庫，清單顯示剛儲存的內容，儲存鈕消失，清單上方沒有「資料已被他人或外部同步更新」橫幅。管理員不必等系統約 2 秒一次的資料更新，可立刻再雙擊同一位使用者的「說明」欄輸入第二次內容並再次儲存，同樣出現「儲存使用者數據成功」，不會被自己上一次的存檔擋下。若第二次儲存跳出「儲存使用者數據失敗」接「未儲存：載入此頁面後資料已被他人或外部同步更新。資料未變更，請重新整理頁面後再操作。」，表示確有他人改過資料，請重新整理頁面後再編輯。便於連續修改同一筆資料。
  - flow:
    - 測試資料：base seed（B-U2 mary，`id-for-mary`）；第一次說明 `CE-a1-users`，第二次說明 `CE-a2-users`。登入身分為管理員 token `sys`。
    - 操作：登入後台 → 點「管理使用者」頁籤，等 store 載入 4 筆 →（測試端開始攔住網路推播，見〈規則摘要〉手段說明）→ 雙擊 mary 之說明儲存格輸入第一次說明（Enter）→ 點「儲存變更」→ 結果訊息框點「確認」→（推播仍被攔住）立即再雙擊 mary 之說明儲存格輸入第二次說明（Enter）→ 點「儲存變更」→ 結果訊息框點「確認」→（測試端放行被攔住之推播）→ 觀察 1.5 秒。
    - 驗證：
      1. 語意：第一次存檔出現 `userSaveUsersSuccess`（文字見〈訊息對照〉）；點「確認」後 store 內 mary 之說明已等於第一次說明（網路推播仍被攔住，更新來自存檔回傳之寫入後之列）、儲存鈕消失、`users-banner-stale` 為 0 節點。
      2. 語意：立即再存之第二次存檔出現 `userSaveUsersSuccess`，不出現失敗框（不被自己上一次之存檔誤擋為 `saveStale`）。
      3. 語意：放行被攔住之推播並觀察 1.5 秒後，`users-banner-stale` 仍為 0 節點、儲存鈕不出現（其後抵達之同內容推播不視為他人更新）。
      4. 語意：庫內 mary 之說明等於第二次說明。
      5. 視覺：無標準圖（純語意案例，理由見〈規則摘要〉標準圖通則）。
    - 雙語：eng / cht 各一輪（成功訊息文字語系不同）。
    - 清理：案例結束以 `createIsolation().restore()` 還原——先以 `purgeExternalRows` 刪外部列夾具（本案無），再經管理者寫入 RPC 把 users、grups、pemis 整表寫回案前快照；回驗三表筆數等於快照且無外部列殘留。mary 之說明由整表寫回復原。
    - 備註：存檔 RPC 帶 `{ baseline, returnRows:true }`，成功回 `{ msg, rows, others }`（`server/procCore.mjs:updateTabItems` 之 `readAfter`）；`LayoutContentUsers.vue:saveUsers` 於 `isModified=false` 與 `syncMark.dirty=false` 之後呼叫 `applySavedRows`（`src/js/applySaved.mjs`）以 `source:'savedRows'` commit，清單頁依既有 `changeParams` 流程以之重建畫面與基準。測試端攔網路推播時放行此 commit，故驗得到「不待推播」。操作者點「確認」後才再編輯，是真實使用者之最快路徑。與 E2E-002～004 為四清單頁之對稱案例（`PAGES` 組態），與 E2E-005／006 為對話框之對稱路徑。

## 規則摘要

- **權限**：本檔案例皆為管理員（token `sys`）之畫面軸行為；單一帳號，無負向權限案例。寫入經 `verifyConn` 守門；他人之變更以管理者寫入 RPC（`TOKEN_ADMIN`）與外部同步端點（`TOKEN_APP`）模擬。
- **事實來源與未實測範圍**：本檔事實只來自現行程式碼（`server/procCore.mjs`、`server/procLang.mjs`、`src/js/{draftSync,applySaved,cellEditing,rowDigest}.mjs`、`src/schema/contracts/`、六個 `.vue` 元件、`node_modules/w-serv-orm/src/baseline.mjs`）與 `test/e2e-concurrent-edit.test.mjs`、`test/tools/{e2e-setup,e2eExt,api-setup}.mjs`；撰寫本檔時未啟動服務、未實機探測、未重跑 e2e，無探測 log。含時間之敘述（約 2 秒輪詢、1.5 秒／1.2 秒／0.8 秒觀察窗）取自程式碼註解與案例檔，非本輪實測；筆數與列次隨種子變動。〔2026-10-23 補記: 撰寫後已實跑 `test/e2e-concurrent-edit.test.mjs` 比對模式，24 案 × 2 語系 48／48 通過（與 `api-baseline` 同行程 60 過 0 敗），且 E2E-012（targets）於兩語系各重複 6 次共 12／12 通過〔修正 targets 表收尾還原前為 1／12，根因見下〕; 上列時間仍未逐項實測。〕
- **載入基準與先動先贏（背景）**：基準為草稿所依據之整表（`makeBaseline(rows, 表名)`，核心 `buildBaseline`），於建立草稿時綁定、不於存檔當下由最新 store 計算；伺服端於表鎖內（`guardWrite`）以新鮮讀取之庫內整表比對，列內容、列增刪、名次任一不同即整次拒收 `saveStale`、零寫入、不部分變更。他人改列、增列、刪列之案例與橫幅畫面屬姊妹文件。
- **名次入基準**（E2E-017～019）：基準為依（`order` 數值，主鍵碼元序）排序之 `[[id, 'h1:…'], …]`，序即名次；他人只重排（共有列相對次序改變）→ 核心 `reordered=true`，伺服端 reason `rowReordered`，存檔被拒；`order` 欄本身不入摘要（`orderKey` 不在 `fields`），故存檔重編號、外部同步平移其外部列 `order` 而名次不變者不算變更。
- **空值等價**（無 e2e，見〈已知落差〉）：欄位頂層之 `undefined`、`null`、缺欄、`''` 為同一空值（核心 `canonField`）；`0`、`false`、`'0'` 不是空值；數字與字串不互轉；巢狀值之 `null` 與 `''` 不等價。摘要欄位依寫入契約 `fields` 白名單；`serverOnly`（`userId`、`timeCreate`、`userIdUpdate`、`timeUpdate`）不入摘要、存檔不採客戶端值。
- **回傳寫入後之列**（E2E-001～006）：客戶端第二參帶 `{ baseline, returnRows:true }`，伺服端於同一表鎖內寫入後新鮮讀回該表全部列（有改寫引用端表時另帶 `others`），成功回 `{ msg:'saveTabItemsSuccess', rows, others }`；未帶 `returnRows` 回字串（既有呼叫端不變）。前端 `applySavedRows` 僅在回傳形狀、表名白名單、每列主鍵皆合法時 commit（`UpdateTableData`，payload 帶 `source:'savedRows'`），否則退回等推播。不以自己送出之值當新基準（寫入時 `clearXSS` 會改寫字串）。其後同內容推播摘要相同，不視為他人更新。
- **編輯器草稿**（E2E-009～013）：`hasDraft ＝ 已提交修改 || 儲存格編輯器開啟中`（ag-grid `getEditingCells()` 非空）；編輯器開啟中收到推播 → 保留、凍結基準、顯示橫幅（編輯器內已輸入未提交之文字不進 rows，儲存鈕此時不出現）；編輯結束且無已提交修改而 store 已變新 → 補重建。反向對話框無可編輯儲存格，此項只涵蓋四清單頁。
- **對話框開而未編輯**（E2E-007、008）：`planDialogSync`——無未存修改且表異於開框基準 → 重建對話框內容與基準；有未存修改 → 保留並提示；自己存檔中所致之推播 → 靜默（`ownSaving`）。
- **主體身分驗證在前端**（E2E-014～016）：反向對話框以名稱引用主體；開框時記 `subject={id,name,saved}`，存檔流程開頭與 `delay(300)` 後各以 `checkSubject` 比對存檔當下主體表（`ok`／`renamed`／`gone`／`taken`／`noSubject`），非 `ok` 一律整次拒存、零寫入、對話框保持開啟；開框中 `syncStore` 以同函數顯示同一提示且不重建。伺服端不知主體（見〈已知落差〉待裁示）。
- **舊格式基準**（E2E-020）：基準非陣列、含非 `h1:` 加 14 位小寫十六進位之摘要、或 id 重複 → `saveBaselineFormat`，於取鎖與任何讀寫之前拒收，不降級為不帶基準；缺或 `null` 之基準沿用既有政策。
- **前端與伺服端同構**（E2E-021～024）：前端 `rowDigest.makeBaseline` 與伺服端 `buildBaseline` 取同一份核心與同一份契約；e2e 不 import `src`／`server`，以黑箱比對（基準 id 序＝伺服端依（order，id）排序之 id 序、摘要格式、送出列數、伺服端接受存檔）。
- **手段說明（setup，非使用者動作）**：「他人」＝管理者寫入 RPC（`editTableRows`：讀現況整表 → 改 → 整表寫入，依陣列位置重給 order）或外部同步端點（`syncRows`：app token、以 `from` 為界全量取代）；「推播尚未抵達」＝包裝 `$vo.$store.commit`，攔下帶 `tableName` 與陣列 `data` 之 payload、放行 `payload.source==='savedRows'` 之 commit（頁面套用自己存檔回傳列），放行時依序補 commit，用以固定「存檔成功後約 2 秒輪詢尚未送達」之窗口（E2E-001～006）；包裝 `$fapi.updateXxx` 以擷取送出之基準（E2E-021～024）或改寫為舊版形狀（E2E-020）。皆不改變使用者可見之畫面。
- **輸入空間（頁面／對話框 × 能力）**：頁面軸 4（users、grups、pemis、targets）× 7 項能力（存檔後立即再存、編輯器開啟中視為草稿、Esc 補重建、他人只重排、外部列 order 平移、舊格式基準、同構）＝ 28 格；已設 e2e 17 格（立即再存 4、編輯器草稿 4、Esc 補重建 1、只重排 2、order 平移 1、舊格式 1、同構 4）、未設 11 格（見〈已知落差〉）。對話框軸 2（`VeGrupBlngUsers`、`VePemiBlngGrups`）× 4 項能力（存檔後重開再存、開而未編輯時重建、主體被取代且已編輯、主體被取代且未編輯）＝ 8 格；已設 e2e 7 格、未設 1 格。語系軸 2（eng、cht）每案各一輪。合計案例 24 ＝ 17 ＋ 7；`it` 48 ＝ 24 × 2。另有不入上列之能力：空值等價（無 e2e）。
- **標準圖通則**：本檔 24 案皆為純語意案例，不設標準圖——所驗為資料與狀態是否正確（存檔後基準、草稿保留、拒存、基準格式），所用橫幅、提示、結果框與對話框皆為既有元件之既有畫面（橫幅與對話框提示之標準圖屬姊妹文件範圍）；案例檔以 `stages: []` 宣告（allowEmpty），無 `--baseline` 模式（直跑 `--baseline` 只印提示並 `cleanup()`）。
- **清理與隔離**：每案 `afterCase` 呼叫 `createIsolation().restore()`——`purgeExternalRows` 刪外部列夾具後，經管理者寫入 RPC 把 users、grups、pemis 整表寫回案前快照，並回驗三表筆數與無外部列殘留；檔首 `capture()` 以 `assertPristineSeed` 守三表主鍵集合。**targets 表不在共用還原範圍**（`TABLE_FN` 僅三表），故本檔自行補上：`capture()` 另擷取 targets 之 base seed 22 列（斷言筆數與 `from` 皆空），`restore()` 於三表還原後經管理者寫入 RPC 把 targets 整表寫回，並逐列回驗說明與筆數。修正前（2026-10-23 重複量測）E2E-012 之 targets 輪於同案第二輪起 11／12 失敗：他人寫入之說明與庫內相同 → 無變更、不產生推播 → 橫幅永不出現，根因為測試隔離缺口，非產品行為；`assertPristineSeed` 只比主鍵集合、不比欄位內容（`test/tools/baseSeed.mjs` 檔頭自述），故此類殘留不會被共用守門攔下，凡會改 targets 說明之新測試檔須自備還原。
- **測試環境呈現**：無（本檔畫面皆為正式環境同一畫面）。

## 已知落差

- **設計事實（記錄備查）** 2026-10-23：反向對話框無可編輯儲存格，儲存格編輯器草稿只涵蓋四清單頁——`VeGrupBlngUsers.vue`／`VePemiBlngGrups.vue` 之 `genOpt` 為 `defCellEditable:false`，`kpCellEditable` 之 `name`、`enable` 皆為 `false`（「是否使用」為即時提交之核選方塊）；`syncStore` 雖已把 `isCellEditing` 接入 `planDialogSync`，現況其值恆為假，日後對話框加入可編輯儲存格時自動適用。使用者可觀察之後果：對話框內沒有「輸入到一半」之狀態可能遺失。故 E2E-009～013 只設四清單頁；對話框之 `editing` 分支由 `unit-draftSync` DS-5／DS-6 與 `unit-cellEditing` 涵蓋。層級：本專案產品程式碼（ADR-037 決定 38、README Upgrade Notes）。
