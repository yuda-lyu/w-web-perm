# 設計要點與取捨

本檔記錄 w-web-perm 專案之跨流程 (cross-cutting) 設計決策.
每條 ADR 一段, 含: Status / Context / Decision / Consequences / Affected.

修改決策時新增 ADR (編號遞增) 並把舊條 Status 改為 Superseded, **不刪舊條**
保留決策歷史, 方便日後 audit 追溯為什麼當初這樣選.

> 本專案核心為「權限樹解析」: 四層資料 (使用者 `cgrups` → 群組 `cpemis` → 權限 `crules` → 目標 `targets`) 逐層展開, 經 OR/AND 兩階段合併算出某使用者對每個 target 的最終 `'y'`/`'n'`. 解析主體為純函式 `getUserRules` (`src/plugins/mShare.mjs`, 前後端共用), 由後端 `getGenUserAndRulesByUserId` (`server/WWebPerm.mjs:779`) 與外部介接 API 共同消費. 以下 ADR 多圍繞此解析鏈與其周邊寫入 / 同步 / 測試守護之橫切契約.

## ADR-001: 權限合併語意 — OR 聯集 / AND 非對稱交集 / OR 先 AND 後

**Status**: Accepted (2026-06-09)

**Context**:
- 同一使用者可同時納入多個群組、每個群組可納入多個權限, 每個權限對同一 target 可能給出不同的 `'y'`/`'n'`. 須訂出明確且唯一的合併語意, 否則「使用者最終對某 target 有沒有權限」無法被確定性判定.
- 合併同時發生於兩個層級 (群組內合併各權限、群組間合併各群組結果), 兩層若採不同語意會讓權限樹難以推理.
- 不解決會踩到: 權限判定不確定、同一筆資料在不同 caller 算出不同結果、無法寫可斷言的 unit 測試.

**Decision**:
- **OR 聯集 (`objOR`)**: 對同一 key, 任一物件為 `'y'` 即 `'y'`; 皆 `'n'` (或缺) 才 `'n'`; 兩物件的 key 取聯集 (`mShare.mjs:308-325`).
- **AND 交集 (`objAND`)**: 以第一物件 (obj1) `cloneDeep` 為基底, 遍歷 obj2 — 只在 obj1 該 key 為 `'y'` 且 obj2 該 key 為 `'y'` 時保留 `'y'`, 否則 `'n'` (`mShare.mjs:327-344`).
- **AND 非對稱性 (load-bearing)**: obj1 獨有的 key (obj2 不遍歷到) 保留 obj1 原值; obj2 獨有 (基底未涵蓋) 的 key 先補 `'n'` 再判定, 等同**強制 `'n'`** (`mShare.mjs:331-340`). AND 交換 obj1/obj2 順序結果可能不同, 此非對稱性是刻意行為, 非 bug.
- **OR 先 AND 後 (固定順序)**: `mergeRules` 先取所有 OR 項聯集出 `kpRuleFin`, 再以所有 AND 項逐一交集收緊 (`mShare.mjs:346-375`). 故 AND 只能把 OR 得到的 `'y'` **收緊**為 `'n'`, 無法把 OR 得到的 `'n'` **反轉**為 `'y'`.
- **初值選取**: 有 OR 項時 `kpRuleFin` 起始於第一筆 OR 的 `kpRule`; 無 OR 但有 AND 時起始於第一筆 AND 的 `kpRule` (`mShare.mjs:351-358`).
- **同一函式套兩層**: 群組內 (合併各權限) 與群組間 (合併各群組結果) 皆呼叫同一 `mergeRules`, 兩層語意一致.

**Consequences**:
- ✅ 權限判定確定性: 同一筆四層資料永遠算出同一棵權限樹, 可逐 case 以回傳值斷言.
- ✅ 兩層共用同一合併語意, 權限樹易於推理, 不出現「群組內一套、群組間另一套」的不一致.
- ✅ 「OR 先 AND 後」使 AND 的收緊意圖明確 (AND 是限制器, 不是放寬器).
- ⚠️ AND 非對稱性違反一般人對「交集應對稱」的直覺: 對調 AND 兩項可能改變結果 (obj2 獨有 key 被強制 `'n'`). 設計取捨已由 E2E-005 (`流程_權限規則合併計算.md`) + unit 測試 (`unit-getUserRules.test.mjs:284-317`) 凍結為契約, 後續不可「順手對稱化」.
- ⚠️ `mode` 非 `'OR'` / `'AND'` 的項目於 `mergeRules` 內被靜默跳過 (`mShare.mjs:284-285`), 不計入合併; 拼字錯誤的 mode 等於該項不存在.

**Affected**:
- src/plugins/mShare.mjs:280-389 (mergeRules / objOR / objAND)
- test/unit-getUserRules.test.mjs:256-451, 736-877 (OR/AND/混合/兩層巢狀)
- spec/流程_權限規則合併計算.md (合併語意規則表 / E2E-001~006)

## ADR-002: 未授權即拒絕 — 未涵蓋的 target 一律補 `'n'`

**Status**: Accepted (2026-06-09)

**Context**:
- 權限只明確記載「對哪些 target 授 `'y'` / `'n'`」, 但 `targets` 全集通常遠大於任一使用者實際被提及的範圍 (稀疏授權).
- 對「從未被任何生效規則提及」的 target, 預設應為授權還是拒絕? 安全系統的預設必須是拒絕 (fail-closed).
- 不解決會踩到: 預設放寬 = 新增 target 後使用者自動取得權限的安全破口.

**Decision**:
- 合併結果填入 `kp` 後, 以**當前 `targets` 全集**逐項輸出, 每個 target 取其解析後 `isActive`, 取不到者 `get(kp, t.id, 'n')` 補為 `'n'` (`mShare.mjs:485-503`, 詳見 ADR-003 之輸出主軸).
- 回傳 `rules` 必涵蓋 `targets` 中每一個節點 (不漏項), 使消費端可對任一 target 直接查表.
- 整批被過濾為空 (見 ADR-004) 或 `cgrups` 為空時, `mergeRules` 回傳空陣列, 最終仍由 targets 補齊全 `'n'`, 不拋錯 (`mShare.mjs:304-305`).

**Consequences**:
- ✅ fail-closed: 未明確授權即拒絕, 新增 target 不會讓既有使用者自動取得權限.
- ✅ 回傳 rules 涵蓋 targets 全集, 消費端查表不需處理「查無此 target」分支.
- ⚠️ `targets` 為空陣列時回傳空 rules (`unit-getUserRules.test.mjs:101-111`); 消費端須容忍空 rules.

**Affected**:
- src/plugins/mShare.mjs:485-503 (expand 段補 'n')
- test/unit-getUserRules.test.mjs:119-149, 707-732 (target 展開 / 稀疏權限)
- spec/流程_權限規則合併計算.md (E2E-002 / spec 規則摘要「預設」)

## ADR-003: 權限樹以「當前 targets」為輸出主軸, 剔除孤兒 target

**Status**: Accepted (2026-06-09, commit 51bd712)

**Context**:
- 管理員刪除某 target 後, 引用該 target 的 `pemis.crules` 字串仍可能殘留對它的 `'y'`/`'n'` 引用 (crules 與 targets 為各自獨立維護的兩張表, 刪 target 不會回頭清掃所有 crules).
- 修正前 `getUserRules` 的 expand 段把最新 `targets` 只拿來「補缺」(`if (!haskey(kp, t.id)) kp[t.id]='n'`) 而**未拿來過濾**, 輸出集合 = `crules keys ∪ targets`. 結果: 已刪除的 target 因 crules 殘留引用而仍出現在解析後權限樹, `getPermUserInfor` 會回傳已刪除管控對象的授權 — **外部應用查到不該有的權限** (真實 bug, 非推測).
- 不解決會踩到: 刪 target 不生效於外部介接查詢, 權限樹與「現存管控對象」不一致.

**Decision**:
- expand 段改以「當前 `targets`」逐項為**輸出主軸**: 每個 target 取其解析後 `isActive` (取自合併 crules 的 `kp`、預設 `'n'`), `crules` 仍引用但已從 `targets` 刪除的孤兒 key 自然被濾掉 (`mShare.mjs:485-503`).
- 修正前: 輸出 = `crules keys ∪ targets`; 修正後: 輸出 = `targets` (孤兒被剔除). no-orphan 情境 (`crules ⊆ targets`) 輸出集合不變, 無退化.
- 此修正同時滿足 ADR-002「未涵蓋補 `'n'`」: 主軸換成 targets 後, 補預設與剔孤兒由同一段邏輯一次完成.

**Consequences**:
- ✅ 解析後權限樹 = 現存 targets, 刪 target 立即反映於外部介接查詢, 不再殘留孤兒授權.
- ✅ rules 筆數恆等於現存 targets 數, 成為可斷言的不變式 (E2E-005 永久回歸守護).
- ✅ no-orphan 情境輸出不變, 對既有資料無退化.
- ⚠️ 此為「以 targets 為權威主軸」的單向契約: 若未來需求要保留「crules 有引用但 targets 沒有」之孤兒於樹中 (反向), 須重新設計 — 但此需求與 fail-closed 精神相悖, 預設不支援.

**Affected**:
- src/plugins/mShare.mjs:485-503 (expand 段, commit 51bd712 改寫)
- test/e2e-targets.test.mjs (E2E-005-delete-ok 孤兒不變式語意斷言)
- spec/流程_權限規則合併計算.md (執行流程 025-027)
- spec/流程_查詢指定使用者權限.md (外部查詢消費此樹)

## ADR-004: `isActive='n'` 的群組 / 權限於合併前即被過濾

**Status**: Accepted (2026-06-09)

**Context**:
- 群組與權限皆有 `isActive` 旗標, 用於「暫時停用而不刪除」. 停用者是否應參與 OR/AND 合併?
- 若停用者仍進入合併, 一個被停用的 OR 權限仍可貢獻 `'y'`, 停用形同無效.
- 不解決會踩到: 停用旗標失去意義、管理員以為停用了卻仍生效.

**Decision**:
- **群組層級**: 使用者關聯中 `isActive='n'` 的群組整組被 `filter` 移除, 不參與後續任何展開與合併 (`mShare.mjs:404`).
- **權限層級**: 群組 `cpemis` 中 `isActive='n'` 的權限被 `filter` 移除, 不納入該群組的合併 (`mShare.mjs:411`).
- 過濾在「分離 OR/AND 之前」執行, 故被停用者完全不出現於 `ts`; 若整批被過濾為空, 由 ADR-002 補齊全 `'n'`、不拋錯.
- 回傳 `grups` 僅含 active 且名稱可對應的群組 (`mShare.mjs:506-509`), 後端據此組 `grupsNames` (`WWebPerm.mjs:809-810` 註「僅會提供 isActive='y'」).

**Consequences**:
- ✅ 停用旗標語意明確: 停用 = 完全不參與計算, 等同暫時移除.
- ✅ 過濾發生於合併前, 不會出現「停用權限仍貢獻 OR `'y'`」的洩漏.
- ✅ `grupsNames` 天然只含有效群組, 消費端不需再過濾.
- ⚠️ `isActive` 與 ADR-001 的 `mode` 篩選 (跳過非 OR/AND) 為兩道獨立過濾; 兩者皆通過才參與合併.

**Affected**:
- src/plugins/mShare.mjs:404, 411, 506-509
- server/WWebPerm.mjs:809-810 (grupsNames 取 active 群組)
- test/unit-getUserRules.test.mjs:457-521, 603-617
- spec/流程_權限規則合併計算.md (isActive 過濾規則表)

## ADR-005: 名稱比對找不到即靜默忽略 + JSON5 容錯解析 + 空字串降級

**Status**: Accepted (2026-06-09)

**Context**:
- `cgrups` / `cpemis` / `crules` 皆以字串儲存, 經 JSON5 解析後以 `name` 跨表比對. 解析或比對可能因外部資料品質失敗 (引用了不存在的群組/權限名、字串格式寬鬆、欄位為空).
- `getUserRules` 是計算權限樹的核心純函式, 任一輸入瑕疵若直接拋錯, 會讓整個使用者的權限查詢 (含外部介接) 失敗.
- 不解決會踩到: 單筆髒資料 (例如一個已刪群組仍被引用) 導致整個權限查詢 500、所有 target 取不到判定.

**Decision**:
- **名稱比對容錯**: `arrFinder` 以 `name` 將 `cgrups` 項對 `grups` 表、`cpemis` 項對 `pemis` 表逐一比對, 找不到對應者**靜默忽略**而非拋錯 (`mShare.mjs:400, 412`); 同一容器內可對應的項目仍正常生效 (部分匹配).
- **JSON5 解析**: `cvStrToArr` 以 `JSON5.parse` 解析, 允許單引號等寬鬆語法; 解析失敗時 `console.log` 後**降級為空容器**、不向外拋錯 (`mShare.mjs:232-239`).
- **空字串 / 空容器**: `cgrups` 為空字串時解析得空容器, 後續 filter / merge 皆空, 最終靠 ADR-002 補齊全 `'n'` (`mShare.mjs:392, 488-493`).
- 此「容錯不拋錯」是 ADR-006 fail-safe 在純函式層的基礎.

**Consequences**:
- ✅ 單筆髒資料不會讓整個權限查詢失敗; 壞的部分被略過, 好的部分照常生效.
- ✅ 字串欄位允許 JSON5 寬鬆語法, 對人工編輯/外部來源較友善.
- ✅ 空輸入韌性: 空字串/空表降級為空容器, 不拋錯.
- ⚠️ 靜默忽略無使用者可見回饋: 管理員若把群組名打錯, 該群組默默不生效而無錯誤提示 — 須靠後端 `console.log` 或 e2e 守護察覺.
- ⚠️ 「找不到即忽略」使「引用了不存在的名稱」與「正確但無授權」對最終樹的效果相同 (皆 `'n'`), debug 時須查 log 區分.

**Affected**:
- src/plugins/mShare.mjs:232-239 (cvStrToArr JSON5), :256-272 (arrFinder), :392, :400, :412
- test/unit-getUserRules.test.mjs:527-560 (名稱匹配失敗), :883-897 (JSON5 格式), :91-99 (空字串)
- spec/流程_權限規則合併計算.md (名稱匹配與容錯規則表)

## ADR-006: 查詢指定使用者權限 — 查找對象不存在回「全停用空權限」(fail-safe, 非 reject)

**Status**: Accepted (2026-06-09)

**Context**:
- 外部 node 應用以 app token 經 `GET /api/getPermUserInfor` 查詢「某一指定 `userId`」的權限. 查找對象 (`userIdTar`) 可能不存在於 perm `users` 表 (例如該 user 已被刪、或外部應用持有的是舊 userId).
- 查找對象不存在時, 後端應 reject 還是回空權限? reject 會讓外部應用須處理錯誤分支; 回空權限則統一走成功路徑.
- 不解決會踩到: 外部應用對「user 不存在」與「user 存在但無權限」須寫兩套處理、權限查詢的錯誤面變大.

**Decision**:
- `getGenUserByUserId` 取不到使用者時 (回 `null`), `getUserRules` **容忍**此情形 (`null` user 之 `cgrups` 經 ADR-005 容錯降級為空容器), 回傳「全停用」之空權限物件 — `user` 無有效 `id`、`rules` 各規則 `isActive='n'` (fail-safe).
- 故 handler 回 `state='success'`、`msg` 為含 `user`/`rules` 的物件 (`WWebPerm.mjs:1030, 812`), **非 reject** (見 `流程_查詢指定使用者權限.md` E2E-005).
- 對比: 發起者身分驗證 (app token) 失敗仍 reject 走 `state='error'` (見 ADR-007) — 「查找對象不存在」與「發起者無權限」分屬兩種路徑, 前者 fail-safe、後者守門拒絕.
- 發起者驗證**不反查 perm `users` 表**, 僅以部署方注入的 `getUserByToken` 取使用者再過 `verifyAppUser` (`WWebPerm.mjs:620, 635`), 故可支援應用程式專屬之虛擬使用者帳號.

**Consequences**:
- ✅ 外部應用對「user 不存在」與「user 無權限」統一走成功路徑取空權限樹, 處理邏輯一致.
- ✅ fail-safe 預設全停用, 對齊 ADR-002 fail-closed 精神 — 查不到 = 沒有任何權限, 不會誤放行.
- ✅ 建立於 ADR-005 純函式容錯之上, 後端不需為「user 不存在」寫額外分支.
- ⚠️ 外部應用無法單從 `state` 區分「user 不存在」與「user 存在但全 `'n'`」, 須檢視 `user.id` 是否有效 — 屬已知取捨.

**Affected**:
- server/WWebPerm.mjs:782, 798, 1030 (getGenUserByUserId / getUserRules / handler)
- src/getPermUserInfor.mjs (客戶端依 state==='success' 判定, resolve 物件)
- spec/流程_查詢指定使用者權限.md (E2E-005 / spec 規則摘要「查找對象」)

## ADR-007: 外部介接守門 — app token 經 `getAndVerifyAppUser`, 不經 verifyConn / Bearer

**Status**: Accepted (2026-06-09)

**Context**:
- `/api/getPermUserInfor` (查詢) 與 `/syncAndReplaceTabs` (同步寫入) 為直接 `server.route` 註冊的自訂端點, 供外部 node 應用以 query `token` 介接, 不走瀏覽器使用者通道.
- ORM exec 通道由 `verifyConn` 守門; 但這兩個自訂端點不經該通道, 須自帶守門, 否則任何人皆可查/改權限資料.
- 不解決會踩到: 自訂端點裸奔、外部任意 caller 可查任一 userId 權限或覆寫整表.

**Decision**:
- 兩端點守門皆由 handler 內 `getAndVerifyAppUser(token, from)` 負責 (`WWebPerm.mjs:614`): 以 `getUserByToken(token)` 取使用者 → 以部署方注入的 `verifyAppUser(user, from)` 判定為合法 app 使用者; 任一步失敗即 `Promise.reject` 走 `state='error'`.
- `verifyAppUser` 為部署方注入 `WWebPerm` 建構參數的唯一守門判定函式 (`WWebPerm.mjs:138, 635`); 信任邊界集中於此一函式.
- token 缺 / 無效 / 取不到使用者 / `verifyAppUser` 回 false 一律 reject, 回傳 `{ state:'error', msg }` (英文字串如 `token does not have permission` / `user does not have permission`), **非 i18n** (`procLang.mjs` 無對應鍵, 由呼叫端應用自行呈現).
- handler 統一以 `pm2resolve(core)` 把 core 的 resolve/reject 轉為 `{ state, msg }` (`WWebPerm.mjs:1045, 1128`).

**Consequences**:
- ✅ 自訂介接端點守門集中於 `getAndVerifyAppUser` 單一入口, 兩端點共用, 易 audit.
- ✅ 守門判定 (`verifyAppUser`) 由部署方注入, perm 本身不綁定身分系統, 介接彈性高.
- ✅ 回傳為機器可讀 `{ state, msg }`, 與瀏覽器 i18n 通道解耦.
- ⚠️ app token 等同高敏資料: 外洩即可查/改權限資料, 須限制傳遞通路.
- ⚠️ `verifyAppUser` 為部署方責任; 若注入的實作把關不嚴, 守門隨之鬆動 — perm 無法替部署方補強.

**Affected**:
- server/WWebPerm.mjs:138, 614-647 (getAndVerifyAppUser / verifyAppUser 注入)
- server/WWebPerm.mjs:985-1051 (getPermUserInfor handler), :1057-1134 (syncAndReplaceTabs handler)

## ADR-008: 外部同步採「依 `from` 全量取代」+ 空 rows 被拒 (防誤清源)

**Status**: Accepted (2026-06-09)

**Context**:
- `/syncAndReplaceTabs` 讓外部應用把本地維護的某張表 (`targets`/`pemis`/`grups`/`users` 四選一) 整批推送至伺服器, 由伺服器覆寫該應用在該表的資料. 多個外部應用各自推送, 須彼此隔離不互相覆蓋.
- 取代模型有兩種: 逐列 diff (與後台瀏覽器寫入相同, 見 ADR-009) 或依來源全量取代. 同步場景下「外部應用本地即真理」, 全量取代語意更直觀.
- 若全量取代允許空 rows, 外部應用一旦誤送 `rows=[]` 會把該來源整批清空 (資料災難).
- 不解決會踩到: 跨應用資料互相覆蓋、外部誤送空集合清空權限源.

**Decision**:
- **全量取代**: `syncAndReplaceTabs` 以 payload 的 `from` 為範圍鍵, 先 `delAll({ from })` 刪該應用既有列, 再整批 `procOrm insert` (`WWebPerm.mjs:736, 740`); **非逐列 diff** (無 `ltdtDiffByKey`、無 `ckKey` 去重). 各應用以各自 `from` 隔離.
- **空 rows 被拒**: `parsePayload` 以 `isearr` 要求 rows 為**非空**陣列 (`WWebPerm.mjs:683`); `rows=[]` 即 reject `invalid rows in payload`, **未進 delAll**, 故該 `from` 既有列不被清空. **不支援「以空集合清源」** — 此為防外部應用誤送空陣列而整批清空資料之安全閘.
- **白名單守門**: query `keyTable` 須屬 `[targets, pemis, grups, users]` 四者之一, 否則 reject (`WWebPerm.mjs:1089-1092`).
- **欄位邊界**: 端側 `provideTabs` 以白名單 `ltdtpick` 過濾欄位 (`provideTabs.mjs:8-63, 83`); 稽核欄位 (`userId` / `time*`) 一律由後端 `procOrm` 補, 不由 payload 帶入; `order` 在此路徑沿用外部帶入值, 不重給 (`WWebPerm.mjs:726` 註).

**Consequences**:
- ✅ 跨應用以 `from` 隔離, 各應用全量推送互不覆蓋.
- ✅ 空 rows 安全閘防止外部誤送清空權限源 — 清源須有意為之 (推非空集合或走後台), 不會手滑釀災.
- ✅ 四表共用同一全量取代路徑, 差異僅 `ds[keyTable].keys` (schema), 維護單一邏輯.
- ⚠️ 因此**不支援以同步 API 清空某 `from` 的所有列**; 真要清空須走其他路徑. 屬刻意限制.
- ⚠️ 註: `流程_外部應用同步權限資料.md`「欄位邊界」表曾有一行誤記「允許空陣列」, 與實際 `isearr` 行為 (拒絕) 相悖; 以本 ADR 與該文件 E2E-002 / spec 規則摘要為準 (rows 須非空).

**Affected**:
- server/WWebPerm.mjs:652-696 (parsePayload, isearr 非空檢查 :683), :700-744 (syncAndReplaceTabs 全量取代), :1089-1092 (keyTable 白名單)
- server/provideTabs.mjs:8-63, 66-90 (端側欄位白名單)
- spec/流程_外部應用同步權限資料.md (E2E-001~006 / spec 規則摘要)

**Update (2026-10-14): 防誤清源補「寫入前列驗證」(ADR-026)**

- 先 `delAll({ from })` 再 insert 之全量取代, 於 w-serv-orm 1.1.8 起遇「會被 XSS 清除改寫之主鍵」整批拒絕、LMDB 遇 UTF-8 超過 1978 位元組之主鍵整批拒絕時, 拒絕發生在 delAll 之後——該 `from` 之既有列全數清空(2026-10-14 真 WServOrm＋真 lmdb 與 HTTP 實打實測, 主控交付 `run01-審計回應.md` V4／V7). 本 ADR 之「防誤清源」原只擋空 rows, 不足以涵蓋.
- 處置: `syncAndReplaceTabs` 於 delAll 之前以 `validateRowsBeforeWrite` 驗全部列(主鍵非字串／過長／重複 → `invalidRows`; 任一字串欄位含標記 → `htmlMarkupNotAllowed`), 違規即拒、該 from 既有列不變; ORM／I/O 失敗之原文只入 srLog, 外部應用收 `saveWriteFail`. 測試: `api-syncAndReplaceTabs` API-sync-007～009.

## ADR-009: 後台寫入採「整表批次 diff」(ltdtDiffByKey), 重給 order

**Status**: Accepted (2026-06-09)

**Context**:
- 後台四份清單 (Users / Grups / Pemis / Targets) 的編輯為「載入整表 → 在前端表格增刪改 → 整批存回」. 存回時須把前端整表與 DB 既有列對齊, 算出哪些列要刪/增/改.
- 若每列各打一支 API, 整表存檔會發出大量請求且難保證原子性與順序; 若整表 delete + re-insert (同 ADR-008 同步路徑) 則會丟失既有列的稽核欄位與既有 `order`.
- 不解決會踩到: 存檔效率差、重複 key、order 錯亂、稽核欄位遺失.

**Decision**:
- 統一走 `updateTabItems(keyTable, userId, rows, keyDetect)` (`WWebPerm.mjs:352`): 先 `ltdtmapping` 對齊 schema 欄位、**重給 `order = k+1`** (`WWebPerm.mjs:360-363`, 與 ADR-008 同步路徑沿用外部 order 不同), 再以 `ckKey` 偵測未給/重複的鍵, 然後以 `ltdtDiffByKey(ltdtOld, ltdtNew, keyDetect)` 算出 `del` / `add` / `diff` 三組, 分別經 `procOrm` 寫入 (`WWebPerm.mjs:419-447`).
- **去重鍵依表而異** (`ckKey`, `WWebPerm.mjs:398-417`): `targets` 以 `id`、`pemis`/`grups` 以 `name`、`users` 以 `email` 去重; **`users` 以 `email` 而非 `name` 去重** (`users` 允許重複 name).
- **diff key (`keyDetect`) 依表而異** (`WWebPerm.mjs:455-476`): `targets`/`users` 以 `id`、`pemis`/`grups` 以 `name` 比對新舊列.
- 全程經 `procOrm` 而非裸 `woItems.insert/save/del`, 以自動補稽核欄位 (`WWebPerm.mjs:427, 435, 443` 註).

**Consequences**:
- ✅ 整表一次存回, 由 diff 算出最小變更集 (只刪/增/改有變動的列), 既有列保留稽核欄位.
- ✅ 重給 order 使後台列順序由前端表格順序決定, 確定且可控.
- ✅ 去重/diff 鍵的差異 (users 用 email) 集中於 `updateTabItems` 一處, 不分散.
- ⚠️ 後台寫入 (重給 order、diff) 與外部同步 (沿用 order、全量取代) 為兩套刻意不同的寫入路徑; 新增寫入入口時須選對路徑, 不可混用.
- ✅ **三層防護之後端 mutex 層已落地** (見 ADR-012): 整表批次寫入以 `pmKeyMutex` 按 `updateTabItems:{tableName}` 粒度序列化 (`WWebPerm.mjs:290, 362`), 同表並行寫入排隊、不同表並行, 避免 read-modify-write race 下的 lost-update.

**Affected**:
- server/WWebPerm.mjs:28 (ltdtDiffByKey import), :352-450 (updateTabItems), :453-478 (updateTargets/Pemis/Grups/Users)
- 並行序列化見 ADR-012 (按鈕雙擊三層防護)

## ADR-010: E2E pixel baseline 採 pixelmatch 反鋸齒感知容差, 非 byte-exact

**Status**: Accepted (2026-06-09)

**Context**:
- 後台四清單與關聯編輯之 e2e 以 pixel baseline 守護整體畫面長相. SVG icon (@mdi) / 字型邊緣之次像素 raster 在跨 browser session 不具決定性.
- 若以 `buf.equals` byte-exact 比對, 肉眼等同的反鋸齒 noise 會被當失敗, 造成無止境 flake (對齊全域 §6.2 殷鑑: icon 改 SVG 後 byte-exact 炸出大量次像素 flake).
- 不解決會踩到: e2e baseline 反覆假性失敗、被迫退化成純語意斷言或頻繁 regen.

**Decision**:
- 比對統一走 `assertBaselineMatch(buf, baselinePath, label, opts)` (`test/e2e-setup.mjs:430`): 以 `pixelmatch` (`includeAA:false` 自動忽略反鋸齒邊緣像素) + `maxDiffPixels` 容差 (預設 100) + `threshold` (預設 0.1) 比對 (`e2e-setup.mjs:473-474`). **舊的 `buf.equals` byte-exact 比對已完全移除, 現行程式碼內不存在**(唯一的 `.equals()` 在 `e2e-setup.mjs:294`, 屬 `captureStable` 判斷連續兩張截圖是否已 settle, 與 baseline 比對無關, 勿誤認).
- 尺寸不同直接 fail (版面/裁切變必為真差異, `e2e-setup.mjs:465-467`).
- 容差只放補強層, 主驗證仍為語意斷言 (DOM 文字 / URL / 元素存在); 真 regression (icon 換 / 版面位移 / 顏色變) 量級遠超 `maxDiffPixels` 仍被抓 (對齊全域 §6.2 原則 1).
- 截圖前以 `captureStable` (`e2e-setup.mjs:227`; 帶紅框標注版為 `captureStableWithBox`, `e2e-setup.mjs:306`) 等 WDrawer nav 收斂、凍結 SVG SMIL 動畫、等 web fonts 載入、retry-until-stable; 遮罩 (`maskRegions`) 僅用於 DOM 凍不到的 `<img>` 內 SVG `<animate>`, 絕不遮靜態 UI.

**Consequences**:
- ✅ 反鋸齒 noise 不再造成 flake, baseline 穩定可重現.
- ✅ 真 regression (量級遠超容差) 仍被抓, 守護價值不減.
- ✅ 比對門檻可由個別 case 經 `opts.maxDiffPixels` / `threshold` 覆寫, 需更嚴/更鬆時有出口.
- ⚠️ 極小幅真差異 (≤ maxDiffPixels 的真改動) 可能漏抓; 屬語意斷言為主、pixel 為補強層的刻意取捨.

**Affected**:
- test/e2e-setup.mjs:14 (pixelmatch import), :163-242 (captureStable), :309-356 (assertBaselineMatch)
- test/e2e-*.test.mjs (所有 e2e 檔)
- test/pics/<flow>/ (baseline 圖檔)

## ADR-012: 按鈕雙擊三層防護 — 元件 promiseUnlock / 頁面 loading / 後端 mutex

**Status**: Accepted (2026-06-18); 元件層寫法(handler 第一行 `msg.pm.resolve()`)與後端層契約(同一操作者之同表並行)由 ADR-025 修正(2026-09-29): 按鈕鎖改持續至請求結束並加送出流程狀態, 後端於 kmx 外層加「依操作者占位」(同一操作者 → `saveInProgress`)與新增列已存在檢查(`saveNewRowExists`); 不同操作者仍如本 ADR 序列化皆成功

**Context**:
- 後台四份清單的「存檔」屬有副作用寫入 (整表 diff 增刪改, ADR-009). 使用者雙擊、或 API 被直打 / e2e race 並發, 都可能讓同一表的 read-modify-write 互相覆蓋 (lost-update): 兩請求各拿同一舊快照算 diff 各自寫, 後者蓋掉前者.
- 單靠前端防護擋不住繞過前端的並發 (API 直打); 單靠後端鎖則使用者仍會看到按鈕無回饋的雙擊體驗.
- 不解決會踩到: 重複寫入 / lost-update、按鈕無鎖視覺、並發下 DB 終態不確定.

**Decision** (對齊本專案 CLAUDE.md「按鈕雙擊防護」與全域 §5.1):
- **元件層**: 四個主存檔鈕 `WButtonCircle` 加 `:promiseUnlock="true"` (`LayoutContent{Users,Grups,Pemis,Targets}.vue:188`); handler 收 `{ pm }`、**第一行 `msg.pm.resolve()`** 釋放視覺鎖、fire-and-forget 呼叫內部 `doSaveXxx`. Ve 系列彈窗 `clickSave(msg)` 亦把 `msg.pm.resolve()` 移到第一行.
- **頁面層**: `doSaveXxx` 走 §5.1 canonical 五段 — 同步檢測 (空列表 / isError) 在 `updateLoading(true)` **之前** early-return; 確定打 API 才開 loading; 各 async 各自 catch + `okSave` 旗標短路; 外層 `core().catch` 接非預期例外、`finally` 一處關 loading. 可預期錯誤走 `$dg.showCheckYes` DOM 模態 (不用原生 dialog).
- **後端層**: `pmKeyMutex` 單例 (`WWebPerm.mjs:290`) 把 `updateTabItems` (`:362`) 與 `syncAndReplaceTabs` (`:714`) 包進 `kmx('updateTabItems:'+keyTable, …)` / `kmx('syncAndReplaceTabs:'+keyTable, …)`. **粒度 = `{op}:{tableName}`** (非 sso 的 per-row key, 因 perm 是整表批次 diff): 同表寫入排隊序列化、不同表並行.

**Consequences**:
- ✅ 三層各擋一類並發: 元件擋 sync 雙擊、頁面 loading overlay 擋 async 期間互動、後端 mutex 擋 API 直打 / e2e race; 同表寫入序列化, 無 lost-update.
- ✅ 後端向後相容, 不改 RPC 介面與回傳; 元件僅加行為 prop, 不動視覺 prop, 不影響 baseline.
- ⚠️ mutex 為 in-process (單後端實例內有效); 多後端實例共用同一 DB 的並發不在此契約內 (對齊全域 §3.1: 多 process 並發屬合約外, 非當前需求).

**Affected**:
- src/components/LayoutContent{Users,Grups,Pemis,Targets}.vue:188 (:promiseUnlock), saveXxx handler + doSaveXxx 五段

## ADR-013: 整表批次寫入 (updateTabItems del→insert→save) 採非交易, 不做 rollback

**Status**: Accepted (2026-06-22)

**Context**:
- `updateTabItems` (`server/procCore.mjs`) 以「差異後 del → insert → save」三步落地整表 diff (ADR-009), 三步各自 `await procOrm(...)`, 底層 `w-orm-lmdb` 為各自獨立 commit, **步驟間無交易/rollback**.
- 整段已包在 `kmx('updateTabItems:'+keyTable, …)` 互斥內 (ADR-012): kmx 保證「同表不並發」(防 lost-update), **但不保證「單次操作中途失敗時的部分回滾」**.
- 理論上若中途某步 reject (如 del 成功、insert 因 ORM I/O 失敗), DB 會停在部分更新的不一致態.

**Decision**:
- 維持非交易設計, **不引入跨步交易/補償回滾**. 理由 (對齊全域 §3.1 真痛三條件):
  1. 寫入前 `ckKey` 已擋掉空值/重複等可預期錯誤, diff 後的 del/insert/save 多為純資料操作, 中途失敗需 DB 層 I/O 異常 — **未被觀察** (無重現、無 ticket).
  2. 無任何 spec 宣稱整表 diff 寫入須具交易原子性; lmdb 逐表逐法呼叫本就無跨呼叫交易語意.
  3. 後果 (部分更新) 為推測性, 且本工具為單一管理員驅動之後台, 觸發面窄.
- 失敗時各 `updateXxx` 已 `srLog.error` 記 err key (event=`updateTargets-error` 等) 後 rethrow, 供事後追查.

**Consequences**:
- ✅ 不為消除假想風險引入交易層複雜度與退化 (§3.1).
- ⚠️ 若日後實機觀察到「del 成功 / insert 失敗」導致整表部分遺失 (condition「已被觀察」成立), 再評估最小修法: 將 del+insert+save 包進單一錯誤邊界、失敗時以前置快照補償.

**Affected**:
- server/procCore.mjs (updateTabItems del/insert/save 三步; updateTargets/Pemis/Grups/Users 失敗記 err key)

**Update (2026-10-14): 前提「中途失敗需 DB I/O 異常、未被觀察」已不成立——可預判之失敗改於寫入前擋下(ADR-026), 非交易之決定維持**

- w-serv-orm 1.1.8 起 procOrm 對「會被 XSS 清除改寫之主鍵」整批拒絕, LMDB 對 UTF-8 超過 1978 位元組之主鍵整批拒絕; 兩者皆可由使用者輸入觸發, 且發生在 del 之後(改標的路徑為 `…<x` 時該列遺失, 2026-10-14 真瀏覽器實測 V7, 已被觀察). 本 ADR 決策理由 1 之「ckKey 已擋掉可預期錯誤」因此不足.

## ADR-015: 寫入通道授權契約 — 內建 ORM/kpFunExt 由 verifyConn(checkToken) 守門, 整合者負責 getUserByToken 把關

**Status**: Accepted (2026-06-23) — 文件化既有設計契約(對應審計 v1 資安-1 / 待修 T01); **2026-09-29 業主裁示: 資料通道維持嚴格預設**(見文末 Update 2026-09-29; 下方 Decision 之 footgun 警示與「可選強化預設不做」已被取代, 原文保留作歷史)

**Context**:
- 本套件對外有兩類通道, 守門不對稱:
  1. **自訂讀取 API**(`/api/getPerm`、`/api/getUserByToken`): 經 `getAndVerifyClientUser` → 呼叫整合者提供之 `verifyClientUser(user)`(範例為 `isAdmin==='y'`), 故套用整合者之 client 授權政策。
  2. **內建 ORM exec 通道 + kpFunExt 變更函式**(`updateTargets/Pemis/Grups/Users`、`select/insert/save/del/delAll`): 唯一守門為 `verifyConn`, 而 `verifyConn` 走 `p.checkToken` → 只驗「token 可經 `getUserByToken` 解析出結構合法 user」(id/email/name/isAdmin 齊備, isAdmin∈{'y','n'} 皆可), **不呼叫 `verifyClientUser`、不檢查 isAdmin**。
- `verifyConn` 為套件**內部**邏輯(非整合者傳入參數), 整合者無法直接改其判定; 整合者對寫入通道的實際控制點是 **`getUserByToken`**(決定哪些 token 能解析出有效 user)。

**Decision**(契約釐清, 不改 code):
- 內建寫入通道之存取邊界 = **「token 可由 `getUserByToken` 解析出結構合法 user」**。**整合者負責**確保 `getUserByToken` 只對「應具寫入權」之主體回傳有效 user(例如僅對管理員 token 解析成功, 或在 `getUserByToken` 內依角色決定)。
- **明確警示(footgun)**: `verifyClientUser` **只套用於上述自訂讀取 API, 不套用於內建寫入通道**。整合者若提供 `verifyClientUser`(如限 isAdmin)並預期它守住一切, 須知**寫入通道不經此 hook** —— 讀取被擋、寫入仍放行。要 admin-only 寫入, 須在 `getUserByToken` 層把關。

**Consequences**:
- ✅ 維持套件彈性: 寫入授權政策交由整合者之 `getUserByToken` 決定, 不在套件硬編特定角色規則。
- ⚠️ 不對稱為已知契約: 若整合者同時(a)以 `getUserByToken` 解析非管理員 token(供讀取 API 經 `verifyClientUser` 過濾)且(b)未在 `getUserByToken` 層限制寫入主體, 則該非管理員 token 可經內建通道寫入全部權限表。此為**整合契約責任**, 非套件缺陷; 但部署前務必確認 `getUserByToken` 的把關範圍。
- 🔧 可選強化(整合者要求時再做, 預設不做, 因有破壞性): 將 `verifyConn` 由 `p.checkToken` 改走 `getAndVerifyClientUser`, 使寫入通道亦套 `verifyClientUser`。**代價**: `getAndVerifyClientUser → getTokenUser` 會額外要求「該 user 須存在於 perm `users` 表且 `isActive='y'`」(`WWebPerm.mjs:441`), 改變整合契約(連線主體須先在 perm 表), 可能破壞既有整合, 故須整合者明確同意後才套用。

**Affected**:
- server/WWebPerm.mjs:1066-1101(verifyConn)→ :1082(p.checkToken)→ :467-477(checkToken); :481-502(getAndVerifyClientUser, 僅用於讀取 API)

**Update (2026-09-07/09-12): 上述「可選強化」已實作, 但實作方式尚待業主裁示**

- **觸發**: 整合者 rddmanager_2_perm 提出建議書(其 §2)要求「於 verifyConn 呼叫 verifyClientUser, **或新增 verifyWriteUser 鉤子**, 讓部署層授權政策涵蓋資料通道; 閱讀類維持現狀即可」。該部署已將前端登入限為系統管理者, 故持有效 token 之非管理者仍可自製客戶端經資料通道寫入權限資料。
- **實測佐證(修正前)**: app token(不在 perm users 表)可寫 grups; admin 自行設 isActive='n' 後仍可經資料通道讀寫並自我復活。
- **目前實作**: `p.checkToken` 改走 `getAndVerifyClientUser(token, apiType)`, 即本 ADR 所列之可選強化, 且為**預設生效、無開關**。回歸測試 `test/api-verifyConn-auth.test.mjs`(AUTH-000~004)守護。
- **與本 ADR 之衝突(待裁示)**: 本 ADR 原訂此強化「預設不做, 因有破壞性, 須整合者明確同意後才套用」; 目前實作為預設生效, 且一併收緊讀取(verifyConn 層只見 apiType, 無法區分讀寫), 超出建議書「閱讀類維持現狀」之要求。對其他未知整合者屬破壞性變更(連線主體須先在 perm 表)。
- **建議之三層拆分(尚未實作, 待裁示)**: ①**perm 表內明確停用者(isActive='n')拒絕**——此為 perm 自身 UI「是否有效」之承諾, 不在表者不受影響, 故可預設開啟, 不破壞整合契約; ②新增整合者可選傳入之鉤子(如 `opt.verifyConnUser(user, from)`), **未傳即維持舊行為**; ③「須在 perm 表」之要求**只在整合者傳入該鉤子時**才生效。如此 rddmanager 傳鉤子即獲完整保護, 其他整合者原封升級不壞, 且符合本 ADR 原訂之「整合者要求時再做」。

## ADR-016: token 經 URL query string 傳遞 — 為整合者轉址需求維持(刻意設計)

**Status**: Accepted (2026-06-23) — 業主確認之刻意設計

**Context**:
- 本套件之登入與對外查詢採 token 經 URL query 傳遞:應用啟動可由網址 `?token=` 取得(App.vue,亦 fallback 至 localStorage);對外 SDK(`perm.mjs` / `getPerm` / `getPermUserInfor`)之端點 URL 含 `?token={token}`(及 getPermUserInfor 之 `&userId=`)。
- **業主整合需要「轉址(redirect / SSO 回跳)」攜帶 token** —— 轉址流程以 URL 帶 token 為必要手段,故維持此設計。
- 一般資安觀點對「token 經 query string」會提示 referrer / 瀏覽紀錄 / log 之揭露面;但須區分:此為**整合契約所需之刻意取捨**,非疏漏。

**Decision**:
- **維持 token 經 URL 傳遞**,不改為純 header/cookie。理由:整合者之轉址/SSO 回跳依賴 URL 攜帶 token,改動會破壞整合流程。

**Consequences**:
- ✅ 滿足整合者轉址/SSO 回跳之必要傳遞方式。
- ✅ 揭露面已部分受控:**`srLog` 全程不記 token 值**(已查證,WWebPerm.mjs 各 srLog 呼叫僅記 event / err key / ip / origin / referer,無 token 欄位),故無「token 明文入持久化 log」之面。
- ⚠️ 已知殘留揭露面(接受):URL 中之 token 可能進入瀏覽器歷史 / referrer header。屬轉址設計之固有取捨;若整合者部署環境敏感,可於其轉址層自行縮短 token 壽命或改用一次性 token,但非本套件預設行為。

**Affected**:
- src/App.vue(?token= 登入)、src/perm.mjs / src/getPerm.mjs / src/getPermUserInfor.mjs(URL 帶 token)、server/WWebPerm.mjs(srLog 不記 token)

**Update (2026-09-25): 更正 Consequences 第二點「srLog 全程不記 token 值」——該查證漏了 referer 與注入函數之錯誤原文兩條通道**

- **原載『srLog 全程不記 token 值(已查證, 各 srLog 呼叫僅記 event / err key / ip / origin / referer, 無 token 欄位)』不成立**: 查證只看了「有沒有 token 欄位」, 未看欄位**值**從哪來. 實測(ADR-023 修正前探測): ①`verifyConn` 之 `referer` 原樣記錄, 而本設計正是以 `?token=` 開站(w-ui-loginout 讀完不清網址), 同源請求依瀏覽器預設政策帶完整網址作 Referer——每個資料通道請求都把使用者權杖寫進 srLog; ②`verifyConn-error` 之 `msg` 取自 checkToken 之 reject, 而部署方注入之 `getUserByToken`(常為 w-web-sso ≤1.1.4 之 helper)失敗時 reject 含介接權杖與使用者權杖之完整網址. 另 console(stdout)有 22 處原樣印權杖, 亦屬持久化揭露面(行程管理器常擷取 stdout 落檔).
- **現況**: 已由 ADR-023 處置——`referer` 改記 `maskUrl(referer)`(只留 origin + pathname)、注入函數經 `wrapInjected` 包裝(上游原文不入 log)、console 經 `maskTok` / `maskQuery`; 前端 `public/index.html` 加 `referrer: strict-origin`(發布後生效). 本 ADR 之決策(維持 token 經 URL 傳遞)不變; 殘留揭露面(反向代理 access log 之網址、瀏覽器歷史)仍為接受之取捨, 已外洩之 log 之清理見 w-web-sso ADR-068 營運處置.
- **教訓**: 「log 不含 X」之查證須追每個欄位值之來源(含請求標頭與上游錯誤訊息), 不能只看欄位名.

## ADR-017: 測試檔命名與定位之三個刻意例外 (e2e-doubleclick / api-updateTabs / getUserRules)

## ADR-018: token 失效之模擬走前端狀態 API, 為 act 階段之技術限制例外

**Status**: Accepted (2026-07-09)

**Context**: `e2e-{targets,pemis,grups,users}.test.mjs` 之 **E2E-010(儲存失敗)** 皆需讓「持有無效 token」成為前置狀態, 再點 Save 觀察失敗 modal。四檔一律於 `run()` 中段以 `page.evaluate(() => window.$vo.$ui.updateUserToken('invalid-token-e010'))` 注入(如 `test/e2e-users.test.mjs:359`)。

依全域 e2e 技能, setup helper「只能用於**不是本測試重點**的 trigger」。本案之 token 失效**正是該 case 的重點觸發條件**, 嚴格說屬邊界。惟:

- **無任何真實 UI 路徑可使 token 失效** —— token 由整合者之 `getUserByToken` 判定, 前端無「使 token 過期」之按鈕; 等待真實過期不可行(無 TTL 控制)。
- 該注入**不繞過任何 production 程式碼路徑**: 注入後仍完整走「點 Save → 五段 core() → `$fapi.updateXxx` → 後端 `verifyConn` → `checkToken` 拒絕 → 失敗 modal」, 前後端鏈路一次不少。被抹平的只有「token 如何變成無效」這個前置狀態。

**Decision**: **接受此例外**, 不視為 act 層級違規。理由是它抹平的是**前置狀態(世界已是某狀態)**而非**使用者動作**; 且該注入點之後的整條使用者動作鏈與斷言鏈皆完整。四檔須維持 `//setup：模擬 token 失效` inline 註解。

**Consequences**:
- ✅ E2E-010 得以驗證真實的「後端拒絕 → 前端失敗 modal」鏈路, 而非假造 modal。
- ⚠️ 代價: 「token 從有效變無效」這一步未經 UI 驗證。此步驟本就不存在對應 UI, 故非覆蓋缺口。
- ❌ **不得**擴大解釋: 除 token 失效外, 其餘 act 階段一律走 user-facing input(L1-L3), 禁用 `.fill()` / `vm.method()`。

**Affected**:
- test/e2e-{targets,pemis,grups,users}.test.mjs 之 E2E-010(各檔 `updateUserToken` 呼叫點)

## ADR-020: 側欄選單 launch 級 1px 剛性位移 flake —— 根因調查與確定性渲染修法

**Status**: Accepted (2026-08-26)

**Context**: 2026-08-25 全量重產標準圖後, e2e 間歇性失敗(每輪完整跑 130+ 張截圖中獎 1~3 張, 觀測 5 次全在 eng): 左側選單(WListVertical 五項)相對 baseline 整體水平位移 1px, diff 固定 3634~3635px、bbox (14,77)-(183,300)。

**根因調查結論**(本專案 + GPT-5.6-Sol 獨立調查交叉驗證, 調查證據存 testPending 四組現場):
- **已驗證**: 逐像素驗證 `capture(x,y)==baseline(x+1,y)` 於 icon/文字區**零失配**——內容連 AA 色階都原封不動整體左移 1px, 即「同一份已光柵化 bitmap 被合成到偏左 1px」, **非**字形 subpixel 重畫、**非** DOM layout(rect 量測 6 輪整數穩定)、**非** scrollLeft(WPanelScrollyCore divShell 實測 scrollWidth==clientWidth==200、強制 scrollLeft=1 被 clamp 且零像素變化, eng/cht 幾何相同)。
- **已驗證**: 位移邊界 == WPanelScrolly 捲動內容層邊界(抽屜邊線 x=199、收合鈕區、頁首皆零差異); 同 launch 連拍位元級穩定 → **launch 級二態**; 同一產圖程式兩輪會在不同 case 翻面 → baseline 本身是抽樣, 重產不能收斂。
- **當時假說(已被下方「最終收斂」取代)**: WPanelScrolly 捲動內容 raster layer 在帶常駐 `transform:translateX(0%)` + `transition:all` 之 WDrawer layer tree 中, 以 launch 級決定的水平 raster origin 被合成。
- 本專案原為三姊妹專案(sso/api/perm)中**唯一裸 launch** 者; w-web-api 有最接近先例(WTree 整棵樹 ~6px 剛性位移, 六旗標後消失, self-consistency 2/4→5/5)。

**Decision**(業主核可 1,2,3; 統計重跑不得作為 e2e 驗證手段——業主僅裁示此點, 根因鑑別須繼續):
1. 紅框標注改「截圖後 sharp 疊圖」, 不再注入/移除 DOM(api toast 殷鑑: 暫時 DOM insert/remove 偶發整頁偏 1px; 量測工具不得改動被測頁 layer tree)。幾何與原 DOM 版一致。
2. `launchBrowser` 加 w-web-api 六旗標確定性渲染組, e2e-init 三處直接 launch 改走 `launchBrowser`(旗標分叉防護)。採 api 六旗標不採 sso 四旗標: 本案已排除字形重畫, api 組才有剛性位移先例與實測數據; 不另加 sso-only 之 `--font-render-hinting=none`。
3. 全量重產 324 張標準圖(旗標改變所有 AA/顏色像素, cht 亦不可豁免)。

**Consequences**:
- ✅ 比對政策不變: `threshold:0.1, includeAA:false, maxDiffPixels:100` 不放寬; 1px 剛性位移**必須**繼續 fail(它是結構性差異, 不是 AA noise)。禁止以 ±1px 容差回退或統計重跑掩蓋。
- ✅ **根因已收斂**(見下「最終收斂」); 本 ADR 之六旗標 + sharp 疊圖修法保留(確定性渲染防護仍有價值), 不因上游修正而回退。
- ✅ **同款幾何盤查已收斂**: 上游 2.5.7(2026-09-01)另移除 `WDialog.vue` 屏蔽層內撐開層之 `+1px`(原 `calc(100svw + (nativeBarWidth+1)px)` → `100svw`); 原調查期間對 WDrawer transform / transition 之假說經業主裁示為假議題, 不列待辦。
- 調查全文原存 tmp/sol-reply2.md(T1 像素分析)、tmp/sol-reply3.md(T2-T5 姊妹盤點與修法規格), tmp 已清理, 以本 ADR 為準。

**最終收斂**(2026-08-30 ~ 2026-09-01 補記):
- **根因**: `w-component-vue` `WPanelScrollyCore.vue:29` 捲動殼寬度為 `calc(100% + (nativeBarWidth+1)px)`; headless Chromium 之捲軸為 overlay 而 `nativeBarWidth=0`, 故捲動殼恰**懸出外層 1px**, 被外層 `overflow-x:hidden` 裁切。軟體合成器對此懸出層之對齊方式二選一(左緣貼齊＝正常、右緣貼齊＝整層左移 1px), 於 launch 初始化決定一次, 與本 ADR 觀測之「launch 級二態、同 launch 連拍位元級穩定、內容連 AA 色階原封不動整體左移」完全一致。
- **量測**: `+1` 時捲動殼實寬 200 / 裁切殼 199(懸出 1px); 改 `+0` 後 199 / 199, 側欄與正常態參考圖逐像素 0 差異。位移量＝懸出量之方程式與 w-web-api WTree 先例(6px 溢出 → ~6px 位移)吻合。
- **上游修正**: w-component-vue **2.5.3 為 `${nativeBarWidth+1}px`, 2.5.4(2026-08-26 發佈)起改 `${nativeBarWidth}px`**(npm tarball 逐版比對確認); 本專案 2026-08-31 升至 2.5.6。
- **本專案處置**: 升版後全量重產 324 張標準圖並跑完整 e2e 全綠; 重產後認證掃描(LCD 彩邊、側欄指紋分群雙語對稱)通過。1px 調查期間加入之 e2e 診斷閘門(`E2E_BARE` 裸 launch / `E2E_DIAG` 治癒階梯 / `E2E_DIAG2` launch 探針)已於 2026-09-01 全部移除(其中 `E2E_BARE` 曾因搭配 `--baseline` 誤覆寫正式 baseline, 屬應拆鷹架)。

**Affected**:
- test/e2e-setup.mjs(chromiumLaunchArgs、launchBrowser、captureStableWithBox)

- test/pics/**(324 張全量重產)

2. **M 契約(遮罩, 四 repo 一致)**: 新增 `server/maskLog.mjs` 之 `maskTok`(空值 → `''`; 陣列逐元素; 字串露出 `k = min(4, floor(n/8))` 字, `k=0` 只給 `(len=n)`, 露出字之控制字元換 `?`; 其他型別只給 `(typeof)`)、`maskQuery`(淺拷貝, 鍵名小寫為 `token` 者遮罩)、`maskUrl`(http(s) 只留 origin + pathname; 非 http(s) 只回 protocol; 無法解析 `(invalid-url)`). 22 處 console 改經遮罩; `verifyConn` 之 srLog `referer` 改記 `maskUrl(referer)`. 測資與 sso `maskToken` 同一組.
3. **SDK**: `getPermUserInfor` 佔位符缺一即拒(`||`, 對齊 sso ADR-056 修正紀錄); `getPerm` / `getPermUserInfor` 代入改 `split(佔位符).join(encodeURIComponent(值))`; `funConvertPerm` 同步拋錯或 reject → `noUserDataAfterConvert`; `fetchJson` 之 reject `message` 改為 `err.name`(附代碼形狀 `/^[A-Z][A-Z0-9_]{1,40}$/` 之 `cause.code` / `code`), `kind` / `status` 不變, 故 `perm().conn` 與 `provideTabs` 之 reject 不再帶網址.
4. **參考部署與範例**: srv.mjs 不印權杖值; JSDoc 與 README 範例同. srv.mjs 新增兩個測試權杖(僅 `process.env.NODE_ENV !== 'production'`): `{token-for-reject}`(以舊版 helper 形狀之字串 reject, 夾合成秘密)、`{token-for-verify-throw}`(`verifyClientUser` / `verifyAppUser` 對其 throw 合成秘密).
5. **referrer 政策**: `public/index.html` 加 `<meta name="referrer" content="strict-origin">`——縱深防禦: 同源請求之 Referer 只帶 origin, 反向代理 access log 之 Referer 欄亦不含權杖; 後端 `maskUrl` 為主防線, 不依賴前端.

**Consequences**:
- ✅ 四個 HTTP 入口與資料通道於上游失敗時回自家 key; C1 / C2 / C3 皆不含權杖(探測 after 全通道 0 筆).
- ✅ 上游失敗首度入 srLog(warn), 可稽核; 仍可經 `upstream` 欄區分 sso 端 K 契約之失敗點.
- ⚠️ **log 筆數**: 方案 v2 之跨 repo 敘述為「同一次失敗 1–3 筆: 包裝處 warn(因) + 呼叫點 error(果)」; 本專案實測為 2 或 3 筆: HTTP 入口與 `getUserIdByToken` = warn + 呼叫點 error(`getTokenUser-error` / `getAndVerifyClientUser-error` / `getAndVerifyAppUser-error` / `getUserIdByToken-error`)共 2 筆; 資料通道再加 `verifyConn-error` 共 3 筆. 統計頁會出現新事件名 `inject-*-fail`.
- ⚠️ **部署方可觀察之行為變化**: 注入函數拋錯時回應 `msg` 由上游原文改為自家 key; verify* 拋錯時由 `Error.message` 改為 `userNoPermission`. 依賴 `msg` 原文者須改依 key(本即 CLAUDE.md「錯誤一律回 key」).
- ⚠️ **SDK 線上格式**: 代入值經 `encodeURIComponent`, 含大括號之權杖(如 `{token-for-application}`)送出為 `%7B…%7D`, 伺服端解出值不變; UUID、英數與 `-_.~` 為恆等. `getPermUserInfor` 之 url 只含一個佔位符者由「照送」改為 reject `noTokenUserIdInUrl`. 兩支既有測試因凍結舊行為而更新: `unit-fetchJson-sdk` FJ-011(斷言原樣大括號)、`api-getPermUserInfor` 002(「對照子斷言」斷言只缺 userId 時不拒).

## ADR-024: 統計圖圖例採混合式——一般式放得下維持、放不下改捲動式；判定以離屏量測 (2026-09-24)

> 編號說明: 同日另一工作(權杖安全 W / M 契約)於程式碼與測試註解預先引用 ADR-023(其本文已於 2026-09-25 寫入本檔, 見上), 為免撞號本 ADR 取 024.

**Status**: Accepted (2026-09-24 業主指示「重新仔細思考與規劃的修正方案」, 經兩位獨立審查者複審後「當得出有最終修正方案後, 就由你執行」)

**Context**:
- 部署方回報(2026-09-24 建議書「建議 w-web-perm 修正:「統計資訊」之「事件發生頻率」圖例於較窄版面壓住折線圖」, 原置專案根 `建議w-web-perm修正.md`, 修正完成後已於 2026-09-27 刪除; 1.1.4、8 種事件): 版面變窄時「事件發生頻率」圖例換行後疊在刻度與折線上(768 寬 4 列、500 / 360 寬 8 列). 查證屬實: 圖例 `{show, top:0}` 為可換行之一般式, 繪圖區頂為 echarts 6.1.0 預設 **65**(回報原載 60; `GridModel.js:84`), 列距 21: 2 列底 39、3 列底 60 擦到最上方刻度字頂 59、4 列底 81 壓進繪圖區. 本專案 mock 5 事件於視窗 400(圖寬 300)即 3 列.
- 回報提兩案: ①全面改捲動式(w-web-api 同類圖作法); ②依圖例高度加大繪圖區頂. 並要求 1600 寬畫面與現行相同.
- 技術限制(皆已讀碼並實測): echarts `resize()` 不 flush zrender(`echarts.js:964-1012`), resize 後讀顯示列表為上一寬度之排版; 圖例子類型改變時以新傳入之選項重建模型(`Global.js:322-344`), 未帶之 `top`/`show`/`selected`/頁次回預設(`top` 遺失即落到圖底, echarts 6 圖例預設為 bottom); 捲動式翻頁有 800ms 平移動畫(`ScrollableLegendModel.js:91`); `w-echarts-vue` 1.0.14 `autoresize` 以參照判斷變更且略過 ResizeObserver 首次回報(`WEchartsVue.vue:150-154,285-293`).

**Decision**:
1. **混合式**: 一般式圖例放得下時維持一般式(寬螢幕外觀與現行相同), 放不下時改捲動式(單列 + 左右箭頭與頁次). 「放得下」= 一般式圖例文字底緣 ≤ 57(= 繪圖區頂 65 − 刻度半字高 6 − 留白 2), 實際等同最多兩列. `grid.top: 65` 於 option 明寫以防預設變動.
2. **判定以離屏量測**(`src/js/legendFit.mjs` `createLegendMeasurer`): 未掛 DOM 之 echarts 實例只含一般式圖例、隱藏座標軸與同名空系列, 量得 `{rows, bottom}`; 為事件名稱集合與圖寬之純函數. 不讀可見圖(resize 未 flush)、不在可見圖上試排(試排即重建模型: 頁次歸零, 帶回頁次則每次縮放滑動 800ms). 量測失敗(寬 ≤ 0、找到之文字數 ≠ 名稱數)一律判捲動式(單列不會重疊).
3. **觸發時機**: 圖表設定更新後(`$nextTick`); 容器尺寸與圖不一致而重繪後(`autoresize.onResize`, throttle 100; w-echarts-vue ≥1.0.15 於每次尺寸回報比對容器與圖之尺寸, 含圖剛建立之同一幀, 並於呼叫 `onResize` 前 flush). 使用 1.0.14 期間(2026-09-24~26)另有「`autoresize` 物件須為固定參照」與「設定更新後之下一個 rAF 比對圖寬與容器寬, 不同即先 `resize()`」兩項專案端補救, 1.0.15 修正後移除後者(前者之 data 物件保留, 無害), 見修正紀錄.
4. **切換**: 類型不變不動圖(捲動式頁次保留); 類型改變才 `setOption({ legend: { ...genLegend(type), selected: 目前 selected } })`. 圖例設定之單一來源為 `genLegend(type)`(`{show, top:0, type}`, 捲動式另帶 `tooltip.show` 於滑過時顯示被截斷名稱之全名), `genOpt` 與切換共用.
5. **測試資料**: 後端 `staEventMock` 接受 `'many'`(13 種本系統實際事件名), `true` 仍為原 5 種(既有標準圖不變); 13 事件於圖寬 1140 時「全部加總」名稱之語系差異恰跨越門檻(eng 1130 放得下、cht 1150 放不下; 逐 1px 實測), 用以驗證判定隨語系翻轉.
6. `w-echarts-vue` 兩缺陷先於專案端避開(第 3 點), 修正建議交元件庫(2026-09-24 建議書 `建議w-echarts-vue調整.md`, 1.0.15 採納後已於 2026-09-27 刪除), 已於 1.0.15 修正; `legendFit.mjs` 無外部相依, 日後可移入元件庫為 opt-in 屬性(1.0.15 未提供此類屬性).

**Alternatives(不採)**:
- 全面捲動式(回報案①): 寬螢幕上原本兩列即可完整看到的圖例變成須翻頁, 且 1440 / 1600 寬畫面改變(違反回報之驗收條件、既有標準圖全數改變).
- 依圖例高度加大繪圖區頂(回報案②): 圖高固定 300, 窄版 8 列時繪圖區剩不到一半, 折線反而難讀.
- 固定寬度斷點(如 < 768 改捲動式): 放不放得下取決於事件數、名稱長度與語系, 13 事件於 1440 寬 cht 即放不下, 斷點必然失準.
- 在可見圖試排或讀可見圖之圖例元件高度: 見 Context 技術限制; 圖例元件實例之取得(`getViewOfComponentModel`)於型別定義為 private.
- 改由元件庫提供屬性: 先在本專案穩定, 再以建議書提出(第 6 點).

**雙獨立複審**(2026-09-24, 全域技能 dispatch-claude, 兩位 Opus 5.5 max 各自讀檔並以測試架實測, 報告 32 / 42 條): 原方案(可見圖 resize 後讀顯示列表、模板字面值 `autoresize`、切換只帶 `{type, selected}`、捲動式試排)之三個高嚴重度缺陷兩位結論一致且各附重現; 採納 14 條(上述限制、門檻幾何化、量測失敗判捲動式、mock 13 事件、e2e 只點可視窗內項目與以元素名定位翻頁鈕、導覽區收合跨門檻案例、E2E-003 重產前守門、瀏覽器單元測試與全寬掃描、文件與事實更正); 不採: 每次在可見圖試排(800ms 滑動)、`@hook:mounted` 補判(圖之重建只經 `updateCharts`, 已有判定)、放大翻頁箭頭(改變外觀, 列為設計事實); 延後: w-web-sso 三張圖同機制(另立後續, 移植前以同法驗證 bar 圖).

## ADR-025: 按鈕雙擊防護補齊——按鈕鎖至請求結束、送出流程狀態、後端依操作者占位 (2026-09-29)

**Status**: Accepted(業主 2026-09-29 指示「前端按鈕用 promiseUnlock、後端依使用者加狀態擋連發」, 四專案同一原則, 對應 w-web-sso ADR-074; 修正 ADR-012 之元件層寫法與後端層契約)

**Context**(行號為修改前之 git HEAD):
- 有副作用之送出入口共 6 個, 皆為 `WButtonCircle` 且已 `:promiseUnlock="true"`: 四清單頁工具列儲存鈕(`LayoutContent{Grups,Pemis,Targets,Users}.vue:178-191`)→ `updateGrups` / `updatePemis` / `updateTargets` / `updateUsers`; 兩個自帶存檔之關聯對話框(`VePemiBlngGrups.vue` → `updateGrups`、`VeGrupBlngUsers.vue` → `updateUsers`)之儲存鈕為 `WDialog` 內建鈕(`node_modules/w-component-vue/src/components/WDialog.vue:189-205`, 經 `clickSave` `:973-986` 以 `click-save` 事件交出 `msg.pm`). `VeCgrups` / `VeCpemis` / `VeCrules` 之儲存只把設定序列化回傳頁面、不打 API; 本系統無登出、無改密碼、無「先開確認框再打 API」之流程(`showCheckYesNo` 僅註冊於 `Common/CheckYesNo.vue`, `src/` 內無呼叫).
- ADR-012 之元件層寫法: handler 第一行 `msg.pm.resolve()`(如 `LayoutContentGrups.vue:1189`、`VePemiBlngGrups.vue:993`)後 fire-and-forget, 鎖立即解除. `WButtonCircle` 之滑鼠與鍵盤 Enter 同走 `clickBtn`(`WButtonCircle.vue:30-31`), 受 `loadingTrans` 擋(`:626`), 元件無缺陷; 全頁 loading(WDialog)不搶焦點、只擋滑鼠, 鍵盤事件仍送達背後之按鈕(w-web-sso 2026-09-29 實測), 故焦點留在儲存鈕時連按 Enter 可送出 2 次.
- 後端 `updateTabItems`(`server/procCore.mjs:56-171`)只以 `kmx('updateTabItems:'+keyTable)` 序列化(`:63`), 同一操作者連送 2 次皆被執行: 第 2 次於第 1 次完成後處理時, 第 1 次剛新增之列經 `ltdtDiffByKey`(`:141`; users / targets 以 `id`、grups / pemis 以 `name` 比對)被當「修改」整列 `save`, 而 procOrm 之 save 只覆寫 `userIdUpdate` / `timeUpdate`(`node_modules/w-serv-orm/src/getMapOrm.mjs:71-88`), 伺服器於新增時填入之建立者 `userId` / 建立時間 `timeCreate` 被前端新列之佔位字 `{${$t('xxxAddIdNew')}}`(四頁 `addItem` / `copyItem`, 如 `LayoutContentUsers.vue:929-934`、`:994-1000`)覆寫. w-orm-lmdb insert 以 `ifNoExists(id)` 去重, 不會產生重複列.
- 本專案特有: 清單頁與對話框之驗證失敗(`isError` / 空清單)於開 loading 之前早退並開訊息框(ADR-012 頁面層 canonical, 如 `LayoutContentGrups.vue:1204-1216`); 自帶存檔之對話框存檔失敗不關窗(`CLAUDE_rulebook.md`「自帶存檔之對話框, 存檔失敗不得關窗」).
- 單例之等待者(w-web-sso 同日發現, 本專案同型): `Common/CheckYes.vue`、`Common/CheckYesNo.vue` 與 5 個 Ve* 對話框皆為單例, `show()` 直接 `vo.pm = genPm()`(如 `CheckYes.vue:63`、`VeCgrups.vue:865`)而不了結前一個等待者. 送出流程以 runSubmit 涵蓋至結果訊息框關閉後, 若訊息框開啟中又有另一處開框, 前一流程永久等待、其 key 永不釋放, 該操作無法再觸發; Ve* 對話框開啟中再次開啟(焦點留在表格內之開啟鈕時按 Enter)則前一階段之 promise 永久懸置.

**Decision**:
1. **前端(元件層)**: 6 個入口之 handler(`saveGrups` / `savePemis` / `saveTargets` / `saveUsers` / 兩對話框之 `clickSave`)**不於 handler 解鎖**, 把 `msg.pm` 交給送出函式(`vo.doSaveX({ pm: msg.pm })`); 鎖於全頁 loading 關閉(`$ui.updateLoading(false)`, 即請求結束)時釋放——請求期間滑鼠與鍵盤皆擋, 結果訊息框出現時按鈕已恢復. 驗證失敗之早退路徑未開 loading, 於開訊息框前以 `runSubmit` 交給流程之 `unlockBtn()` 釋放本次按鈕鎖(按鈕鎖只涵蓋請求期間).
2. **前端(送出流程狀態)**: 送出函式以 `$ui.runSubmit(key, (unlockBtn) => …, { pm })` 包覆(核心 `src/plugins/submitGuard.mjs`, 與 w-web-sso 同內容): 同 key 之流程(自觸發至結果訊息框關閉; 對話框含成功後關窗)進行中再觸發即略過, 被略過之觸發立即釋放其按鈕鎖. key: `saveGrups` / `savePemis` / `saveTargets` / `saveUsers` / `savePemiBlngGrups` / `saveGrupBlngUsers`. 兩對話框之 promise(`vo.pm`)與開關(`bShow`)行為不變: 成功才 resolve 並關窗, 失敗保持開啟可重按儲存.
3. **新增列標記**: 四清單頁 `addItem` / `copyItem` 設 transient `r._isNew = true` 並隨列送出; 後端檢查後由 `ltdtmapping` 依 schema 取欄時剝除, 不入庫.
4. **後端**: `updateTabItems` 以 ``lockSave(`updateTabItems:${keyTable}`, userId, …)``(`server/lockSave.mjs`, 與 w-web-sso 同內容; 占位鍵實為 `updateTabItems:{表名}:{操作者 id}`)包在 kmx 之外層: 同一操作者之同表寫入處理中再送出 → reject `saveInProgress`(不排隊: 排隊後再寫一次即上述覆寫); 不同操作者之並行仍由 kmx 序列化、各自成功(ADR-012 之契約保留). kmx 內 `select` 之後, 非 `pickKeysOnly` 模式時, 標 `_isNew` 之列 id 已存在 → reject `saveNewRowExists`(擋第 2 次於第 1 次完成後才到之依序重送; `modeEditUsers='for:grups'` 本不採納新增列, 不檢查). `cacheSt` 與 `lockSave` 建於 `server/WWebPerm.mjs`(`let kmx = pmKeyMutex()` 之後), 與 kmx 同樣注入 `procCore`. 兩個 key 於 `server/procLang.mjs` 加 eng + cht(文字同 w-web-sso); 錯誤 key 之 log 沿用 `updateXxx` 之集中 `errLog`(`event: 'updateXxx-error'`, `msg` 為 key).
5. **刻意不套**: `VeCgrups` / `VeCpemis` / `VeCrules` 之儲存(不打 API, 重複觸發只重複 resolve 同一 promise, 無作用; 其 handler 保留第一行解鎖並於註解說明); `syncAndReplaceTabs`(外部應用以 app 權杖同步之 HTTP 路由, 非按鈕入口; 依 `from` 全量取代為冪等, 同一應用可並行同步不同 `from` 分區, 以操作者占位會誤擋; kmx 照留); 編輯模式開關、欄位挑選、新增 / 複製 / 刪除列(前端表格編輯)、開啟對話框之原生按鈕(無副作用).
6. **單例之等待者一律了結**(2026-09-29 追加, 對應 w-web-sso 同日之 CheckYes / CheckYesNo 修正): 上述 7 個單例之 `show()` 開頭若 `vo.pm` 存在先了結再建新者——`CheckYes` `resolve()`(視同按確定)、`CheckYesNo` `reject('close')`(視同選否)、Ve* `reject('close window')`(視同關閉, 同各自 `clickClose`; 5 個呼叫端 `showVe*ById` 皆有 `.catch(() => {})`); 對已結束者無作用.

**Consequences**:

## ADR-026: 相依升版(w-serv-orm 1.1.10 / w-serv-hapi 1.1.6)之配合——資料通道只開 select、已移除設定 fail-fast、寫入前驗證、寫入失敗回語系鍵、測試輔助之完成判定 (2026-10-14)

**Status**: Accepted(主控複審裁示 D1–D8, 2026-10-14; D1 同日由「① 全放行已認證者」改採「② 只開 select」; 對應 w-web-sso ADR-080～083)

**Context**(行號為修改前之 git HEAD; 實測編號見主控交付 `run01-審計回應.md` 第六節):

- **已移除之設定**: w-serv-orm 1.1.9 移除 `useCheckUser` / `getUserById` / `useExcludeWhenNotAdmin`, 給值即由 `checkOptRemoved` 拋錯; 本套件仍讀取、包裝(ADR-023 第四個注入函數)並轉交.
- **先破壞後寫入**: 1.1.8 起 procOrm 對「會被 clearXSS 改寫之字串主鍵」整批拒絕、非主鍵欄位改寫後存入; 1.1.10 起 save/del 之逐筆失敗亦 reject; LMDB 主鍵上限 1978 位元組(既有). 本套件兩條寫入路徑——`updateTabItems`(del → insert → save, `server/procCore.mjs:170-192`)、`syncAndReplaceTabs`(delAll({from}) → insert, `server/WWebPerm.mjs:642-646`)——之拒絕發生在破壞步驟之後: 改標的路徑為含標記者該列遺失、刪＋增同批部分套用(V3); 外部同步該 from 之既有列全數清空(V4); 真瀏覽器重新進站後 22 → 21 筆(V7). 名稱、說明、email 之 `<` 後接字母被靜默改存為 `&lt;`.
- **原文外送**: 上述拒絕之英文原文原樣成為 kpFunExt 之 reject, 前端 `tErr`(`src/plugins/mUI.mjs:203-209`)查無語系鍵即顯示「無法連線至伺服器」; 外部應用收英文原文.
- **資料通道開放裸寫入**: `methodsExec: ['select','insert','save','del','delAll']`(`WWebPerm.mjs:1143`), 已認證者可直呼裸寫入, 繞過 kpFunExt 之 lockSave(ADR-025)、kmx(ADR-012)、寫入前驗證與整表 diff(ADR-009); 前端與測試皆只用 kpFunExt 寫入、同步只用 select(Grep `\$fapi\.` 8 處、`callRpc(` 皆 kpFunExt).
- **原型鍵**: ckKey 與前端 `errItemsBy*` 以 `{}`＋`haskey`(`in`)判重複, id／名稱為 `constructor`、`toString` 者被判重複而無法儲存(`procCore.mjs:114`).
- **測試輔助**: e2e `seedDb` 於子行程 exit 即 resolve(`test/tools/e2e-setup.mjs:96`), 1.1.10 之 genTestData 遇逐筆失敗拋錯而 `g_initialTestData` 以離開碼 0 結束 → 種子失敗被當成功(V5); `spawnSrv` 丟棄後端輸出, 後端啟動即崩潰時只見 60 秒 readiness 逾時; 7 檔 × 2 處取 base seed 之臨時瀏覽器無 try/finally, 基準遺留 15 個 Chrome 使 mocha 印出總結後不結束.

**Decision**:
1. **資料通道只開 select**(D1②): `methodsExec: ['select']`; `authorizeExec` 為 `server/dataChannel.mjs:createAuthorizeExec`——只對已取得 userId 之 select 回 `true`, 拒絕記 `srLog.error({ event: 'authorizeExec', msg: <key>, tableName, methodName })`(key: 取不到 userId → `cannotFindUserId`, 非 select → `userNoPermission`); 直呼裸寫入由 w-serv-webdata 回 `invalid func[表名.方法]`. 連線者身分之授權仍在 verifyConn(ADR-015). `operOrm` 經 `wrapOperOrm`: ORM 拒絕之原文只入 srLog(`operOrm-error`), 前端收 `anUnexpectedErrorOccurred`.
2. **已移除設定 fail-fast**(D2): 刪除讀取、包裝與轉交; `srLogInit` 之後以 `w-serv-orm/src/checkOptRemoved.mjs` 檢查(未給、null、false 通過), 記 `srLog.error({ event: 'WWebPerm-init-error', msg })` 後轉拋, 先於 WServOrm 建構(不開資料庫). WServOrm 不帶 opt(`g_mOrm.mjs`、`srv.mjs` 同). **與 w-web-sso ADR-083(忽略＋啟動警告)不同之理由**: 本套件過去把三鍵透傳給 w-serv-orm 且實際生效(含依使用者過濾 select 結果), 靜默忽略會無聲失去部署方以為仍在之可見範圍保證; sso 過去即已忽略三鍵, 其「忽略並警告」係延續自身歷史, 兩者不必一致. 資料通道之授權閘(verifyConn → getAndVerifyClientUser 加只開 select)已嚴於原 ORM 檢查, 部署方刪除三鍵即可, 無須替代設定.
3. **寫入前驗證**(D3, 任一字串欄位, 同 w-web-sso ADR-081 決策 1.3): `server/validateRows.mjs:validateRowsBeforeWrite(rows, { idRequired, rowsIdOnly })`, 單一職責之純函數: 主鍵有給須為字串或數字、UTF-8 ≤ 1978 位元組、與其他列不重複; 任一字串欄位 `clearXSS(v) !== v` 即拒(與 w-serv-orm `getMapOrm.mjs` 之 adjustData 同一函數、同一份 wsemi). 站點: `updateTabItems` 於 diff 之後、del 之前驗 add＋diff 列(same 列只參與主鍵重複; 未變更之舊資料不阻擋儲存)——標記 → `htmlMarkupNotAllowed`、重複 → `saveRowFieldDuplicate`、其餘 → `saveRowFieldInvalid`; `syncAndReplaceTabs` 於 delAll 之前驗全部列——標記 → `htmlMarkupNotAllowed`、其餘 → `invalidRows`.
4. **寫入失敗回語系鍵**(D4, 用語同 w-web-sso): 拒絕值為 procLang 鍵者原樣轉出, 其餘(ORM／I/O 原文、Error)記 srLog(`msg` 為鍵、`raw` 為原文)後改回 `saveWriteFail`(`server/procCore.mjs:toOutKey`, 四個 updateXxx 與 syncAndReplaceTabs 共用). 新鍵 `htmlMarkupNotAllowed`、`saveWriteFail`; `invalidRows` 文字改同 w-web-sso(原 `Invalid rows`／`資料列無效`).
5. **建構期錯誤記 srLog**(B-2): `new WServHapiServer` 包 try/catch, 記 `WServHapiServer-init-error` 後轉拋(w-serv-hapi 1.1.6 起設定錯誤於建構時同步拋出).
6. **行程層錯誤政策**(D5, 同 w-web-sso R-ERR-01): WWebPerm 與 srv.mjs 不註冊 process 之 unhandledRejection／uncaughtException 監聽(w-serv-hapi 1.1.6 起亦不代為註冊); fire-and-forget 站點於源頭 catch——盤點 `server/`、`srv.mjs` 之計時器、`.then`、未 await 之 promise 與 async 監聽, 唯一站點為 `server/staLogs/staLogsCore.callWorker.mjs` 之 `wk.terminate()`, 補 `.catch`; 種子與維運腳本之頂層 promise 皆 catch 並設 `process.exitCode = 1`.
7. **查表容器無原型**(C-1): `procCore` 之 ckKey、mergePickKeysOnly、`validateRowsBeforeWrite` 之 id 表, 與前端清單頁、關聯對話框中以使用者資料(標的 id、群組／權限／使用者名稱、email)為鍵之查表改 `Object.create(null)`(解析自使用者 JSON 者改以 hasOwnProperty 判斷).
8. **測試輔助**: `seedDb` 經 `test/tools/seedChild.mjs:runSeedChild`(見 `finish.` 才成功; 子行程結束而未見、逾時一律失敗並附輸出尾段); `spawnSrv` 保留輸出末 4 KB、子行程非因重啟／cleanup 而結束且離開碼非 0 時印出; 取 base seed 之臨時瀏覽器一律經 `captureBaseSeedOnce`(try/finally 關瀏覽器).

**Consequences**:
- ✅ 後端可啟動; 可預判之寫入失敗被拒時資料表零變更; 使用者看到可理解之原因(新案例 E2E-011).

## ADR-027: 打包後可用——staLogs worker 檔改為首次使用時解析, 頂層不宣告 __filename/__dirname (2026-10-14, X1; w-web-sso、w-web-api 同一作法)

**Status**: Accepted(主控 X1 指示 2026-10-14; 對應 w-syslog 審計之方案④, 證據見主控 `dnow/20261014041244/agent-out/run01-審計回應.md` §2.1、§2.4、§6–§7)

**Context**:
- `server/staLogs/staLogsCore.callWorker.mjs:8-11`(修改前)於模組頂層宣告 `let __filename = fileURLToPath(import.meta.url)`、`let __dirname = path.dirname(__filename)`, 並於**載入時**以 `path.resolve(__dirname, 'staLogsCore.shellWorker.mjs')` 算出 worker 路徑.
- 本套件之 `main`(`dist/w-web-perm.umd.js`)由 `toolg/gDistRollup.mjs`(w-package-tools rollupFile, format umd)打包: rollup 把 `import.meta.url` 換成 `require('url').pathToFileURL(__filename).href` 之墊片, 其避讓名單不含 `__filename`, 墊片綁到本模組(或同一 bundle 內任一模組)頂層宣告而被改名之 `__filename` → 載入即 `ReferenceError: Cannot access '<名>' before initialization`(TDZ). 2026-10-14 實測: 以 gDistRollup 同設定把修改前之本檔單獨打包, `require` 即 `Cannot access 'Tr' before initialization`.
- 改名後仍有第二層: 打包後 `__dirname` 為 bundle 所在之 `dist/`, 其下無 worker 檔, 第一次統計即找不到檔.
- 盤點(R-PKG-01): `server/`、`src/`、`srv.mjs`、`g_*.mjs` 以模組位置定位檔案者只有本檔; bundle 內之相依只有 w-syslog 1.0.32 同型(其 1.0.33 修正, 主控另行續接升版).

**Decision**:
1. 頂層不宣告 `__filename`/`__dirname`, 不於載入時以模組位置組路徑; 不用 `import.meta.dirname`/`filename`/`resolve`(umd 換成 `undefined`). `import.meta.url` 只在函數內使用(呼叫時才求值, 不涉 TDZ).
2. 新增 `server/staLogs/resolveShellWorker.mjs:resolveShellWorker({ fpSelf, cwd, pkgName, rel, existsSync, readFileSync, createRequire })`(單一職責, 依賴可注入): (a) 由 fpSelf 往上找**最近**之 `package.json`, name 為 `w-web-perm` 且其下 `server/staLogs/staLogsCore.shellWorker.mjs` 存在 → 採用(最近者名稱不符即不再往上, 不越界採用他套件旁之同名檔)——涵蓋 repo 內之 src 與 dist、已安裝之 src 與 dist; (b) `createRequire(fpSelf).resolve('w-web-perm/server/staLogs/staLogsCore.shellWorker.mjs')`——被下游再打包; (c) 同上以 `process.cwd()` 為基準——bundle 被搬離 node_modules 樹而由專案根執行; (d) 皆失敗拋 Error, 訊息含套件名、相對路徑與已試之位置.
3. `staLogsCore.callWorker.mjs` 之 `getShellWorkerPath()` 於首次 `runWorker` 時解析並以模組層變數快取成功結果(失敗不快取, 下次重試); `runWorker(param, fpWk)` 保留注入點, 未給時解析, 解析失敗以該 Error reject(不 spawn、不在載入時拋).
4. 前提: `.npmignore` 未排除 `server/`, 已安裝時 worker 檔存在(若改動須同步改 R-PKG-01).

## ADR-028: 數字主鍵以其字串形式處置, 外部同步拒絕屬其他來源之主鍵 (2026-10-14, 發布前升級輪; w-serv-orm 1.1.11)

4. **回應之 id 型別**(對外行為變更): `POST /syncAndReplaceTabs` 成功之 `msg`(procOrm insert 之回報)中, 數字主鍵之 id 由 `123` 變為 `'123'`; `server/provideTabs.mjs` resolve 之值亦同. 1.1.10 時之 `123` 與庫內實存者(隨機主鍵)不符, 屬更正. README〈Upgrade Notes〉記之.
5. 不採納: 建議書 3.5-4(把 `test/tools/unitOrm.mjs` 之替身改為非字串主鍵即以產生之主鍵寫入)——1.1.11 起經 procOrm 之寫入已先轉字串, 替身不再收到數字主鍵; 測試中直呼 `woItems` 者一律用字串主鍵.

## ADR-029: 迭代使用端傳入之物件一律依自有鍵(R-OBJ-ITER-01), 整表寫入之 rows 非陣列即拒絕(R-ORM-05) (2026-10-20, 主控第 85 項; 來源 wsemi 第 62 項審計附帶發現 F2)

**Status**: Accepted(主控指派第 85 項, 建議書 `建議w-web-perm修正.md`; 主責 agent 實測後修正建議書之範圍, 見 Context; 外審結果見主控修正報告)

**Context**:
- 建議書指 `server/validateRows.mjs:96` 以 lodash `each` 走訪列物件, 列含數字 `length` 欄位時字串欄位漏檢. **函數層屬實**(HEAD `434c0d4` 實測: `length:0`、`1`、`2**32-1` 皆回 `null`; `2**32-1` 單次耗時 79 秒).
- **但 HTTP／RPC 路徑上不可達**: `updateTabItems` 與 `syncAndReplaceTabs` 皆於呼叫 `validateRowsBeforeWrite` 之前以 `ltdtmapping(rows, ds[keyTable].keys)` 依 schema 欄位重建列, 四表 schema 皆無 `length` 欄, `length` 到不了 `validateRows`(真後端實測兩條路徑皆已回 `htmlMarkupNotAllowed`). 故建議書所述「標記驗證被略過」屬縱深防禦缺陷, 非現行可觸發之漏檢.
- 同型缺陷真正可達處在**容器層與權限評估**: ①`procCore.updateTabItems`／`mergePickKeysOnly` 對未驗型之客戶端 `rows` 以 lodash `each` 走訪——`rows = { length: N }` 使 `each` 迭代 N 次(`2**32-1` 約 80 秒阻塞事件迴圈), 且非陣列 `rows` 經 `ltdtmapping` 變 `[]`, 被 `ltdtDiffByKey` 視為「全部刪除」而**整表清空並回成功**(真後端實測 `updateTargets` 送 `{ length: 2e7 }`: targets 22 → 0, 回 `saveTabItemsSuccess`); ②`src/plugins/mShare.mjs` 之 `getUserRules` 走訪使用者(含外部應用)寫入再經 JSON5 解析之 `cgrups／cpemis／crules`(伺服端每次 getPerm／getPermUserInfor 皆走): `{"length":0,"M1":…}` 使群組／權限／規則被略過而評估為無權限; `{"length":4294967295}` 使查詢空轉或耗盡記憶體(子行程 128 MB 堆積實測 1 秒內崩潰, exit 134)——寫入一次即持久影響該使用者每次權限查詢.
- 前端 5 個清單元件亦以 lodash `each` 走訪同一批 JSON5 解析物件(瀏覽器端), 異常內容之資料使管理介面分頁空轉或略過鍵.

**Decision**:
1. **共用走訪函數** `src/js/eachOwn.mjs`: 真陣列(`Array.isArray`)索引迴圈、一般物件 `Object.keys`、其餘不迭代; callback 回 `false` 跳出, 同 lodash `each`. 對無 `length` 鍵之物件與真陣列與 lodash `each` 逐項等價(`unit-eachOwn` EO-004).
2. `server/validateRows.mjs`: 四處走訪全改 `eachOwn`; `rows`／`rowsIdOnly` 以 `Array.isArray` 判真陣列(偽稱 Array 之物件 → `rowsInvalid`／視為未給).
3. `server/procCore.mjs`: `updateTabItems` 入口(進 `lockSave` 之前)`!Array.isArray(rows) || !rows.every(isRowObj)` → reject `saveRowFieldInvalid`(R-ORM-05; `isRowObj`＝非 null、非陣列、至少一個自有可列舉鍵之物件; 空陣列仍合法); `mergePickKeysOnly` 非陣列 `rowsIn` 視同未送入任何列. 外審(sol／minimax)另發現單元素陣列其元素為空值(`[null]`、`[{}]`、`['']`、`[[]]`)時 wsemi `isearr` 使 `ltdtmapping` 回 `[]`、同樣整表清空並回成功, 故守門含「各列須為非空物件」.
4. `src/plugins/mShare.mjs` `getUserRules`: `cvKpToArr`、`objOR`、`objAND`、`rulesFin` 四站改 `eachOwn`.
5. 前端 11 站(`LayoutContentGrups`／`LayoutContentPemis`／`LayoutContentUsers`／`VeGrupBlngUsers`／`VePemiBlngGrups`)改 `eachOwn`, 僅換走訪函數、不動版面與互動.
6. 站點不變式 `unit-eachOwn` SITE-OI-001／002 守護: 已套站點不復用 lodash, `server`／`src` 內不得新增 `each(kp…)` 類走訪(允許清單逐「檔案::變數」).

**Consequences**:
- ✅ 列物件、rows 容器、權限評估與前端解析不再因 `length` 鍵略過真實鍵或依 `length` 迭代; 成本只依實際鍵數.
- ⚠️ **行為變更**: `updateTargets／Pemis／Grups／Users` 之 `rows` 非陣列(字串、數字、null、undefined、一般物件、帶 `length` 之物件)或含非物件／空物件之列(`[null]`、`[{}]`…)由「整表清空並回成功」改為「回 `saveRowFieldInvalid`、資料不變」; `modeEditUsers='for:grups'` 模式原將非陣列 `rows` 視為無送入列(資料不變且回成功), 現亦拒絕. 官方前端與既有測試皆只送陣列; 自寫客戶端若依賴「送非陣列即清空」須改送 `[]`. 外部同步 `syncAndReplaceTabs` 之守門(`isearr`, 拒空陣列與單元素空值)與後台**語意不同而非對稱**, 兩者用途不同(防誤清源 vs 允許清空).
- ⚠️ `getUserRules`: `cgrups／cpemis／crules` 解析結果為字串時, 原依 lodash 逐字元迭代(名稱為索引、`isActive` 為單字元), 現不迭代(無群組／權限／規則); 此為資料損壞情形, 無實用語意.
