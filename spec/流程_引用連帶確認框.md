# 引用連帶確認框流程

## 觸發

管理員（瀏覽器使用者，經 w-ui-loginout 登入取得有效 token、`connState='csLogin'`）進入後台後，於 `LayoutContent.vue` 左側導覽點「管理權限群組」（`mmGrups`）、「管理權限」（`mmPemis`）、「管理對象」（`mmTargets`）進入對應之清單頁（`LayoutContentGrups.vue`、`LayoutContentPemis.vue`、`LayoutContentTargets.vue`）。本文件涵蓋「被引用表」之刪除、改名、新增動作在**儲存前**彈出之確認框與被拒訊息框之使用者可觀察行為：群組（被使用者 `cgrups` 引用）、權限（被群組 `cpemis` 引用）、標的（被權限 `crules` 引用）。屬編輯類流程；各頁之進入與預設狀態（編輯模式開、無列被勾選、無儲存鈕）同 `流程_後台群組清單.md`、`流程_後台權限清單.md`、`流程_後台標的清單.md`。

規則來源：引用連帶（刪除連帶清理引用、改名級聯，ADR-036、`sgud/rule/rulebook.md` R-REF-CASCADE-01）與「新增撞懸空名」確認（F-23 原則 7，`src/js/getAddImpact.mjs`，`spec/設計要點與取捨.md` ADR-037）。刪除或改名被引用之群組／權限時，引用端之授權字串於同一次寫入內被連帶清理或改名；新增一個與「仍被啟用中之引用指向、卻查無實體」之名稱（懸空名）相同之群組／權限／標的時，該引用即解到新實體而使引用端取得或受其限制，故須明確同意。

與既有案例之關係：同型情境在 `流程_後台群組清單.md` E2E-005／014／015／016／017、`流程_後台權限清單.md`、`流程_後台標的清單.md` 與 `test/e2e-array-form.test.mjs`（AF-026／027／036～042）已有語意斷言，但**確認框與被拒訊息框未入標準圖**（見各 spec〈已知落差〉「確認框與引用連帶案例之標準圖未產製」）；本檔以全新夾具另立 flow `ref-cascade`，補確認框入圖（主控授權為新案例產標準圖）並補「新增撞懸空名」案例（既有 e2e 無）。既有案例與既有標準圖一概不動。

## 重要流程

- **E2E-001**
  - title: 刪除被引用的群組須先確認並可取消
  - description: 管理員在群組清單頁的編輯模式下，勾選一個正被使用者引用的群組，點「刪除勾選權限群組」，畫面先跳出確認框，說明將自幾位使用者移除對所選群組的引用，若其中有使用者以 AND 引用，還會說明這些使用者的限制解除後授權可能變多。點「取消」，群組仍在清單中，也不會出現儲存鈕；再次刪除並點「確定」，該群組才從清單移除並出現儲存鈕，此時資料庫尚未變動，再點「儲存變更」才真正寫入，成功時出現「儲存權限群組數據成功」。儲存時引用這個群組的使用者，包括由外部來源同步的使用者，其「管控使用權限群組」會同時移除該群組，授權依移除後的設定重新計算。便於刪除前得知有多少使用者受影響。
  - flow:
    - 測試資料：base seed 四表；案例前置（非使用者操作）：以管理者寫入 RPC 新增後台群組 `rc-del-g`（id `id-rc-delg`，`cpemis` 為 權限P3 之 OR）與後台使用者 `rc-del-uo`（id `id-rc-uo`，`cgrups` 為 權限群組M1 之 OR 加 `rc-del-g` 之 OR）；再經外部同步端點推入外部使用者 `rc-del-ua`（id `id-rc-ua`，`from` 為 `appRefCascade`，`cgrups` 為 權限群組M1 之 OR 加 `rc-del-g` 之 AND）。登入身分為管理員 token `sys`。

      1. 語意：刪除前以 `getPermUserInfor` 查得 `rc-del-uo` 之授權樹為 M1 ∪ P3＝`專案A/頁A/區塊A`、`專案A/頁C`、`專案B/頁A/區塊A`、`專案B/頁A/區塊B`、`專案B/頁A/區塊C`，`rc-del-ua` 為 M1 ∩ P3＝`專案A/頁C`、`專案B/頁A/區塊B`（預期值由 base seed 規則集依 `R-AUTH-MERGE-00` 推導）。
      2. 語意：點刪除後出現確認框（單一框；標題 `systemMessage`、按鈕 `no`／`yes`），訊息逐字為 `confirmDelRefsAndGrup` 代入 `{n}`＝2、`{m}`＝1（eng：`The reference to the selected group(s) will be removed from 2 user(s). For the 1 user(s) that refer to it with AND, the restriction will be lifted and their authorization may increase. - **E2E-004**
  - title: 權限改名撞懸空名稱時儲存被拒
  - description: 管理員在權限清單頁把某個權限改名，新名稱與一個正被群組啟用引用、卻在權限清單中找不到的名稱相同，也就是引用中的懸空名稱，系統為避免改名後的權限被這些引用接管，會整次拒絕儲存。畫面不會跳出確認框，而是直接出現失敗訊息，內容為「儲存權限數據失敗」接拒絕原因，說明新名稱仍被已不存在之項目的授權設定引用、資料未變更，並建議先清理懸空引用或改用其他名稱。關閉訊息後資料庫完全不變，清單仍保留已改的名稱與儲存鈕，可修正後再存。
  - flow:
    - 測試資料：base seed 四表；案例前置（非使用者操作）：經外部同步端點推入外部群組 `rc-dang-g`（id `id-rc-dg`，`from` 為 `appRefCascade`，`cpemis` 為 權限P1 之 OR 加不存在之 `rc-ghost-p` 之 AND）。被改名之權限取 base seed 之 權限P4。登入身分為管理員 token `sys`。
    - 操作：登入後台 → 點「管理權限」頁籤 → 雙擊 權限P4 名稱儲存格改為 `rc-ghost-p`（Enter）→ 點「儲存變更」→ 失敗訊息框點「確認」。

      1. 語意：改名後清單頁出現儲存鈕；點儲存後不點任何按鈕即出現失敗結果框（單一訊息加確認鈕，不是否／是之確認框），訊息逐字為 `pemiSavePemisFail` 之文字接「: 」再接 `renameCascadeNameInUse` 之文字（eng：`Failed to save permissions: Not saved: a new name is still referenced by settings of items that no longer exist, so the renamed item would take over those references. ## 規則摘要

- **權限**：本檔案例皆為管理員（token `sys`）之畫面軸行為，寫入經 `verifyConn` → `checkToken` → `getAndVerifyClientUser` 守門（同 `流程_後台群組清單.md`）。
- **確認框次序**：群組／權限頁儲存時依序為改名預覽確認、新增確認、開 loading、送出；各自只在需要時彈出，單一框、單一問句；任一選「否」中止儲存（不送出、不開 loading，編輯與儲存鈕保留）。標的頁為刪除或改 id 之儲存前確認。
- **刪除**：群組／權限刪除被引用者先確認，只自清單移除，儲存時於同一次寫入內連帶清理引用端（`R-REF-CASCADE-01`）；無引用者直接移除不彈框。標的頁刪除不彈框，儲存時確認。
- **改名**：同 id 異名為改名（`opt.cascadeRename` 預設 `true` 時級聯改寫引用端）；新名為「仍被啟用中引用而查無實體」之懸空名時整次拒存（`renameCascadeNameInUse`，預覽不彈框、由伺服端預檢拒絕）。
- **新增撞懸空名**：允許，但須明確同意；`{n}` 為受影響引用端數、`{m}` 為其中以 AND 引用者（標的恆 0）。
- **標準圖通則**：新 flow `ref-cascade`，檔名 `ref-cascade-<lang>-E2E-NNN-<序>-<kebab>.png`，放 `test/pics/ref-cascade/`；每個操作步驟兩張（點擊前框住要點、點擊後框住有反應之元素）；一圖一框；彈窗框整個面板（含標題、訊息、按鈕）；不為成功訊息框產圖（主控指示，避免與既有成功框之圖混淆）；純語意案例（E2E-002、007、008）不設標準圖。標準圖共 5 案、每語系 10 張（E2E-001、003、004、005、006 各兩張），2026-10-22 run07 N2 產製並逐張目視審畢（框住對象與本檔視覺項一致、兩語系對稱）。
- **測試環境呈現**：無。
