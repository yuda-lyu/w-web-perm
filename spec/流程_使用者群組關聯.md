# 使用者群組關聯流程

## 觸發

管理員（瀏覽器使用者，經 w-ui-loginout 登入取得有效 token、`connState='csLogin'`）於後台後可由兩個入口進入同一份 `users.cgrups`（JSON5 格式 `{群組名:{mode:'OR'|'AND',isActive:'y'|'n'}}`）的編輯，差別在進入視角與儲存路徑：

- **入口 A（使用者視角）**：於使用者清單頁（`LayoutContentUsers.vue`）某列 `cgrups` 欄的按鈕，點擊觸發 `$dg.showVeCgrupsById(id)`（`LayoutContentUsers.vue` 之 `cgrups` 欄 cell-render 按鈕），開啟群組關聯編輯對話框 `VeCgrups`。此對話框以「該使用者擁有哪些群組」為列，逐群組可勾選啟用、切 OR/AND 合併模式。對話框 Save 後僅 `resolve` 一個 `cgrups` JSON 字串回填至該使用者列（`LayoutContentUsers.vue:showVeCgrupsById`），**不自行打 API**；實際寫入 DB 由使用者清單頁的 Save 統一送出。
- **入口 B（群組視角）**：於群組清單頁（`LayoutContentGrups.vue`）某列 `belongUsers` 欄的按鈕，點擊觸發 `$dg.showVeGrupBlngUsersById(id)`（`LayoutContentGrups.vue` 之 `belongUsers` 欄 cell-render 按鈕），開啟群組成員編輯對話框 `VeGrupBlngUsers`。此對話框以「全部使用者」為列，欄位依序為「使用者名稱、是否使用、所屬權限群組名稱」（本列自己可改的在左、由其他群組帶來的在右）；勾選「是否使用」即把該使用者歸入本群組，合併模式不另設欄，而是併入右欄代表本群組的那顆標籤（`VeGrupBlngUsers.vue` template 之 `RelationChips`），點該標籤左段即展開 OR / AND 清單。對話框 Save 後於對話框內**自行**重組各 user 的 `cgrups` 並 `$fapi.updateUsers` 直接寫入 DB（`VeGrupBlngUsers.vue:saveUsers`）。

兩入口寫入端點同為 `updateUsers`，經 hapi `verifyConn` 刪 Bearer 取 token → `checkToken(token, apiType)` → `getAndVerifyClientUser` 守門（`server/WWebPerm.mjs:verifyConn`、`p.checkToken`、`getAndVerifyClientUser`）：token 須可由部署方 `getUserByToken` 解出使用者、該使用者須存在於 perm `users` 表且 `isActive='y'`（`server/WWebPerm.mjs:getTokenUser`）、並通過部署方 `verifyClientUser(user, from)`（資料通道之 from 為 apiType，如 `main`），**任一不符即拒絕連線**（ADR-015，2026-09-29 業主裁示資料通道採嚴格預設）；是否限定管理員由 `verifyClientUser` 決定（開發樣本限 `isAdmin='y'`，`srv.mjs`）。

## 重要流程

- **E2E-001**
  - title: 管理員自使用者列 cgrups 按鈕開啟群組關聯對話框
  - description: 管理員在使用者清單頁開啟編輯模式後，點某列「管控使用權限群組」欄的按鈕，畫面開啟「編輯使用權限群組」對話框，逐列列出全部權限群組，每列有群組名稱、「合併權限群組模式」控制項與「是否使用」勾選框，模式控制項顯示 OR 或 AND 且點開可選；該使用者既有的群組設定會回填為對應列的勾選與模式，未勾選的列其模式控制項呈淡色不可點。適合檢視並調整某位使用者擁有哪些權限群組。
  - flow:
    - 測試資料：base seed users（含一筆已設定數個群組的 user 作為 cgrups 來源）；不另建特化資料。
    - 操作：登入後台 → 點「使用者」頁籤 → 開啟編輯模式 → 點某列 `cgrups` 欄按鈕。

- **E2E-002**

## 執行流程

兩入口共用同一份 `users.cgrups`，但儲存路徑分流：入口 A 對話框 Save 僅 `resolve` 一個 `cgrups` 字串回填前端列、**不打 API**（實際寫 DB 待使用者清單頁 Save）；入口 B 對話框 Save 於對話框內**自行** `$fapi.updateUsers` 直接寫 DB。以下分兩條 trace。

位置標註為符號錨 `[檔名:符號]`（函式名；2026-10-21 起取代行號，行號會隨改版漂移）；步驟編號於同日重排。入口 A／B 之寫入 `cgrups` 前皆經 `cvKpToObj`（解碼）、`getKpLossy`（無法無損表示之判定，2026-10-21 起為「同名同時為有效 OR 與 AND」「啟用而名稱非字串之項目」「該層啟用項皆 mode 缺漏或不合法」三格，ADR-033、ADR-035）與拒存分支（`authLossyBlocked`，ADR-030／031）。授權合併與項目之儲存順序、物件鍵序、陣列元素序無關（`R-AUTH-MERGE-00` 第 4 條，ADR-033），故編輯器不再保留原鍵序（`keepKeyOrder`）、不再判定鍵序易位（`getKpWriteLost`、`getKeyOrderLost`），三者及其拒存分支已於 2026-10-21 刪除，步驟編號於同日再次重排（入口 A 由 046 步縮為 044 步、入口 B 由 057 步縮為 055 步）；見各路徑對應步驟。

## spec 規則摘要

- **權限**：兩入口寫入皆經 `updateUsers` → `verifyConn` → `checkToken` → `getAndVerifyClientUser` 守門（token 須有效、其使用者須在 perm `users` 表且 `isActive='y'`、並通過部署方 `verifyClientUser` 才可寫；ADR-015 嚴格預設）；是否限管理員由 `verifyClientUser` 決定（開發樣本限 `isAdmin='y'`）。
  - 修改留痕（2026-09-29）：原載「經 `checkToken` 守門（有效 token 才可寫）」並引 `WWebPerm.mjs` 之舊行號——行號已漂移（2026-10-21 起本 spec 全面改用符號錨），且未載 perm `users` 表／`isActive` 要求；ADR-015 業主裁示資料通道維持嚴格預設後，依現行碼（`WWebPerm.mjs:p.checkToken` → `getAndVerifyClientUser`）改寫本段、觸發段與執行流程之守門行。
- **同源異視角**：入口 A（使用者頁 `cgrups` 按鈕 → `VeCgrups`）與入口 B（群組頁 `belongUsers` 按鈕 → `VeGrupBlngUsers`）編輯同一份 `users.cgrups`（JSON5 `{群組名:{mode:'OR'|'AND',isActive:'y'|'n'}}`），差別在「以群組為列 vs 以使用者為列」。
- **儲存路徑差異（核心）**：
  - 入口 A 對話框 Save 僅 `vo.pm.resolve(cgrups)` 回傳字串、回填前端使用者列並設 `isModified=true`，**不自行打 API**；實際寫 DB 由使用者清單頁的 Save 統一以 diff 批次送出。
  - 入口 B 對話框 Save 於 `core()` 內重組各受影響 user 的 `cgrups`、`await saveUsers` → `$fapi.updateUsers` **直接寫 DB**，並於對話框內呈現 `userSaveUsersSuccess` / `userSaveUsersFail`。
- **粒度**：入口 A 無 Save 成敗訊息（成敗由使用者清單頁呈現），僅開啟 / 切換守門訊息；入口 B 有 `userSaveUsersEmpty` / `userSaveUsersSuccess` / `userSaveUsersFail` 操作結果（皆走 `showCheckYes` DOM 模態）。
- **邊界**：
  - 入口 B（`VeGrupBlngUsers`）重組後之 `cgrups` 只記錄 `isActive==='y'`（啟用）的群組：取消勾選（enable=n）即自重組後的 `cgrups` 移除該群組鍵（`VeGrupBlngUsers.vue:revRows`、`VeGrupBlngUsers.vue:doSave`）；入口 A（`VeCgrups`）則逐列寫出 `{ mode, isActive: enable }`，enable 為 `'n'` 之列仍寫為 `isActive:'n'`，不略過（`VeCgrups.vue:doSave`）。
  - `mode` 僅接受 `OR` / `AND`，回填時非此二值一律補 `OR`。
  - 入口 B 以 `fltKpGrup` 過濾使用者 `cgrups` 內已不存在於現行 `grups` 的群組鍵，避免過時鍵殘留（`VeGrupBlngUsers.vue:fltKpGrup`）。
  - 後端對 `users` 之 `email` 檢查（空值、重複）自 2026-10-21 run05（ADR-035 決定 h）起**只擋本次寫入造成或觸及者**，歷史既有之空值或重複原樣送回不拒；`mappingBy` 為 `'name'` 時另對 active 列之 `name` 檢查非空與唯一（同樣只擋本次造成或觸及者），其餘情形不檢查 `name`（`procCore.mjs:updateTabItems`）。原載「`email` 不可空 / 不可重複，由 `ckKey('email')` 對**全表**守門」自此不成立。本流程不改 email 與 name，入口 B 寫入時隨列一併送出，歷史髒列不再使本流程之存檔失敗。
- **容錯與列身分配對（入口 B，ADR-032）**：①`genItems`／`revRows`／`doSave` 對每位使用者之 `cgrups` 解碼失敗（空字串即後台新增使用者之預設值、壞 JSON）一律視為空容器，不使對話框打不開、不使存檔拋例外（R-REL-PARSE-01）；壞 JSON 列之本群組歸屬未變時其字串逐字不動；②對話框之列帶使用者 `id`，`revRows` 與 `doSave` 一律以 `id`（不以列索引）配對 store 中之使用者（`pairRowsToSnapshot.mjs:pairRowsToSnapshot`），開框後他人重排 `order` 或增刪其他使用者不影響配對；對話框之某列所對應的使用者已被刪除 → 整次拒存並顯示 `relationRowsStale`（R-REL-PAIR-01）。
- **授權不變與合併規則（`R-AUTH-MERGE-00`，ADR-033，2026-10-21）**：伺服端合併結果與 `cgrups` 之鍵序、陣列元素序無關（先對全部 OR 項聯集、再與全部 AND 項交集，未列之管理對象視同 `n`），故兩入口存檔皆不保留原鍵序、也不判定鍵序易位；拒存為「原字串（陣列形式）含同名同時為有效 OR 與 AND」一格（物件形式一個名稱只有一個 `mode`，無法無損表示），另自 2026-10-21 run05（ADR-035 決定 f）起增「啟用而名稱非字串之項目」一格（E2E-013），同日主控裁決（限制項）再增「該層啟用項皆 mode 缺漏或不合法」一格（`getKpLossy` 第三格，陣列與物件形式皆然；E2E-016），入口 A 增「群組表同名多列設定不一致」一格（E2E-014，與有損判定無關、由對話框之列判定）：入口 A 列內容有任何變更即拒存、入口 B 有損使用者列之本群組歸屬或模式有變更即整次拒存。兩入口皆為兩態（勾／不勾）：未勾選之群組在入口 A 寫為 `isActive:'n'`、在入口 B 不寫入，該項不參與合併，與原本未列等價。原載「兩個以上 AND 群組時合併依鍵序、存檔須保序、整數式名稱 AND 易位須拒存」自 2026-10-21 起不成立。
- **遇衝突或歧義一律收嚴並於引用處提示（ADR-035，2026-10-21 run05，使用者原則「收嚴＋增加提示」）**：伺服端對引用查無（懸空）者以其模式參與、內容全 `n`（AND 使授權為空），對同名多筆取交集，對模式缺或非法者為限制項（只當 AND 的交集項、不單獨當基底，該層無任何合法 mode 之啟用項則結果全 `n`；`流程_權限規則合併計算.md` E2E-017～019）；編輯器同步：①存檔**不丟棄啟用中的引用**——懸空引用以額外列保留（可改為停用，E2E-011）、名稱 `''` 原樣寫出、模式缺或非法之啟用項顯示並存為 AND（E2E-012）；②**無法保留者拒存**——啟用而名稱非字串之項目（E2E-013）、該層啟用項皆 mode 缺漏或不合法（E2E-016）、群組表同名多列設定不一致（E2E-014）；③入口 B 改寫另一實體之字串時只動本群組一項，其餘引用原樣保留（E2E-015）；④有衝突之引用於名稱儲存格（入口 A）、「所屬權限群組名稱」儲存格（入口 B）、使用者清單頁 `cgrups` 欄左側顯示警告圖示，tooltip 見〈i18n 訊息粒度規則〉；**無衝突之資料列畫面與修改前逐像素相同**（既有標準圖不變）。
- **契約**：入口 A（VeCgrups）之 `clickSave` 不打 API，第一行 `pm.resolve()` 後 fire-and-forget `doSave`（刻意不套 runSubmit）；入口 B（VeGrupBlngUsers）之 `clickSave` 把按鈕鎖 `msg.pm` 交給 `doSave`、不於 handler 解鎖，`doSave` 以 `$ui.runSubmit('saveGrupBlngUsers', …)` 包覆 `core() + .then/.catch/.finally`；`finally` 一處關 loading；入口 B `updateUsers` 失敗由 `okSave` 旗標短路後續、走 `userSaveUsersFail`。對話框 Close 一律 `pm.reject('close window')`，由各入口 `.catch` 接住。（修改留痕 2026-09-29：原載兩入口皆「第一行 `pm.resolve()` 後 fire-and-forget」，入口 B 已由 ADR-025 改寫。）
- **送出入口與連按**（ADR-025）：兩對話框之 Save 為 WDialog 內建鈕（promiseUnlock），全頁 loading 與訊息框（WDialog）只擋滑鼠、不搶焦點；入口 B 之按鈕鎖涵蓋請求期間，流程狀態涵蓋至結果訊息框關閉，期間再觸發即略過；後端同一操作者並行寫 `users` 之第 2 次回 `saveInProgress`。對話框為單例：開啟中再次 `show()`（如焦點留在開啟鈕時按 Enter）時，舊階段之等待者視同關閉（`reject('close window')`，同按 Close），不再永久懸置。
