# 後台標的清單流程

## 觸發

管理員（瀏覽器使用者，經 w-ui-loginout 登入取得有效 token、連線守門通過）進入後台後，於左側導覽點「管理對象」（`mmTargets`）進入標的清單頁（`LayoutContentTargets.vue`）。此頁以 ag-grid（`WAggridVue`）列出 `targets` 表，提供：編輯模式切換、顯示欄位挑選、新增 / 複製 / 刪除 / 儲存。`targets` 的主鍵 `id` 為**路徑式字串**（如「專案A/頁A/區塊A」），於編輯模式可就地編輯，並作為列首固定欄與勾選 / 拖曳欄。

寫入端點 `updateTargets` 經 hapi `verifyConn` → `checkToken(token, apiType)` → `getAndVerifyClientUser` 守門（`server/WWebPerm.mjs`：`verifyConn`、`p.checkToken`、`getAndVerifyClientUser`）：token 須可由部署方 `getUserByToken` 解出使用者、該使用者須存在於 perm `users` 表且 `isActive='y'`（`getTokenUser`）、並通過部署方 `verifyClientUser(user, from)`（資料通道之 from 為 apiType，如 `main`），**任一不符即拒絕連線**（ADR-015，2026-09-29 業主裁示資料通道採嚴格預設）；是否限定管理員由 `verifyClientUser` 決定。

  - title: 管理員勾選刪除標的列並儲存成功
  - description: 管理員在標的清單頁的編輯模式下，勾選一個標的列後點工具列的「刪除勾選對象」，該列先自清單移除，此時資料庫尚未變動；再點工具列的儲存鈕時，若所選標的正被某些權限的規則引用，畫面會先跳出確認框，說明將自幾個權限的規則移除對該管控對象的設定，並列出被刪除的標的。點「確定」才真正寫入並出現訊息「儲存對象數據成功」；點「取消」則不送出，清單仍保留已刪除的狀態與儲存鈕。寫入時，引用該標的的權限規則中對它的設定會一併移除，使用者的授權不再包含已刪除的標的。例如刪除種子資料的第一個標的「專案A/頁A/區塊A」，它被權限「權限P1」引用。適合在整理不再使用的管控對象時使用。

## 執行流程

主要寫入路徑為 `saveTargets`（其餘 `addItem` / `copyItem` / `deleteItemsCheck` 僅變更 `opt.rows` 並設 `isModified=true`，不即時打 API，皆於 Save 時統一以 diff 批次送出）。`saveTargets` 為按鈕 handler（WButtonCircle `:promiseUnlock="true"`），把按鈕鎖 `msg.pm` 交給 `doSaveTargets`、不於 handler 解鎖；`doSaveTargets` 以 `$ui.runSubmit('saveTargets', …)` 包覆 `core()`，流程自觸發至結果訊息框關閉，期間再觸發（滑鼠或焦點在 Save 鈕時之鍵盤 Enter）即略過；按鈕鎖於請求結束（`updateLoading(false)`）或早退訊息框開啟前釋放（ADR-025）。

## spec 規則摘要

- **權限**：所有 `updateTargets` 寫入經 `verifyConn` → `checkToken` → `getAndVerifyClientUser` 守門（token 須有效、其使用者須在 perm `users` 表且 `isActive='y'`、並通過部署方 `verifyClientUser` 才可寫；ADR-015 嚴格預設）；是否限管理員由 `verifyClientUser` 決定。
  - 修改留痕（2026-09-29）：原載「經 `checkToken` 守門（有效 token 才可寫）」並以行號引用 `WWebPerm.mjs`——行號已漂移，且未載 perm `users` 表／`isActive` 要求；ADR-015 業主裁示資料通道維持嚴格預設後，依現行碼（`WWebPerm.mjs` 之 `p.checkToken` → `getAndVerifyClientUser`）改寫本段、觸發段、執行流程與資料來源表之守門行。
- **粒度**：id 錯誤走 cell 警告 icon + tooltip（具體 2 種，視覺提示）；操作主要結果（成功 / 失敗 / 空）一律 `$dg.showCheckYes` 持久 modal（System message 對話框 + OK 鈕，對齊全域 §5.1 禁原生 alert），非預期例外走 `$alert` toast 低調呈現；id 空 / 重複由前端 `isError`（`errItemsById`）於存檔前彙整為 `errInIds` 攔截、不送後端，後端 `ckKey('id')` 為繞過前端時的縱深防禦；token 失效等後端 reject 才聚合為 `targetSaveTargetsFail`。
- **邊界**：
  - `targets` 主鍵 `id` 為**路徑式字串**（階層以「/」分隔），**不可空 / 不可重複**（後端 `ckKey('id')` 守門，`procCore.mjs:updateTabItems`），且為 `ltdtDiffByKey` 的 diff key——改寫 id 等同 del 舊列 + add 新列。
  - CRUD 為「單頁多動作 + 批次儲存」模型：`addItem` / `copyItem` / `deleteItemsCheck` 及就地編輯只改 `opt.rows` 並設 `isModified=true`，**不即時打 API**；一律 Save 才以 `ltdtDiffByKey` 批次 del / insert / save 送出。
  - 稽核欄位（`userId` / `time*`）前端填 `{待自動給予}` 佔位符，後端 `procOrm` 補實值。
  - 本頁無關聯入口按鈕；id / description / from 為可就地編輯欄，其餘欄唯讀。
  - loading 於 `core()` 內、在 `isError` / rows 空兩同步檢查**之後**才開啟（`LayoutContentTargets.vue` 之 `doSaveTargets`）；早退分支不開 loading，符合全域 §5.1 canonical（`updateLoading` 應在同步檢查後）。
- **引用連帶（2026-10-22 run06，ADR-036、規則帳本 R-REF-CASCADE-01）**：標的被刪除或改 id 時，引用它之 `pemis.crules` 項目（不論 `'y'` 或 `'n'`）於同一次寫入內被連帶清理。標的 id 即名稱，改 id 對伺服端等同刪舊增新，**不級聯**（標的 id 改名之級聯為後續階段）；新 id 不繼承舊 id 之引用，刪除後以同名重建者亦不繼承（原則 6）。儲存前若有權限之規則將被清理，前端先彈確認框（`confirmSaveDelRefsTarget`，列出權限數與被刪除或改 id 之舊 id；E2E-005、E2E-011、E2E-012），按「取消」不送出、資料與儲存鈕保留；無權限引用者不彈框（E2E-013）；成功訊息維持 `targetSaveTargetsSuccess`（被清理之權限數已於確認框告知）。引用端先寫、主體後寫，任一步失敗以寫入前原值補償還原；寫入前驗證（ADR-026）先於引用連帶之預檢與寫入，被拒時引用端零變更（E2E-011）。取鎖階層 targets、pemis、grups、users。外部同步（同一 `from` 內依穩定 id）同樣適用，見 `流程_外部應用同步權限資料.md`〈同步之引用連帶〉。
- **契約**：`saveTargets` 為按鈕 handler，把 `msg.pm` 交給 `doSaveTargets`、不於 handler 解鎖；`doSaveTargets` 以 `$ui.runSubmit('saveTargets', …)` 包覆 `core() + .catch + .finally`，`finally` 一處關 loading；`updateTargets` 失敗由其 inline `.catch` 顯示失敗提示，並以 `okSave` 旗標 `if (!okSave) return` 短路後續。（修改留痕 2026-09-29：原載「第一行 `msg.pm.resolve()` 釋放視覺鎖後 fire-and-forget」，已由 ADR-025 改寫。）
- **送出入口與連按**（ADR-025）：入口只有 Save 鈕（WButtonCircle，滑鼠與焦點在鈕上之鍵盤 Enter 同走元件之 `clickBtn`）。全頁 loading 與訊息框（WDialog）只擋滑鼠、不搶焦點；按鈕鎖（`promiseUnlock`）涵蓋請求期間，流程狀態（`runSubmit('saveTargets')`）涵蓋至結果訊息框關閉，期間再觸發即略過。後端以「updateTabItems:targets:操作者 id」占位：同一操作者並行儲存之第 2 次回 `saveInProgress`、不寫入；新增 / 複製之列帶 `_isNew`，依序重送同一包（第 1 次已建立該列）回 `saveNewRowExists`、整包不寫入。不同操作者之並行仍由 kmx 序列化、各自成功。
- **寫入前驗證**（ADR-026）：寫入順序為刪除 → 新增 → 修改，且無交易；可預判之寫入失敗（主鍵非字串、UTF-8 超過 1978 位元組、與他列重複；本次新增或修改之列任一字串欄位會被 XSS 清除改寫）一律於刪除之前擋下並回語系鍵、資料庫零變更。只驗本次會寫入之列；未變更之既有列（含早期寫入之含標記資料）不寫入、不驗，不阻擋儲存。判準與 w-serv-orm 之 clearXSS 同一函數（全樹只有一份 wsemi）。修改路徑即「刪舊列＋新增新列」，故含標記之新路徑被拒時原標的不會消失。
- **新列重用本次刪除之 id**（ADR-025）：本表 id 可就地改寫；同一次儲存中刪除（或改掉 id）既有標的 X，又把新增列之 id 改為 X，淨效果為修改 X——送出前以 `reuseDeletedIds` 把該列改為一般列並沿用資料庫之建立者 / 建立時間，儲存後 X 之內容為新列之值、建立者與建立時間不變、修改者與修改時間為本次。
