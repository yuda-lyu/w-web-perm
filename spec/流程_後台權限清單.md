# 後台權限清單流程

## 觸發

管理員（瀏覽器使用者，經登入取得有效 token、連線通過 `verifyConn` 守門）進入後台後，於左側導覽進入權限清單頁（`LayoutContentPemis.vue`）。此頁以 ag-grid（`WAggridVue`）列出 `pemis`（權限設定）表，欄序為 名稱 / 說明 / 管控對象（`crules`）/ 管控所屬權限群組（`belongGrups`）——本權限自己管控的在左、由上層帶過來的在右（2026-09-16 依業主要求對調，見 `LayoutContentPemis.vue` `data` 之 `tabKeys` / `tabKeysPick` / `tabKeysShow`）；提供：編輯模式切換、顯示欄位挑選、新增 / 複製 / 刪除 / 儲存，以及 `crules` 欄（編輯該權限對管控對象的 y/n 規則）與 `belongGrups` 欄（檢視該權限所屬權限群組）兩個關聯入口按鈕。

寫入端點 `updatePemis` 經 hapi `verifyConn` → `checkToken(token, apiType)` → `getAndVerifyClientUser` 守門（`server/WWebPerm.mjs`：`verifyConn`、`p.checkToken`、`getAndVerifyClientUser`）：token 須可由部署方 `getUserByToken` 解出使用者、該使用者須存在於 perm `users` 表且 `isActive='y'`（`getTokenUser`）、並通過部署方 `verifyClientUser(user, from)`（資料通道之 from 為 apiType，如 `main`），**任一不符即拒絕連線**（ADR-015，2026-09-29 業主裁示資料通道採嚴格預設）；是否限定管理員由 `verifyClientUser` 決定。

- **E2E-005**
  - title: 管理員勾選刪除權限列並儲存成功
  - description: 管理員在權限清單頁的編輯模式下，勾選一個權限列後點工具列的「刪除勾選權限」。若所選權限正被群組引用，例如種子資料的第一個權限「權限P1」被群組「權限群組M1」引用，畫面會先跳出確認框，說明將自幾個群組移除對所選權限的引用，點「確定」才把該列自清單移除，此時資料庫尚未變動；再點工具列的儲存鈕才會真正寫入，並出現訊息「儲存權限數據成功」。儲存時，引用這個權限的群組其「管控使用權限」也會一併移除該權限，因此這些群組的使用者不再透過它取得授權。若在確認框點「取消」，該權限不會被刪除。適合在整理不再使用的權限時使用。

      3. **解析後權限樹（權限系統核心，不可省）**：刪除首列權限 P1 後，以 `getPermUserInfor` 查使用此權限之 user（peter 之群組 M1 使用 P1+P2），其 resolved rules 的 active target 集合須**失去 P1 獨有的 `專案A/頁A/區塊A`**、只剩 P2 之 3 個 target（`專案A/頁C`, `專案B/頁A/區塊A`, `專案B/頁A/區塊B`）。**驗「刪權限 → 受影響使用者解析後權限正確縮減」，非只驗 DB 列消失**。預期值由 `getUserRules` 演算法算出。

  - description: 管理員在權限清單頁就地修改某個權限的名稱後點儲存，若有群組正引用這個權限，畫面會先跳出確認框，說明儲存後將一併更新幾個群組對已改名權限的引用，並列出每個改名的舊名稱與新名稱；若其中有群組的來源是外部應用，確認框會加註這些群組的引用下次外部同步時可能被外部資料覆寫。名單最多列出 5 個改名，超過時以「…等 N 個」帶出總數，沒有群組引用的權限改名不會列入名單。點「取消」則不送出，清單仍保留已改的名稱與儲存鈕；點「確定」才寫入，成功訊息會附註已將幾個群組對已改名權限的引用一併更新為新名稱，這些群組的引用名稱同步換為新名稱，所屬使用者的授權與改名前完全相同。適合在調整權限名稱時，先確認會影響多少群組。

## spec 規則摘要

- **權限**：所有 `updatePemis` 寫入經 `verifyConn` → `checkToken` → `getAndVerifyClientUser` 守門（token 須有效、其使用者須在 perm `users` 表且 `isActive='y'`、並通過部署方 `verifyClientUser` 才可寫；ADR-015 嚴格預設）；是否限管理員由 `verifyClientUser` 決定。
  - 修改留痕（2026-09-29）：原載「經 `checkToken` 守門（有效 token 才可寫）」並以行號引用 `WWebPerm.mjs`——行號已漂移，且未載 perm `users` 表／`isActive` 要求；ADR-015 業主裁示資料通道維持嚴格預設後，依現行碼（`WWebPerm.mjs` 之 `p.checkToken` → `getAndVerifyClientUser`）改寫本段、觸發段、執行流程與資料來源表之守門行。
- **粒度**：欄位錯誤走 cell 警告 icon + tooltip（具體 2 種：name 空 / name 重複）；Save 擋存彙整走 `showCheckYes` 持久 modal（粗 1 種 `errInNames`）；操作結果（成功 / 失敗 / rows 空）一律 `showCheckYes` 持久 modal（成功 `pemiSavePemisSuccess` / 失敗 `pemiSavePemisFail` / 空 `pemiAddEmpty`）；唯外層 `.catch` 之非預期例外（`anUnexpectedErrorOccurred`）走 `$alert` toast 低調呈現。
- **邊界**：
  - `pemis` **name 不可空 / 不可重複**（前端 `errItemsByName` 警告 + 後端雙守門：`ckKey('name')` 驗空值／非字串、`findTouchedDup` 驗唯一〔精確 `===`、只拒本次新增或修改所造成之同名，F-02、ADR-034〕，`procCore.mjs:updateTabItems`）。庫內歷史既有重複（僅外部同步可造成）原樣送回不被伺服端拒絕，且改以 `id` 對應差異（改名不被靜默吞掉）；**前端 `errItemsByName` 自 2026-10-21 run05 起與伺服端同一判準（`getNameErrs.mjs`／`findTouchedDup.mjs`），只擋本次造成或觸及之同名，歷史同名顯示警告圖示（`warnNameHistDup`）而不擋存**（E2E-011、E2E-012；原載『前端仍對歷史重複標警告並擋存』自此不成立，實測確認見〈已知落差〉）。後端 diff key 為 `id`（`procCore.mjs:updatePemis`；2026-10-21 run04 起，原通常為 `name`、庫內已有同名列時才改 `id`——ADR-034 Update：寫入後名稱集合須等於送入之整表）。
  - CRUD 為「單頁多動作 + 批次儲存」模型：`addItem` / `copyItem` / `deleteItemsCheck` / `showVeCrulesById` 只改 `opt.rows` 並設 `isModified=true`，**不即時打 API**；一律 Save 才以 `ltdtDiffByKey` 批次 del / insert / save 送出。
  - 兩個關聯入口：`crules` 按鈕開 `VeCrules`（resolve 回填 `crules` 字串、可編輯）；`belongGrups` 按鈕開 `VePemiBlngGrups`（resolve 不回填本列；編輯態可勾選，儲存由對話框自行直接 `updateGrups`，ADR-014；唯讀態才僅供檢視）。
  - `belongGrups` 為前端 computed 衍生顯示欄，非 `pemis` schema 持久欄位，不寫入 DB。
  - 稽核欄位（`userId` / `time*`）前端填 `{待自動給予}` 佔位符，後端 `procOrm` 補實值。
  - `isError` / `errItemsByName` 為前端 computed 驗證（`LayoutContentPemis.vue` 之 computed `isError` / `errItemsByName`）；只要 `errItemsByName` 非空即彙整為 `errInNames` 擋存。
- **引用連帶（2026-10-22 run06，ADR-036、規則帳本 R-REF-CASCADE-01）**：權限被刪除或改名時，引用它之 `grups.cpemis` 於同一次寫入內連帶處理。**刪除**：移除該引用（任何 mode、含停用項；以 AND 引用者限制解除，授權可能變多，效果等同舊版「找不到即忽略」；不採「被引用則禁止刪除」，使用者 2026-10-21 裁示），刪除前以確認框提示筆數與其中以 AND 引用者（E2E-005、E2E-014）；刪除後以同名新增（新 id）之權限不繼承舊引用。**改名**（同 id 異名；伺服端 `opt.cascadeRename` 預設 `true`）：引用字串連帶改為新名稱，儲存前以確認框預覽，名單至多 5 個、其餘以「…等 N 個」帶總數（E2E-015），成功訊息附筆數；改名被伺服端預檢拒絕與 `cascadeRename:false` 兩條路徑之行為同群組頁（`流程_後台群組清單.md` E2E-016、E2E-017），本頁無 e2e 案例（見〈已知落差〉）。引用端先寫、主體後寫，任一步失敗以寫入前原值補償還原引用端。外部同步（同一 `from` 內依穩定 id）同樣適用，見 `流程_外部應用同步權限資料.md`〈同步之引用連帶〉。
- **契約**：`savePemis` 為按鈕 handler，把 `msg.pm` 交給 `doSavePemis`、不於 handler 解鎖；`doSavePemis` 以 `$ui.runSubmit('savePemis', …)` 包覆 `core() + .catch + .finally`，`finally` 一處關 loading；`updatePemis` 失敗由其 inline `.catch` 顯示失敗結果 modal，並以 `okSave` 旗標 `if (!okSave) return` 短路後續。loading 於 `core()` 內、在 `isError` / rows 空兩同步檢查**之後**才開啟；早退分支不開 loading，符合全域 §5.1 canonical（`updateLoading` 應在同步檢查後）。（修改留痕 2026-09-29：原載「第一行 `msg.pm.resolve()` 釋放視覺鎖後 fire-and-forget」，已由 ADR-025 改寫。）
- **送出入口與連按**（ADR-025）：入口只有 Save 鈕（WButtonCircle，滑鼠與焦點在鈕上之鍵盤 Enter 同走元件之 `clickBtn`）。全頁 loading 與訊息框（WDialog）只擋滑鼠、不搶焦點；按鈕鎖（`promiseUnlock`）涵蓋請求期間，流程狀態（`runSubmit('savePemis')`）涵蓋至結果訊息框關閉，期間再觸發即略過。後端以「updateTabItems:pemis:操作者 id」占位：同一操作者並行儲存之第 2 次回 `saveInProgress`、不寫入；新增 / 複製之列帶 `_isNew`，依序重送同一包（第 1 次已建立該列）回 `saveNewRowExists`、整包不寫入（本表 diff 依 `name`，重送之新列會被當「修改」以前端佔位字覆寫建立者與建立時間，故以 id 比對擋下）。不同操作者之並行仍由 kmx 序列化、各自成功。
