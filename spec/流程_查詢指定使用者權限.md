# 查詢指定使用者權限流程

## 觸發

外部 node 應用（非瀏覽器使用者）以系統介接身分查詢「某一指定 `userId`」的權限資訊。應用端呼叫 `getPermUserInfor(url, tokenSelf, userIdTar, opt)`（`src/getPermUserInfor.mjs:getPermUserInfor`），其中 `url` 須同時帶有 `token={sysToken}` 與 `userId={userId}` 兩個佔位符（`src/getPermUserInfor.mjs:getPermUserInfor`, 缺一即拒），函式將 `tokenSelf`、`userIdTar` 經 `encodeURIComponent` 後以 split / join 分別代入 `{sysToken}`、`{userId}`（`src/getPermUserInfor.mjs:getPermUserInfor`；2026-09-25 起, 原為未編碼之 `replaceAll`, 見 ADR-023）後，以內建 fetch（`src/fetchJson.mjs`）打後端 `GET /api/getPermUserInfor`（`server/WWebPerm.mjs:apis(/api/getPermUserInfor)`）。

後端以 `query.token` 解出發起者 `tokenSelf`，經 `getAndVerifyAppUser` 驗證其為合法 app 使用者（`server/WWebPerm.mjs:apis(/api/getPermUserInfor).core`）；驗證通過後以 `query.userId` 為查找對象，呼叫 `getGenUserAndRulesByUserId` 取回該使用者的權限資訊物件並回傳（`server/WWebPerm.mjs:apis(/api/getPermUserInfor).core`）。`getAndVerifyAppUser` 以外部 `getUserByToken` 取得使用者後，**套件自行要求管理員等級**（`server/WWebPerm.mjs:getAndVerifyAppUser`；2026-10-24 perm-run01 本輪 P-1，R-APP-TOKEN-01）：呼叫者在 perm `users` 表者（不論 isActive；含綁定該使用者之使用者用途應用系統 token）以該列為準，須有效且 `isAdmin='y'`；不在表者**只看反查結果 `isAdmin='y'`**（2026-10-24 perm-run02①相容認定，`adminCheck.mjs:isExtAdminUser`：不要求 `isApp`、不要求 id 以 `app:` 開頭；舊版 sso 之應用系統身分即 `isAdmin='y'`，升版不中斷；不在表之 sso 管理員以自身 token 或以綁定它之使用者用途 token 呼叫皆放行）；在表之一般使用者、綁一般使用者之應用系統 token、不在表且 `isAdmin` 非 `'y'` 者皆拒（`userNotAdmin`）；再過部署方 `verifyAppUser`（先 `userNoPermission` 後 `userNotAdmin`）。〔原載「僅以外部 `getUserByToken` 取得使用者再過 `verifyAppUser` 把關，不反查 perm `users` 表，故可支援應用程式專屬之虛擬使用者帳號」於 2026-10-24 不成立（現須管理員等級）；perm-run01 版曾載「不在表者須 `isApp='y'` 且 `isAdmin='y'`」，perm-run02 更正為「只看 `isAdmin='y'`」，系統服務用途之嚴格認定（`isApp='y'`、`isAdmin='y'`、id 以 `app:` 開頭）只用於後台登入檢查、資料通道與 `requireAdmin`。〕

## 重要流程

本流程為系統介接 API，無瀏覽器 UI 終態，E2E 以 API 回傳值斷言為主，不含視覺 baseline。

- **E2E-001**
  - title: 合法 app token 查詢既有 userId 回傳該使用者權限
  - description: 驗證以合法 app 使用者 token（`tokenSelf`）查詢一個存在且 `isActive='y'` 的 `userId` 時，後端通過 `getAndVerifyAppUser` 驗證、`getGenUserAndRulesByUserId` 取回資料，HTTP 回應 `state='success'`、`msg` 為含 `user` 與 `rules` 的物件；客戶端函式 resolve 該物件。屬查詢成功 golden 案例。
  - flow:
    - 測試資料：base seed 既有 user（取一筆 `isActive='y'` 的 `userId` 作查找對象）；發起者 token 為部署方 `getUserByToken` 可解出且通過 `verifyAppUser` 的 app token。
    - 操作：以合法 `tokenSelf` 與既有 `userIdTar` 呼叫 `getPermUserInfor(url, tokenSelf, userIdTar)`。
    - 驗證：
      1. 語意：HTTP 回應 `state='success'`；`msg` 為物件，含 `user`（其 `id` 等於查找的 `userIdTar`，且帶 `grupsNames` 字串欄位）與 `rules`（陣列）；客戶端函式 resolve 該物件。
      2. 視覺：本流程為 API 查詢、無 UI 終態，無視覺 baseline。
    - 雙語：本流程為 API，回傳為資料物件、不含 i18n 文案，單輪即可。
    - 清理：本案唯讀，不改 DB，無需清理。

- **E2E-002**
  - title: 缺少 token 佔位符的 url 在客戶端前置攔截
  - description: 驗證傳入的 `url` 缺少 `token={sysToken}` 或 `userId={userId}` 任一佔位符時（含兩者皆缺），客戶端函式於送出請求前即 reject `noTokenUserIdInUrl`，不打後端。屬客戶端前置參數攔截案例。（2026-09-25 更正：原載「同時缺少兩者時」——舊實作以 `&&` 判斷，只缺一個時仍送出請求，已改為缺一即拒，見 ADR-023）
  - flow:
    - 測試資料：建構三個 `url`：兩個佔位符皆缺、只缺 `userId={userId}`、只缺 `token={sysToken}`；`tokenSelf` / `userIdTar` 給合法非空字串。
    - 操作：以各 `url` 呼叫 `getPermUserInfor`。
    - 驗證：
      1. 語意：三者皆 reject 值 `noTokenUserIdInUrl`；後端未收到請求。
      2. 視覺：無 UI 終態，無視覺 baseline。
    - 雙語：API 流程，reject 值為 camelCase key（`procLang.mjs` 有 eng + cht 定義），單輪即可。
    - 清理：未送出請求、未改 DB，無需清理。

- **E2E-003**
  - title: 缺漏必填參數在客戶端前置攔截
  - description: 驗證 `url` / `tokenSelf` / `userIdTar` 任一為非有效字串時，客戶端函式於對應檢查點 reject `invalidUrl` / `invalidTokenSelf` / `invalidUserIdTar`，不打後端。屬客戶端必填檢查案例。
  - flow:
    - 測試資料：分別建構三組輸入，各令 `url` / `tokenSelf` / `userIdTar` 其一為空字串、其餘給合法值。
    - 操作：以各組輸入呼叫 `getPermUserInfor`。
    - 驗證：
      1. 語意：依缺漏欄位分別 reject `invalidUrl` / `invalidTokenSelf` / `invalidUserIdTar`；後端未收到請求。
      2. 視覺：無 UI 終態，無視覺 baseline。
    - 雙語：API 流程，reject 值為 camelCase key（`procLang.mjs` 有 eng + cht 定義），單輪即可。
    - 清理：未送出請求、未改 DB，無需清理。

- **E2E-004**
  - title: token 非合法 app 使用者後端拒絕
  - description: 驗證 `tokenSelf` 無法經 `getUserByToken` 解出使用者、或解出之使用者未通過 `verifyAppUser` 時，後端 `getAndVerifyAppUser` reject，HTTP 回應 `state='error'`；客戶端因 `state!=='success'` 而 reject `cannotGetUserDataByUrl`。部署方注入之 `getUserByToken` 拋錯或 reject 視同解不出使用者、`verifyAppUser` 拋錯或 reject 視同回 false，回應 `msg` 同為自家 key，上游錯誤原文不回傳（W 契約，ADR-023；`test/api-tokenSafety` TS-001 / TS-002）。屬後端 app 身分驗證拒絕案例。
  - flow:
    - 測試資料：base seed；`tokenSelf` 給一個部署方 `getUserByToken` 解不出使用者（或解出但 `verifyAppUser` 回 false）的 token；`userIdTar` 給既有 userId。
    - 操作：以該 `tokenSelf` 呼叫 `getPermUserInfor`。
    - 驗證：
      1. 語意：HTTP 回應 `state='error'`（`msg` 為 `cannotFindUserFromToken`（getUserByToken 解不出使用者）或 `userNoPermission`（verifyAppUser 回 false））；客戶端函式 reject `cannotGetUserDataByUrl`；DB 不變。
      2. 視覺：無 UI 終態，無視覺 baseline。
    - 雙語：API 流程，回傳 reject 字串、不含 i18n，單輪即可。
    - 清理：本案唯讀，不改 DB，無需清理。

- **E2E-005**
  - title: 查詢不存在的 userId 回傳空權限（全停用，fail-safe）
  - description: 驗證 `tokenSelf` 為合法 app 使用者、但 `userIdTar` 對應之使用者不存在時，後端 `getGenUserByUserId` 取不到使用者，但 `getUserRules` 容忍此情形、回傳「全停用」之空權限物件（fail-safe），故 HTTP 回應 `state='success'`、`msg` 為一個 `user` 無有效 `id`、`rules` 各規則 `isActive='n'` 的物件；客戶端 resolve 該物件。屬「查找對象不存在 → 回空權限」之 fail-safe 案例（**非 reject**）。
  - flow:
    - 測試資料：合法 `tokenSelf`；`userIdTar` 給一個 `users` 表中不存在的 id。
    - 操作：以該輸入呼叫 `getPermUserInfor`。
    - 驗證：
      1. 語意：HTTP 回應 `state='success'`；客戶端 resolve 之物件 `user` 無有效 `id`、`rules` 為陣列且各規則 `isActive='n'`（空權限）；DB 不變。
      2. 視覺：無 UI 終態，無視覺 baseline。
    - 雙語：API 流程，回傳為資料物件、不含 i18n，單輪即可。
    - 清理：本案唯讀，不改 DB，無需清理。

- **E2E-006**
  - title: funConvertPerm 轉換查詢結果
  - description: 驗證 `opt.funConvertPerm` 提供時，客戶端於取得後端回傳的權限物件後，以 `funConvertPerm` 轉換（支援同步或回傳 Promise）並改以轉換後物件 resolve；若轉換結果非有效物件，或 `funConvertPerm` 同步拋錯 / reject（2026-09-25 起，原為部署方錯誤原樣上拋，見 ADR-023），則 reject `noUserDataAfterConvert`。屬客戶端後處理 hook 案例。
  - flow:
    - 測試資料：同 E2E-001 之合法 `tokenSelf` 與既有 `userIdTar`；`opt.funConvertPerm` 給一個將原物件包裝/改寫的函式。
    - 操作：以帶 `funConvertPerm` 的 `opt` 呼叫 `getPermUserInfor`。
    - 驗證：
      1. 語意：函式 resolve 之物件為 `funConvertPerm` 轉換後的結果（與未轉換之原物件不同）；當 `funConvertPerm` 回非物件、同步拋錯或 reject 時改 reject `noUserDataAfterConvert`（不上拋部署方之錯誤原文）。
      2. 視覺：無 UI 終態，無視覺 baseline。
    - 雙語：API 流程，回傳為資料物件、不含 i18n，單輪即可。
    - 清理：本案唯讀，不改 DB，無需清理。

- **E2E-007**
  - title: 以主鍵對應時以外部使用者代號查詢權限
  - description: 權限系統以預設的主鍵方式對應外部系統的使用者時，外部應用查詢某位使用者的權限，傳入的是這位使用者在外部系統的代號：外部同步進來的使用者傳它的來源鍵，後台建立的使用者傳它的 id，而不是權限系統內部另外配發的 id，和使用者登入時的對應方式一致。傳入內部配發的 id 通常找不到使用者，回傳全部停用的空權限，和查詢不存在的使用者一樣（若該內部 id 恰好等於另一位使用者的外部代號，則查到的是那一位）；已停用的使用者同樣查無。權限系統的對應鍵設為 email 或 name 時，傳入的仍是權限系統內部的 id，行為不變。
  - flow:
    - 測試資料：base seed；以合法 app token 以來源 `appMi-14` 對 `users` 推送啟用中的外部使用者（來源鍵 `id-for-admin2`）與停用中的外部使用者（來源鍵 `mi14-off`），讀回前者的內部 id；另一輪以臨時設定重啟後端為 email／name 模式並推送外部使用者（來源鍵 `mi15-guid`）。
    - 操作：以合法 `tokenSelf` 分別查詢：外部使用者的來源鍵、其內部 id、後台使用者 `id-for-admin`、停用外部使用者的來源鍵；email／name 模式下查詢外部使用者的內部 id 與其來源鍵。
    - 驗證：
      1. 語意：傳來源鍵回 `state='success'`、`msg.user.id` 為該列內部 id、`msg.user.srcKey` 為傳入值；傳內部 id 回 `state='success'` 但 `msg.user` 無有效 `id`、`rules` 各規則 `isActive='n'`；傳 `id-for-admin` 回該後台使用者；傳停用列之來源鍵同傳內部 id（空權限）。
      2. 語意：email／name 模式下傳內部 id 回該列、傳來源鍵回空權限。
    - 雙語：API 流程，回傳為資料物件、不含 i18n，單輪即可。
    - 清理：刪除 `from` 為 `appMi-14`、`appMi-15` 之列，還原 users 表。
    - 備註：規則帳本 R-MAPKEY-05；`server/WWebPerm.mjs:resolvePermUserId`（只此路由使用；`/api/getPerm` 之使用者本人 id 已是內部 id，不經解析）；判準單一擁有者 `server/keyCheck.mjs:findLoginUsers`。〔原載 → 改為 2026-10-24（perm-run05，主控收件裁示②）：原載「`userId` 一律為 perm 內部 id」於 `mappingBy` 為 `id` 時不成立。〕測試：`api-mapKeyId` MI-014、MI-015；`api-getPermUserInfor` 007、008（夾具改傳來源鍵）；`unit-loginId` SITE-LI-005。

- **E2E-008**
  - title: 以主鍵對應時代號對到多位使用者之查詢被拒
  - description: 權限系統以預設的主鍵方式對應外部系統的使用者時，若傳入的使用者代號同時符合兩位以上使用者（例如後台使用者的 id 與外部使用者的來源鍵相同，或兩個來源的來源鍵相同；不論其中幾位啟用中），系統無法確定要查的是哪一位，伺服器一律拒絕、不會任取其中一位：回應 state 為「error」、msg 為「ambiguousUserFromPerm」；呼叫端使用 getPermUserInfor 輔助函式時，任何非成功的回應一律回報為「cannotGetUserDataByUrl」。管理者排除重複的使用者資料後恢復正常。
  - flow:
    - 測試資料：base seed；外部列（來源 `appMi-14`，來源鍵 `id-for-admin2`）經推送建立，再以測試框架直寫資料庫預置後台列（id `id-for-admin2`）。
    - 操作：以合法 `tokenSelf` 查詢 `id-for-admin2`。
    - 驗證：
      1. 語意：回傳 `state='error'`、`msg` 為 `ambiguousUserFromPerm`；srLog 記 `api/getPermUserInfor-error`（`msg`、`mappingBy`、`count`），不記查詢值。
    - 雙語：API 流程，單輪即可；`ambiguousUserFromPerm` 於 `server/procLang.mjs` 有 eng + cht 定義。
    - 清理：刪除 `from` 為 `appMi-14` 之列並還原 users 表。
    - 備註：規則帳本 R-MAPKEY-05；測試：`api-mapKeyId` MI-014（驗證 5）。

## 執行流程

客戶端 `getPermUserInfor` 先做必填與佔位符檢查、將 `tokenSelf` / `userIdTar` 經 `encodeURIComponent` 代入 `{sysToken}` / `{userId}` 後以內建 fetch（`fetchJson`）打後端；後端 `/api/getPermUserInfor` handler 以 `pm2resolve(core)` 包裝，`core` 內依序驗 `tokenSelf`、`getAndVerifyAppUser`、驗 `userId`、`getGenUserAndRulesByUserId`，並把 resolve / reject 統一轉為 `{ state, msg }`。部署方注入之 `getUserByToken` / `verifyAppUser` 於 `WWebPerm` 建構時即以包裝版取代（W 契約，`WWebPerm.mjs:WWebPerm` 內以 `wrapInjected` 包裝三個注入參數、`wrapInjected.mjs`），拋錯或 reject 分別視同回 `null` / `false`，並記 `srLog.warn`（`inject-<函數名>-fail`，只記白名單 key 或型別與 `Error.name`）。

（註：本節各步驟之位置標註為符號錨 `[檔名:符號]`（函式或變數名；2026-10-21 起取代行號，行號會隨改版漂移）；`apis(<path>).core` 指 `server/WWebPerm.mjs` 內 `apis` 陣列中該 `path` 之 handler 的 `core()`，`getPermUserInfor.mjs` 為 `src/getPermUserInfor.mjs`。）

## 回傳結構

| 欄位 | 來源 | 說明 |
|---|---|---|
| HTTP `state` | `pm2resolve` 包裝 `core`（`WWebPerm.mjs:apis(/api/getPermUserInfor)`） | `core` resolve → `'success'`；reject → `'error'` |
| HTTP `msg` | 同上 | 成功時為權限物件；失敗時為 reject key（Error 物件取 `message`，`WWebPerm.mjs:apis(/api/getPermUserInfor)`） |
| `msg.user` | `getGenUserAndRulesByUserId` 回傳（`WWebPerm.mjs:getGenUserAndRulesByUserId`） | 查找到的使用者物件，含原欄位與附加之 `grupsNames` |
| `msg.user.grupsNames` | `getUserRules` 結果取 `grups` 之 `name` 以分號串接（`WWebPerm.mjs:getGenUserAndRulesByUserId`） | 僅含 `isActive='y'` 且在群組表中查得之有效權限群組名稱（引用查無〔懸空〕者不列入，雖其仍以空內容參與授權合併，見 `流程_權限規則合併計算.md` E2E-017；2026-10-21 run05 補載） |
| `msg.rules` | `getUserRules` 結果之 `rules`（`WWebPerm.mjs:getGenUserAndRulesByUserId`） | 該使用者的權限規則陣列 |
| 客戶端 resolve 值 `ur` | `data.msg`（`getPermUserInfor.mjs:getPermUserInfor`），若有 `funConvertPerm` 再轉換（`getPermUserInfor.mjs:getPermUserInfor`） | 應用端最終取得的權限資訊物件 |

## i18n 訊息粒度規則

本流程為 server-side 查詢 API，回傳 `{ state, msg }` 為**機器可讀值**（`state='success'` / `'error'`，成功時 `msg` 為含 `user` / `rules` 的權限物件、失敗時 `msg` 為 camelCase 錯誤 key）。後端 reject key（如 `tokenNoPermission` / `cannotFindUserFromToken` / `userNoPermission` / `userIdNoPermrules` / `cannotGetUserRules`）於 `server/procLang.mjs` 皆有 eng + cht 定義；前端 SDK 自身 reject 的 key（如 `noTokenUserIdInUrl` / `cannotGetUserByUrl` / `cannotGetUserDataByUrl` / `noUserDataByUrl` / `noUserDataAfterConvert`）亦於 `procLang.mjs` 有 eng + cht 定義。由呼叫端應用以 key 查 lang 決定如何呈現。故本流程訊息粒度即「一個 reject key 對應一條 procLang 雙語訊息」。

## spec 規則摘要

- **權限**：發起者身分以 `query.token`（即 `tokenSelf`）經 handler 內 `getAndVerifyAppUser` 把關（`WWebPerm.mjs:apis(/api/getPermUserInfor).core`），驗證鏈為 `getUserByToken` 取使用者 → 管理員等級（在 perm `users` 表者以該列為準：有效且 `isAdmin='y'`；不在表者只看反查 `isAdmin='y'`〔perm-run02①相容認定，原 perm-run01 版「須 `isApp='y'` 且 `isAdmin='y'`」不成立〕）→ `verifyAppUser` 確認（部署方否決 `userNoPermission` 先於等級不足 `userNotAdmin`）（`WWebPerm.mjs:getAndVerifyAppUser`，2026-10-24 perm-run01 P-1、perm-run02①，R-APP-TOKEN-01）。在表之一般使用者、使用者用途綁一般使用者、不在表且 `isAdmin` 非 `'y'` 者皆拒；使用者用途綁停用之使用者由列拒（`cannotGetUserFromPerm`）；不在表而 `isAdmin='y'` 者（含未轉傳 `isApp` 之虛擬帳號、綁不在表之 sso 管理員）放行（`api-callerMatrix` MX-H4、MX-R1、MX-R2）。〔原載「此驗證只依外部 `getUserByToken`、不反查 perm `users` 表，故可支援應用程式專屬之虛擬使用者帳號」不成立（現須管理員等級：在表以列、不在表看 `isAdmin='y'`）。〕
- **注入函數失敗（W 契約，ADR-023）**：`getUserByToken` 拋錯或 reject ≡ 取不到使用者（`cannotFindUserFromToken`）；`verifyAppUser` 拋錯或 reject ≡ 未通過（`userNoPermission`）。上游錯誤原文（如舊版 w-web-sso helper 之含權杖網址）不回應、不入 log；srLog 另記 warn `inject-<函數名>-fail`。對外刻意不區分「上游不可達」與「權杖無效」。
- **`userId` 之解析（2026-10-24 perm-run05 起，規則帳本 R-MAPKEY-05）**：`mappingBy` 為 `id`（預設）時，`query.userId` 是使用者於外部系統之代號，與登入同一判準解析（`WWebPerm.mjs:resolvePermUserId`、`keyCheck.mjs:findLoginUsers`）：外部同步列對 `srcKey`、後台列對 `id`（外部列之內部 `id` 不是登入識別），不論 `isActive` 計筆；命中多筆 → `state='error'`、`msg` 為 `ambiguousUserFromPerm`（E2E-008）；查無或恰一筆停用 → 回全停用之空權限（同 E2E-005）；`mappingBy` 為 `email`／`name` 時 `userId` 維持 perm 內部 id。〔原載「`userId` 為 perm 內部 id」於 `mappingBy` 為 `id` 時不成立；對既有以內部 id 查外部列者為行為變更，見 E2E-007 與 README Upgrade Notes 第 4 節。〕
- **查找對象**：查的是 `query.userId`（即 `userIdTar`）所指之**任意指定使用者**，由 `getGenUserAndRulesByUserId` 取其權限（`WWebPerm.mjs:apis(/api/getPermUserInfor).core`，userId 先經上一條解析）；`getGenUserByUserId` 經 `getGenUserByKV` 僅取 `isActive='y'` 之使用者（`WWebPerm.mjs:getGenUserByUserId`、`getGenUserByKV`）。**查找對象不存在時不 reject**（`isActive` 非 `'y'` 之停用使用者同樣查無，與不存在者走同一路徑）：`getUserRules` 容忍取不到的使用者、回傳「全停用」之空權限物件（fail-safe），故 handler 回 `state='success'`、`msg` 為 `user` 無有效 `id`、`rules` 各規則 `isActive='n'` 的物件（見 E2E-005）。
- **回傳契約**：handler 以 `pm2resolve(core)` 統一輸出 `{ state, msg }`（`WWebPerm.mjs:apis(/api/getPermUserInfor)`）——成功 `state='success'`、`msg` 為 `{ user, rules }`；失敗 `state='error'`、`msg` 為 reject key。客戶端依 `state==='success'` 判定成敗，再取 `msg` 為權限物件（`getPermUserInfor.mjs:getPermUserInfor`）。
- **客戶端前置攔截**：`url` / `tokenSelf` / `userIdTar` 任一非有效字串即於送出前 reject（`getPermUserInfor.mjs:getPermUserInfor`）；`url` 缺任一佔位符亦 reject（`getPermUserInfor.mjs:getPermUserInfor`；2026-09-25 更正，原載「缺兩個佔位符」為舊 `&&` 實作之行為），不打後端。
- **代入**：`tokenSelf` / `userIdTar` 一律經 `encodeURIComponent` 以 split / join 代入（`getPermUserInfor.mjs:getPermUserInfor`），不用 `replaceAll`（其取代字串會解讀 `` $` `` 等樣式）；伺服端解出之值與原值相同，UUID、英數與 `-_.~` 之線上格式不變。
- **客戶端後處理**：`opt.funConvertPerm` 為函式時，於成功回傳後對權限物件做轉換（支援同步或 Promise），轉換結果須為有效物件，否則 reject；轉換函式同步拋錯或 reject 亦 reject `noUserDataAfterConvert`（`getPermUserInfor.mjs:getPermUserInfor`）。
- **錯誤分層**：fetch 連線層級失敗或非 2xx → `errTemp` 非 null → reject `cannotGetUserByUrl`，回應非 JSON → `cannotGetUserDataByUrl`（`getPermUserInfor.mjs:getPermUserInfor`）；後端回 `state!=='success'` → reject `cannotGetUserDataByUrl`（`getPermUserInfor.mjs:getPermUserInfor`）；回傳物件非有效 → reject `noUserDataByUrl`（`getPermUserInfor.mjs:getPermUserInfor`）。
