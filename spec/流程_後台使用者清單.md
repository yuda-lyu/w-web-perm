# 後台使用者清單流程

## 觸發

管理員（瀏覽器使用者，經 w-ui-loginout 登入取得有效 token、`connState='csLogin'`）進入後台後，於 `LayoutContent.vue` 左側導覽點「使用者」（`mmUsers`）進入使用者清單頁（`LayoutContentUsers.vue`）。此頁以 ag-grid（`WAggridVue`）列出 `users` 表，提供：編輯模式切換、顯示欄位挑選、新增 / 複製 / 刪除 / 儲存、`cgrups` 群組關聯入口按鈕、`isAdmin` / `isActive` 就地切換。

寫入端點 `updateUsers` 經 hapi `verifyConn` → `checkToken(token, apiType)` → `getAndVerifyClientUser` 守門（`server/WWebPerm.mjs`：`verifyConn`、`p.checkToken`、`getAndVerifyClientUser`）：token 須可由部署方 `getUserByToken` 解出使用者、該使用者須存在於 perm `users` 表且 `isActive='y'`（`getTokenUser`; 以 `mappingBy` 指定之對應鍵查找命中多於 1 筆啟用使用者時一律拒絕 `ambiguousUserFromPerm`、不取首筆，2026-10-21 起，F-14、ADR-034、規則帳本 R-MAPKEY-02）、並通過部署方 `verifyClientUser(user, from)`（資料通道之 from 為 apiType，如 `main`），**任一不符即拒絕連線**（ADR-015，2026-09-29 業主裁示資料通道採嚴格預設）；是否限定管理員由 `verifyClientUser` 決定（開發樣本限 `isAdmin='y'`，`srv.mjs`）。

## spec 規則摘要

- **權限**：所有 `updateUsers` 寫入經 `verifyConn` → `checkToken` → `getAndVerifyClientUser` 守門（token 須有效、其使用者須在 perm `users` 表且 `isActive='y'`、並通過部署方 `verifyClientUser` 才可寫；ADR-015 嚴格預設）；是否限管理員由 `verifyClientUser` 決定（開發樣本限 `isAdmin='y'`）。
  - 修改留痕（2026-09-29）：原載「經 `checkToken` 守門（有效 token 才可寫）」並以行號引用 `WWebPerm.mjs`——行號已漂移，且未載 perm `users` 表／`isActive` 要求；ADR-015 業主裁示資料通道維持嚴格預設後，依現行碼（`WWebPerm.mjs` 之 `p.checkToken` → `getAndVerifyClientUser`）改寫本段、觸發段與執行流程之守門行。
- **粒度**：欄位錯誤走 cell 警告 icon + tooltip（具體 5 種）；Save 擋存彙整（`errInNames` / `errInEmails` 粗 2 種）與操作結果（成功 / 失敗 / 空）一律走 `$dg.showCheckYes` 持久 modal（showCheckYes 前先 `updateLoading(false)`）；非預期例外（外層 catch）保留 `$alert` toast。
- **邊界**：
  - `users` **允許 name 重複**（預設 `mappingBy='id'` 時後端不擋；前端對「本次造成或觸及」之重複 name 仍擋存，歷史既有重複顯示警告圖示、不擋存）；`mappingBy` 為 `'name'` 時後端對 active 列之 name 檢查非空與唯一（只擋本次造成或觸及者，E2E-016）。`email` 不可空 / 不可重複，**只擋本次造成或觸及者**（前端 `getNameErrs`＋後端 `checkUsersWrite` 雙守門，共用 `findTouchedDup` 判準；歷史既有空值／重複原樣送回不拒；ADR-035 決定 h；原載『前端 + 後端 `ckKey` 對全表守門』自 2026-10-21 run05 起不成立）。`mappingBy` 為 `'email'` 時另補 active 列 email 之 trim 後非空與「停用改啟用」之檢查。
  - CRUD 為「單頁多動作 + 批次儲存」模型：`addItem` / `copyItem` / `deleteItemsCheck` / `toggle*` / `showVeCgrupsById` 只改 `opt.rows` 並設 `isModified=true`，**不即時打 API**；一律 Save 才以 `ltdtDiffByKey` 批次 del / insert / save 送出。
  - 稽核欄位（`userId` / `time*`）前端填 `{待自動給予}` 佔位符，後端 `procOrm` 補實值。
  - `isError` / `errItemsByName` / `errItemsByEmail` 為前端 computed 驗證（2026-10-21 run05 起只含「本次造成或觸及」者；歷史既有問題改入 `warnItemsByName`／`warnItemsByEmail`，顯示警告 icon 但不擋存）；原載『name 重複只警告不擋存（僅 email 與必填擋）』與讀碼不符——`errItemsByName` 原就使 `isError` 為真而以 `errInNames` 擋存（重複與空 name 皆擋），已更正。
  - loading 於 `core()` 內、在 `isError` / rows 空兩同步檢查**之後**才開啟（`LayoutContentUsers.vue` 之 `doSaveUsers`）；早退分支不開 loading，符合全域 §5.1 canonical（`updateLoading` 應在同步檢查後）。
- **契約**：`saveUsers` 為按鈕 handler，把 `msg.pm` 交給 `doSaveUsers`、不於 handler 解鎖；`doSaveUsers` 以 `$ui.runSubmit('saveUsers', …)` 包覆 `core() + .catch + .finally`，`finally` 一處關 loading；`updateUsers` 失敗由其 inline `.catch` 顯示失敗提示，並以 `okSave` 旗標 `if (!okSave) return` 短路後續。（修改留痕 2026-09-29：原載「第一行 `msg.pm.resolve()` 釋放視覺鎖後 fire-and-forget」，已由 ADR-025 改寫。）
- **送出入口與連按**（ADR-025）：入口只有 Save 鈕（WButtonCircle，滑鼠與焦點在鈕上之鍵盤 Enter 同走元件之 `clickBtn`）。全頁 loading 與訊息框（WDialog）只擋滑鼠、不搶焦點；按鈕鎖（`promiseUnlock`）涵蓋請求期間，流程狀態（`runSubmit('saveUsers')`）涵蓋至結果訊息框關閉，期間再觸發即略過。後端以「updateTabItems:users:操作者 id」占位：同一操作者並行儲存之第 2 次回 `saveInProgress`、不寫入；新增 / 複製之列帶 `_isNew`，依序重送同一包（第 1 次已建立該列）回 `saveNewRowExists`、整包不寫入，避免把剛建立之列以前端佔位字（`{待自動給予}`）當修改覆寫。不同操作者之並行仍由 kmx 序列化、各自成功。
