# 查詢使用者權限流程

## 觸發

瀏覽器端應用（外部系統）欲查詢「自身」（持有 token 的當前使用者）權限時，呼叫前端 SDK：先以 `getPerm(url, tokenTar, opt)` 直接取得 `{ user, rules }`，或以 `perm()` 工廠的 `conn(url)` 載入後用 `active(key)` / `getUser()` / `getRules()` 查詢單一規則或快取結果。

兩者最終都對後端 `/api/getPerm?token={token}` 發出 GET 請求：`getPerm.mjs` 將 `tokenTar` 經 `encodeURIComponent` 後以 split / join 代入 `url` 內 `{token}` 佔位符（2026-09-25 起, 原為未編碼之 `replaceAll`, 見 ADR-023），以內建 fetch（`src/fetchJson.mjs`）送出（`src/getPerm.mjs:getPerm`）；`perm.mjs` 的 `conn` 接收已帶妥 token 的完整 `url`，以 `fetchJson` 送出（`src/perm.mjs:perm.conn`），失敗時 reject / `permError` 收到 `{ kind, status, message }`，`message` 只含例外名稱與代碼（不含網址）。

後端 `/api/getPerm` handler 自 `req.query.token` 取 token，依序經 `getAndVerifyClientUser`（反查 perm `users` 表 + `verifyClientUser`）→ `getGenUserAndRulesByUserId`（查 `grups` / `pemis` / `targets` 並算 `getUserRules`）後，以 `pm2resolve` 包成 `{ state, msg }` 回傳（`server/WWebPerm.mjs:apis(/api/getPerm)`）。**token 無效 / 非 client 使用者 / 查無使用者一律 reject，`state` 回 `'error'`**；部署方注入之 `getUserByToken` / `verifyClientUser` 拋錯或 reject 分別視同查無 / 未通過（W 契約，ADR-023），`msg` 同為自家 key、不含上游原文。

## 重要流程

> 本流程為 query-api 類型：請求成功僅回傳 JSON 結構（`{ user, rules }`），無瀏覽器 UI 終態，故各 E2E 以 API 回傳結構 / `state` / 權限值為斷言對象，**不含 pixel baseline**。

- **E2E-001**
  - title: 持有效 token 的使用者查詢自身權限取得 user 與 rules
  - description: 驗證瀏覽器應用以有效 client 使用者 token 呼叫 `getPerm(url, tokenTar)`，後端依 token 解出該使用者、合併其群組與權限規則後，回傳含 `user`（含 `grupsNames`）與 `rules` 陣列的物件。屬 golden 成功路徑，其餘失敗 / 轉換案例皆以此回傳結構為基準。
  - flow:
    - 測試資料：base seed 既有 client 使用者（有對應 `grups` / `pemis` / `targets` 關聯）及其有效 token。
    - 操作：以該使用者 token 呼叫 `getPerm(url, tokenTar)`，url 含 `token={token}` 佔位符。
    - 驗證：
      1. 語意：回傳值為物件，含 `user` 與 `rules` 兩鍵；`user.id` 對應該 token 使用者、`user` 含 `grupsNames` 字串；`rules` 為陣列、各元素含 `name` 與 `isActive`。
      2. 視覺：純 API 無 UI 終態，無 pixel baseline。
    - 雙語：本流程為 API、回傳不含 i18n 文案，僅跑一輪。
    - 清理：本案唯讀，不改 DB，無需清理。

- **E2E-002**
  - title: 以 perm() 工廠 conn 載入後用 active 查詢單一規則
  - description: 驗證瀏覽器應用以 `perm()` 取得 SDK，`conn(url)`（url 已帶妥 token）載入成功後，`getUser()` / `getRules()` 回傳與 E2E-001 相同的 `user` / `rules`，且 `active(key)` 對既有規則名回傳 `'y'`（規則 `isActive='y'`）或 `'n'`（其餘 / 不存在）。屬 SDK 快取查詢成功案例。
  - flow:
    - 測試資料：base seed client 使用者與有效 token；該使用者至少一條 `isActive='y'` 規則與一個不存在的規則名。
    - 操作：`let p = perm()` → `await p.conn(url)` → 呼叫 `p.getUser()` / `p.getRules()` / `p.active(知名規則名)` / `p.active(不存在規則名)`。
    - 驗證：
      1. 語意：`getUser()` 回傳物件含該使用者 `id`；`getRules()` 回傳陣列；`active(已啟用規則名)` 回 `'y'`；`active(不存在規則名)` 回 `'n'`。
      2. 視覺：純 API 無 UI 終態，無 pixel baseline。
    - 雙語：API 流程，僅跑一輪。
    - 清理：本案唯讀，不改 DB，無需清理。

- **E2E-003**
  - title: token 無效時查詢被拒
  - description: 驗證以無效 / 偽造 / 過期 token 呼叫 `getPerm`，後端 `getAndVerifyClientUser` 反查不到對應 client 使用者，core reject，`pm2resolve` 將 `state` 設為 `'error'`；前端 `getPerm.mjs` 偵測 `state !== 'success'` 後 reject。屬 token 守門失敗案例，與 E2E-001 共同覆蓋成敗分支。
  - flow:
    - 測試資料：一組不對應任何有效 client 使用者的 token 字串。
    - 操作：以該無效 token 呼叫 `getPerm(url, tokenTar)`。
    - 驗證：
      1. 語意：`getPerm` 回傳的 Promise 被 reject，reject 值為 `cannotGetUserDataByUrl`（後端 `state='error'` 觸發）；未取得 `user` / `rules`。
      2. 視覺：純 API 無 UI 終態，無 pixel baseline。
    - 雙語：API 流程，僅跑一輪。
    - 清理：本案被拒未寫 DB，無需清理。

- **E2E-004**
  - title: url 缺少 token 佔位符時前端即拒
  - description: 驗證呼叫 `getPerm` 時若傳入的 url 不含 `token={token}` 佔位符，`getPerm.mjs` 在送出 axios 請求「之前」即 reject，不打後端。屬前端參數前置檢查攔截案例。
  - flow:
    - 測試資料：一個合法但不含 `token={token}` 的 url（如 `http://host/api/getPerm`）與任意 tokenTar。
    - 操作：以該 url 呼叫 `getPerm(url, tokenTar)`。
    - 驗證：
      1. 語意：`getPerm` 回傳的 Promise 被 reject，reject 值為 `noTokenInUrl`；無後端請求發出。
      2. 視覺：純 API 無 UI 終態，無 pixel baseline。
    - 雙語：API 流程，僅跑一輪。
    - 清理：本案前端即拒，無需清理。

- **E2E-005**
  - title: 提供 funConvertPerm 時回傳值經轉換
  - description: 驗證呼叫 `getPerm` 時於 `opt.funConvertPerm` 傳入轉換函式，後端回傳的 `{ user, rules }` 物件會先經該函式（同步或回 Promise 皆支援）轉換後才回傳；轉換後仍須為有效物件，否則 reject；轉換函式同步拋錯或 reject 亦 reject `noUserDataAfterConvert`（2026-09-25 起，原為部署方錯誤原樣上拋，見 ADR-023）。屬回傳值客製轉換案例。
  - flow:
    - 測試資料：base seed client 使用者與有效 token；一個將回傳物件加上自訂欄位（仍為有效物件）的 `funConvertPerm`。
    - 操作：以 `getPerm(url, tokenTar, { funConvertPerm })` 呼叫。
    - 驗證：
      1. 語意：回傳值為經 `funConvertPerm` 轉換後的物件（含自訂欄位）；若 `funConvertPerm` 回非物件、同步拋錯或 reject，`getPerm` reject、值為 `noUserDataAfterConvert`（不上拋部署方之錯誤原文）。
      2. 視覺：純 API 無 UI 終態，無 pixel baseline。
    - 雙語：API 流程，僅跑一輪。
    - 清理：本案唯讀，不改 DB，無需清理。

- **E2E-006**
  - title: url 或 tokenTar 為無效引數時前端前置檢查即拒
  - description: 驗證呼叫 `getPerm` 時若傳入的 url 非字串（如空字串）或 tokenTar 非字串（如空字串），`getPerm.mjs` 在替換佔位符與送出 axios 請求「之前」的最前置參數型別檢查即 reject，分別回 `invalidUrl` / `invalidTokenTar`（`getPerm.mjs:getPerm`），不打後端。屬前端引數型別前置攔截案例，守門點早於 E2E-004 的佔位符檢查（型別檢查在替換佔位符之前）。
  - flow:
    - 測試資料：一個空字串 url（搭有效 tokenTar）與一個空字串 tokenTar（搭合法含佔位符 url）兩組無效引數。
    - 操作：分別以 `getPerm('', tokenTar)` 與 `getPerm(url, '')` 呼叫。
    - 驗證：
      1. 語意：空 url 組 `getPerm` reject、值為 `invalidUrl`；空 tokenTar 組 reject、值為 `invalidTokenTar`；皆無後端請求發出。
      2. 視覺：純 API 無 UI 終態，無 pixel baseline。
    - 雙語：API 流程，僅跑一輪。
    - 清理：本案前端即拒，無需清理。

- **E2E-007**
  - title: 對應鍵命中多位有效使用者時查詢被拒
  - description: 權限系統的對應鍵設定為 email 或 name，也就是以電子郵件或名稱對應外部系統的使用者時，若權限系統中有兩位以上啟用中的使用者符合同一個值，系統無法確定發起查詢的是哪一位，伺服器一律拒絕、不會任取其中一位：查詢權限的回應 state 為「error」、msg 為「ambiguousUserFromPerm」，同一個使用者的登入與資料存取也同樣被拒。呼叫端使用 getPerm 輔助函式時，任何非成功的回應一律回報為「cannotGetUserDataByUrl」。符合的使用者只剩一位後即恢復正常；完全沒有符合者仍回報「cannotGetUserFromPerm」。管理者請先排除重複的使用者資料。
  - flow:
    - 測試資料：base seed；後端先以預設對應鍵（id）重啟，經同步端點推送一位啟用中的使用者，電子郵件與 base seed 的 `admin@example.com` 相同；再以臨時設定重啟為 `mappingBy: 'email'`（資料庫保留）。
    - 操作：以 token `sys`（對應電子郵件 `admin@example.com`）請求 `/api/getPerm`、`/api/getUserByToken` 與資料通道 `users.select`；之後以同步端點把重複之使用者改為不同電子郵件，再請求一次；另以不在權限系統使用者表之 app token 請求 `/api/getUserByToken`。
    - 驗證：
      1. 語意：命中 2 位時 `/api/getPerm` 與 `/api/getUserByToken` 回 `state='error'`、`msg` 為 `ambiguousUserFromPerm`（回應不含電子郵件）；資料通道回傳輸層 `permission denied`。
      2. 語意：重複排除後三者皆成功；app token（0 位符合）回 `msg` 為 `cannotGetUserFromPerm`。
      3. 視覺：純 API 無 UI 終態，無 pixel baseline（瀏覽器登入被拒時僅轉址，見 `流程_應用啟動與登入.md` E2E-006，e2e 待補）。
    - 雙語：API 流程，僅跑一輪；`ambiguousUserFromPerm` 於 `server/procLang.mjs` 有 eng + cht 定義。
    - 清理：測試收尾刪除同步推送之 `from`、還原 `./settings.json` 並重建 base seed。
    - 備註：規則帳本 R-MAPKEY-02（F-14，ADR-034）；判定單一擁有者 `server/keyCheck.mjs:pickUniqueUser`，`getTokenUser` 於多筆時 srLog 記 `getTokenUser-error`（`msg:'ambiguousUserFromPerm'`、`mappingBy`、`count`），不記對應值。修正前取首筆，登入者身分取決於資料庫列序。測試：`api-mapKey` MK-010、MK-011（`getPerm` 另有本案之 HTTP 層斷言）、`unit-keyCheck` KC-PU-*。

## 回傳結構邊界

| 概念 | 內容 | 來源 |
|---|---|---|
| 後端 HTTP body | `{ state, msg }`：`state` ∈ `'success'` / `'error'` / `'cancelled'`；成功時 `msg` = `{ user, rules }`，失敗時 `msg` = 錯誤 key | `pm2resolve` 統一包裝（`WWebPerm.mjs:apis(/api/getPerm)`） |
| `user` | `{ ...userFind, grupsNames }`：原使用者欄位加上 `grupsNames`（僅 `isActive='y'` 群組名以 `;` 串接） | `getGenUserAndRulesByUserId`（`WWebPerm.mjs:getGenUserAndRulesByUserId`） |
| `rules` | 規則陣列，各元素含 `name`、`isActive`（`'y'` / `'n'`）等 | `getUserRules` 計算結果（`WWebPerm.mjs:getGenUserAndRulesByUserId`） |
| `getPerm` 回傳 | 成功回 `ur`（即 `msg` 物件，或經 `funConvertPerm` 轉換後物件）；失敗回 reject key | `src/getPerm.mjs:getPerm` |
| `perm()` 快取 | `conn` 成功後將 `pmd` 拆為 `_user`（`pmd.user`）/ `_rules`（`pmd.rules`）/ `_kpRule`（`{ ruleName: isActive }`），供 `getUser` / `getRules` / `active` 讀取 | `src/perm.mjs:perm.conn`（`genUser` / `genRules` / `genKpRule`） |
| `active(key)` | 讀 `_kpRule[key]`，值為 `'y'` 才回 `'y'`，其餘（含 key 不存在）回 `'n'` | `src/perm.mjs:perm.active` |

## i18n 訊息粒度規則

本流程為 server-side 查詢 API，回傳 `{ state, msg }` 為**機器可讀值**（`state` ∈ `'success'` / `'error'` / `'cancelled'`，成功時 `msg` = `{ user, rules }` 物件、失敗時 `msg` 為 camelCase 錯誤 key）。後端 reject key（如 `tokenNoPermission` / `userNoPermission` / `cannotFindUserFromToken` / `cannotGetUserRules`）於 `server/procLang.mjs` 皆有 eng + cht 定義；前端 SDK 自身 reject 的 key（如 `noTokenInUrl` / `cannotGetUserByUrl` / `cannotGetUserDataByUrl` / `noUserDataByUrl` / `noUserDataAfterConvert`）亦於 `procLang.mjs` 有 eng + cht 定義。由呼叫端應用以 key 查 lang 決定如何呈現。故本流程訊息粒度即「一個 reject key 對應一條 procLang 雙語訊息」。

## 參數來源

| 概念 | 來源 | 流程影響 |
|---|---|---|
| `url` | 呼叫端傳入，須含 `token={token}` 佔位符 | `getPerm.mjs` 缺佔位符即前端 reject（`getPerm.mjs:getPerm`）；`{token}` 由 `encodeURIComponent(tokenTar)` 代入後以 fetch 送出 |
| `tokenTar` | 呼叫端傳入的當前使用者 token | 經 `encodeURIComponent` 代入 url 作為 `?token=` query（伺服端解出原值）；後端據此於 `getAndVerifyClientUser` 反查發起者使用者 |
| `opt.funConvertPerm` | 呼叫端可選傳入的轉換函式 | 後端回傳物件先經此函式轉換後才回傳；轉換後須為有效物件，拋錯或 reject 視同轉換失敗（`getPerm.mjs:getPerm`） |
| token → 使用者 | 後端外部 `getUserByToken` + perm `users` 表（依 `mappingBy`，預設 `id`，可選 `email` / `name`）反查正規化（`WWebPerm.mjs:getTokenUser`） | 解出 `userIdSelf` 作為 `getGenUserAndRulesByUserId` 查權限的依據 |
| `verifyClientUser` | 部署方提供的識別函式 | 判定 token 對應使用者是否為合法瀏覽（client）使用者；不通過即 reject（`WWebPerm.mjs:getAndVerifyClientUser`） |
| 群組 / 權限 / 目標 | perm `grups` / `pemis` / `targets` 三表 | 由 `getUserRules` 合併計算出 `rules` 與有效 `grupsNames` |

## spec 規則摘要

- **權限**：`/api/getPerm` 守門點為 handler `core()` 內以 `req.query.token` 經 `getAndVerifyClientUser`（`getUserByToken` 反查 + perm `users` 表正規化 + `verifyClientUser` 部署方識別）；token 無效 / 非 client 使用者 / 查無使用者一律 reject，`state` 回 `'error'`。**僅限 client（瀏覽）使用者，不接受 app 使用者**（`WWebPerm.mjs:apis(/api/getPerm).core` 呼叫 `getAndVerifyClientUser`）。
- **對應鍵須唯一（F-14，ADR-034，2026-10-21 起）**：`getTokenUser` 以 `mappingBy` 指定欄位於 perm `users` 查 `isActive='y'` 之使用者，命中 0 筆回 `cannotGetUserFromPerm`、恰 1 筆採用、**多於 1 筆回 `ambiguousUserFromPerm`**（不取首筆，見 E2E-007）；外部同步端在 `mappingBy` 為 `email`／`name` 時已檢查啟用使用者之對應鍵（`流程_外部應用同步權限資料.md` E2E-024～026），但 `mappingBy='id'` 時同步不檢查，歷史或他途造成之重複仍由本步兜底；後台 users 清單原只檢查 `email` 且不檢查 `name`，2026-10-21 run05（ADR-035 決定 h）起改為：任何 `mappingBy` 下 `email` 只擋本次造成或觸及之空值／重複（歷史既有者不擋），`mappingBy` 為 `'name'`（或 `'email'`）時另對啟用列之該欄位檢查非空與唯一（只擋本次造成或觸及者，見 `流程_後台使用者清單.md` E2E-016），故後台清單不再「造出」新的對應鍵重複，但歷史既有者仍由本步兜底。
- **注入函數失敗（W 契約，ADR-023）**：`getUserByToken` 拋錯或 reject ≡ 查無使用者（`cannotFindUserFromToken`）；`verifyClientUser` 拋錯或 reject ≡ 不通過（`userNoPermission`）。上游錯誤原文不回應、不入 log，srLog 另記 warn `inject-<函數名>-fail`。
- **代入**：`tokenTar` 經 `encodeURIComponent` 以 split / join 代入 `{token}`（`getPerm.mjs:getPerm`），不用 `replaceAll`；伺服端解出之值與原值相同，UUID、英數與 `-_.~` 之線上格式不變。
- **查詢對象**：本端點固定查「token 自身所屬」使用者權限（`userSelf` → `userIdSelf`），呼叫端不可指定他人 userId。
- **回傳契約**：後端一律以 `pm2resolve` 回 `{ state, msg }`；前端 `getPerm.mjs` 以 `state === 'success'` 判成敗，成功取 `msg` 為 `{ user, rules }`，失敗 reject。
- **邊界**：
  - `url` 必含 `token={token}` 佔位符，否則 `getPerm` 在送請求前即 reject（前端前置檢查）。
  - `funConvertPerm` 為可選；提供時回傳物件先經其轉換，轉換結果須為有效物件才 resolve；轉換函式同步拋錯或 reject 一律 reject `noUserDataAfterConvert`。
  - `grupsNames` 僅納入 `isActive='y'` 且在群組表中查得的群組名（引用查無〔懸空〕之群組不列入，雖其仍以空內容參與授權合併，見 `流程_權限規則合併計算.md` E2E-017；2026-10-21 run05 補載）；`rules` 內各規則自帶 `isActive`，`perm().active(key)` 以此回 `'y'` / `'n'`。
  - `getUserRules` 的規則合併計算細節屬權限規則合併計算流程，本文件不展開。
- **契約**：前端 `getPerm` 以 `errTemp` 旗標短路 fetch 連線層錯誤；後端 `core()` 經 `pm2resolve` 將 resolve / reject 統一轉為 `{ state, msg }` 供前端判讀。`perm().conn` 為同源 fetch 取得後拆快取（`_user` / `_rules` / `_kpRule`）的薄封裝，成功 `permSuccess` / 失敗 `permError` 回呼可選；失敗物件 `{ kind, status, message }` 之 `message` 只含例外名稱與代碼（如 `TypeError ECONNREFUSED`）或 `HTTP <status>`，不含網址與回應本體（ADR-023）。

## 已知落差

- **設計事實（記錄備查；spec 原載更正）** 2026-10-21：本 spec〈參數來源〉原載「perm `users` 表（依 `mappingBy`，預設 `email`）」不成立：讀碼，`server/WWebPerm.mjs` 之 `WWebPerm` 建構參數 `opt.mappingBy` 僅在值為 `'id'` / `'email'` / `'name'` 時採用，**未給或非此三者時為 `'id'`**（JSDoc 預設 `'id'`；`getTokenUser` 以該欄位值於 perm `users` 表查找 `isActive:'y'` 之使用者）。已改該句。
- **設計事實（記錄備查；spec 原載更正）** 2026-10-21（F-14，ADR-034；使用者 2026-10-21 核可）：〈執行流程〉`020` 原只載「外部 getUserByToken 反查 + perm users 表正規化」，未載對應鍵命中筆數之處置；現況（修前取首筆 `get(userFind, 0, null)`，修後經 `pickUniqueUser`）：命中多於 1 筆回 `ambiguousUserFromPerm`。已補 `020a`、規則摘要與 E2E-007。證據：`server/WWebPerm.mjs:getTokenUser`、`server/keyCheck.mjs:pickUniqueUser`；測試 `api-mapKey` MK-010／MK-011（修前於未改之程式碼重跑為紅：命中 2 筆仍登入成功）。
