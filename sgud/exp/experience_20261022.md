## e2e 側欄 launch 級 1px 剛性位移(2026-08-25 ~ 2026-09-01, ADR-020)

- **症狀**: 全量重產後 e2e 間歇失敗(每輪 130+ 張中 1~3 張, 全在 eng), 左側選單整體水平位移 1px, diff 固定 3634~3635px; 逐像素驗證 `capture(x,y)==baseline(x+1,y)` 零失配 → 同一份已光柵化 bitmap 被合成到偏左 1px, 非字形重畫、非 DOM layout、非 scrollLeft.
- **根因**: 上游 `w-component-vue` `WPanelScrollyCore.vue` 捲動殼寬 `calc(100% + (nativeBarWidth+1)px)`, headless 下 overlay 捲軸 `nativeBarWidth=0`, 懸出恰 1px 被外層 `overflow-x:hidden` 裁切; 軟體合成器對懸出層之對齊二選一(左緣貼齊＝正常, 右緣貼齊＝整層左移 1px), 於 launch 初始化決定一次. 實測 `+1` 時捲動殼 200 / 裁切殼 199, 改 `+0` 後 199/199 且逐像素 0 差異. 位移量＝懸出量方程式與 w-web-api WTree 6px 先例同族.
- **修法**: 上游 2.5.3 為 `+1`, **2.5.4 起移除**(npm tarball 逐版比對確認), 本專案升 2.5.6 後全量重產 324 張並全綠; e2e 端保留六旗標確定性渲染組 + sharp 疊圖紅框 + per-case fresh browser 作防護.
- **代價與教訓**: 三輪調查; 期間 `E2E_BARE=1 --baseline` 曾覆寫 46 張正式 baseline 為無旗標版導致整輪全紅; 診斷閘門(`E2E_BARE` / `E2E_DIAG` / `E2E_DIAG2`)於 2026-09-01 全部拆除. 詳細方法論已沉澱至全域技能[role-coder-for-test-e2e] references(pixel-mismatch-diagnosis / research-review-discipline).

- **儲存鈕殘留**: 儲存成功後伺服器推播 → `changeParams` 重算 → `genOpt` 重建 opt → ag-grid 非同步 `rowsChange` 把 `isModified` 設回 true; 既有 `firstLoading`/`firstSetting` 只擋初始化. 修法對齊 w-web-sso 之 `markDataReload`(收斂於 `$ui.markDataReload`, 四清單頁 genOpt 標記 + 守門 `systemProcing`), 旗標時窗 nextTick+1ms 實測足夠(modal 期間與關閉後 5.5s 皆 false). Ve* 對話框 items 於 show() 一次生成且儲存即關閉, 無此路徑, 不加旗標. **既有標準圖曾把殘留的紅色儲存鈕凍結進所有「儲存成功 modal」圖**, 修正後該批需重產並審圖.
- **i18n 鍵名**: `operMode`(文字「是否使用」)/`operPemiEnable`/`operGrupEnable`(文字「合併…模式」)鍵名與文字交叉, 改為 `operEnable` / `operPemiMode` / `operGrupMode`; 以 `kpLangExt` 覆寫這三鍵之部署須改鍵名(breaking).

## w-aggrid-vue 升版之焦點框修正(2026-09-16, 2.0.86 → 2.0.87)

- **變更內容**: 全套件 src 僅 `WAggridVue.vue` 一處 CSS——`.no-border.ag-cell:focus` 加上 `:focus-within` 並列(依賴無異動)。ag-grid 31 之焦點框規則為 `.ag-cell-focus:focus-within`, 儲存格內子控制項(button / tabindex 元素 / input)取得焦點時, 儲存格只符合 `:focus-within` 不符合 `:focus`, 故舊版對 `kpHeadFocusHighlight:false` 之欄「擋不住」按鈕聚焦時的藍框。
- **本專案命中處**: 五個元件設 `kpHeadFocusHighlight:false`——三個清單頁之開窗按鈕欄(Users `cgrups` / Grups `belongUsers`,`cpemis` / Pemis `belongGrups`,`crules`)與兩個對話框之唯讀徽章欄(VeGrupBlngUsers `grupsNames` / VePemiBlngGrups `pemisNames`)。按鈕欄受惠於本次修正; 徽章欄無可聚焦元素, 不受影響。各處原註解「雖然效果不完全…」即指此缺陷, 已於本次改寫(§2.1 第 5 條: 既有註解不得原樣繼承)。
- **實測**(tmp/probe-focus2.mjs, 同頁以 CSSOM 停用 `:focus-within` 規則作新舊對照): button 取得焦點時, 舊版 cell `border-color: rgb(0, 145, 234)`(藍框), 新版 `rgba(0, 0, 0, 0)`(透明)。鍵盤連按 25 次 Tab 即可停在 `cgrups` 欄 gridcell, 屬真人可達路徑, 故為實質視覺修復。
- **e2e-init 與 `dist/index.tmp`／`dist/index.html`**: `dist/index.tmp` **受版控**, 是業主發布管線之產物(`script.txt`: `npm run build` → `node toolg/genEntry.mjs` 把 `/mperm/` 改成 `{sfd}/` 寫成 index.tmp **並刪除 index.html**); `dist/index.html` 則是後端啟動時由模板代換出的執行期檔(`server/WWebPerm.mjs:710-737`, 未受版控). e2e-init 之 `ensureIndexTmpl` 自 2026-09-16 起改為**只驗不寫**: 模板缺檔或缺任一佔位符即拋錯(訊息指引 `git checkout -- dist/index.tmp` 或依 script.txt 重產), 不再讀 index.html, 故舊經驗「業主途中重建 dist 會報 dist/index.html 不存在」已不再發生. 判讀 e2e-init 失敗時先看 `ls -la --time-style=full-iso dist/` 之時間戳.
- **對標準圖無影響**(重要): e2e 以滑鼠 `click()` 點開窗按鈕後, `document.activeElement` 實測恆為 BODY(點擊前 / 對話框開啟中 / 對話框關閉後三個時點皆是), 儲存格從未進入 `focus-within`, 故 338 張標準圖零差異, 全量 e2e 亦全綠。**判準**: CSS 類升版是否動到標準圖, 取決於「e2e 走到的狀態是否落在該選擇器內」, 不能只看選擇器有沒有命中本專案的欄。

## 權杖外洩修正(2026-09-25, ADR-023; 四 repo 方案見 w-web-sso ADR-068)

- **ADR-016 之「srLog 不記 token」是只看欄位名的查證**: 當時查的是「各 srLog 呼叫有沒有 token 欄位」, 沒追欄位**值**從哪來——`referer` 就是含 `?token=` 之完整網址(本設計以 `?token=` 開站), `verifyConn-error` 之 `msg` 就是上游 reject 原文(含介接權杖). **判準**: 宣稱「log 不含某類資料」前, 逐一追每個欄位值之來源(請求標頭、上游錯誤、使用者輸入), 並以合成秘密實際打一輪、讀回 log 檔確認; 探測與測試之 log 讀取一律以 `time ≥ 本次起點` 篩行, 否則前一輪(含紅燈那一輪)之外洩行會讓綠燈永遠紅.
- **紅燈要落在正確通道**: 重複 token 參數(Hapi 解析為陣列)在 perm 只經 console(stdout)外洩, HTTP 回應與 srLog 修正前後都一樣乾淨; 而 api harness 之 `spawnSrv` 丟棄後端 stdout, api 層斷言這條必然「修正前就綠」. 改以兩層守護: 靜態站點不變式(`unit-maskLog` SITE-*, 修正前列出恰為規格所列 22 處)＋隔離後端探測(真 srv.mjs、另埠 / cwd / db / logs, 讀 stdout 檔). 同理 `api-tokenSafety` 每個 `it` 都含至少一條修正前會紅之斷言, 並把問題收集成清單一次斷言(紅燈 log 一次看全, 不是只看到第一個失敗).
- **靜態掃描器本身先驗鑑別力**: 第一版 WRAP-SITE-002 把行尾註解「…getUserByToken為w-ui-loginout預設值」當成直接使用; SITE-001 把字串標籤 `'req.query'` 當成 `req.query`. 兩者都是在「修正後仍紅」時才發現. 修掉後以最終版掃描器掃 HEAD(修正前)與工作樹: HEAD 22 + 1 + 1 + 1 處、工作樹 0——兩端都驗才算掃描器可信(`tmp` 內 `perm-scan-head.mjs` 之作法: `git show HEAD:<檔>` 落暫存檔再掃).
- **既有測試凍結了缺陷行為**: `api-getPermUserInfor` 002 之「對照子斷言」明文斷言「只缺 userId 佔位符時不走缺佔位符 reject」——把 `&&` 之缺陷寫成了契約; `unit-fetchJson-sdk` FJ-011 斷言大括號原樣送出(線上格式), 而規格改為一律 `encodeURIComponent`. 處置: 先以舊斷言對新碼實跑確認「只有線上格式不同、伺服端解出值相同」, 再改斷言為新契約(並保留解出值之斷言), 於 ADR 列出. **判準**: 測試斷言「不應 reject / 應原樣」之類的反向或格式斷言時, 先問它守的是需求還是當時的實作.
- **注入函數測試權杖需要資料前置**: `{token-for-verify-throw}` 走 client 通道(`/api/getUserByToken`、`/api/getPerm`、資料通道)時會先反查 perm users 表(`mappingBy` 未設時程式預設為 `id`), 表內無此 id 則在 `cannotGetUserFromPerm` 就結束, 根本走不到 `verifyClientUser`——測試會「修正前就綠」而空驗. 故 before 經 `/syncAndReplaceTabs` 以專用 `from` 插入、after 以 `delAll({from})` 清除(同 api-syncAndReplaceTabs 慣例); app 通道(`getPermUserInfor`、`syncAndReplaceTabs`)不反查, 不需前置.
- **srLog 經 pino transport 非同步落檔, 等待要有哨兵**: 讀不到行不代表沒外洩. 以「本次唯一值」之事件當哨兵(`/syncAndReplaceTabs?keyTable=<唯一值>` 會把 keyTable 記入 srLog), 同一行程之 srLog 依呼叫序落檔, 見哨兵即前面各行已落; 30 秒內未見哨兵即判「log 未落檔或 logFd 不符」而失敗, 不讓空集合通過負向斷言.

## 按鈕雙擊防護補齊(2026-09-29, ADR-025; 四 repo 方案見 w-web-sso ADR-074)

- **本專案驗證失敗之早退路徑不開 loading**(ADR-012 頁面層 canonical): 按鈕鎖若只在 `updateLoading(false)` 釋放, 這些路徑之訊息框背後儲存鈕會一直轉圈(e2e grups / pemis `errInNames`、targets `errInIds` / `targetAddEmpty` 之訊息框圖皆拍得到工具列). 解法用 `runSubmit` 交給流程之 `unlockBtn()` 於開框前只釋放本次按鈕鎖, 不借 `updateLoading(false)`(未開 loading 時語意不符, 且會釋放所有進行中流程之鎖).
- **ADR-012 之「同表並行皆 success」原以同一 `sys` 驗**: 加依操作者占位後同一操作者之第 2 次改為 `saveInProgress`, 故 `api-doubleclick` DC-01～04 改兩位操作者. 第二位沿用 `{token-for-application}`, 但資料通道反查 perm users 表(mappingBy 未設時為 `id`)且 `verifyClientUser` 讀的是 **perm 列**之 `isAdmin`(不是權杖宣稱之值), 故須插入 `isAdmin='y'`、`isActive='y'` 之列; users 表之快照與每案復原都要含該列, 否則第一個 users 案例就把第二位操作者刪掉. 殘留會使 `api-verifyConn-auth` 之「app 權杖走 client 通道應拒」失敗, after 以 base seed 還原並 `delAll({from})` 兜底.
- **後端判定邏輯可在單元層驗**(不起服務): 真實 `procCore` + `pmKeyMutex` + `cacheSt`/`lockSave` + w-serv-orm `getMapOrm`(真 adjustData)+ 記憶體資料表(insert 同 `ifNoExists`、save 同合併或插入); `lockSave` 之占位於呼叫當下同步取得, 兩個未 await 之呼叫即可穩定重現「處理中再送出」, 不需延遲. 以 `git show HEAD:server/procCore.mjs` 暫換回舊版對照: 依賴新防護之 6 案失敗、其餘 4 案通過, 即測試有鑑別力(換回後 `cmp` 確認還原).

- **儲存成功後清單由推播重建**(`WServHapiClient` 之 recvData → store → `changeParams` → `genOpt`), 非儲存後主動重取(異於 w-web-sso 之 `getUsersList`): 推播到達前清單仍是送出前之列(含 `_isNew`), 此窗口內再修改並儲存會得 `saveNewRowExists`(訊息指示重新整理), 屬 ADR-025 列明之取捨.
- **「新增列已存在即拒」遇到 id 可編輯之表會誤擋**(主代理審查時發現): 標的表之 id 為可就地改寫之路徑, 「刪除標的 X 並把新增列之 id 改成 X」後儲存, 被當成重送而回 `saveNewRowExists`——訊息要人重新整理, 但照做後重做同一操作仍被擋, 使用者無從完成. 子代理把它記成「可改用直接編輯」之取捨, 實為 UI 可達之缺陷. 判準: 新加一道拒絕規則時, 逐表問「使用者能否用正常操作造出觸發條件」(此處: 哪些表之 id 欄可編輯, `kpCellEditable` 含 `'id'` 者), 能造出者要嘛讓它不被觸發(送出前 `reuseDeletedIds` 正規化為修改), 要嘛讓訊息指出真正可行之做法; 不能只寫進 ADR 之「取捨」.
- **換行判讀不可用 Git Bash 之 `grep $'\r'`**: 其 grep 預設剝除行尾 CR(`-U` 才保留), CRLF 檔會被判成 LF. 本專案工作樹換行本就混雜(HEAD blob 皆 LF、`core.autocrlf=true`; 如 `mUI.mjs`、四個清單頁、`VeCrules`、`CheckYes*`、`WWebPerm.mjs` 為 CRLF, `procCore`、`procLang`、其餘 Ve* 為 LF), 編輯工具會保留各檔原換行. 我一度依誤判把 7 個 CRLF 檔「還原」成 LF, 後以 `tr -cd '\r' < 檔 | wc -c` 計數更正並改回. `git diff` 因 autocrlf 正規化看不出換行變動, 判讀一律以位元組計數為準.

## 授權查值不得解析路徑(R-AUTH-PATH-01, 2026-10-20 run02, ADR-029 Update; 主控 run01 複審裁示)

- **lodash `get` 的路徑語意是授權缺陷**: 精確鍵優先(`'A.0' in obj` 為真就直接取), 其餘才逐段解析——所以「只授權 `A`」時 `get(kp, 'A.0')` 取 `'y'[0]` 得 `'y'`、`'A.length'` 得數字 `1`、`'toString'` 得繼承函數. 影響面不只 `getUserRules`: 外部 SDK `perm.active`、編輯對話框 `VeCrules／VeCgrups／VeCpemis` 顯示既有狀態(顯示為已啟用 → 存檔即寫入真授權)、`mergePickKeysOnly` 之歸屬比對皆同型. 盤點方式: Grep `\b(get|has|set|unset|update)\(` 第二參非字面值者, 逐站判鍵為「常數／索引／伺服端定義」或「使用端 id／名稱」(結果見帳本站點 30; 後者才改 `getOwn`).
- **以使用者資料為鍵之容器要無原型, 且別讓 lodash `cloneDeep` 經手**: 一般物件對 `kp['__proto__'] = 'y'`(字串指派)靜默忽略, `'x' in {}` 對 `constructor／toString` 為真; `cloneDeep` 會把 `Object.create(null)` 複製成一般物件而前功盡棄(`objAND` 改淺複製入無原型容器). 輸出若是外部應用慣用之物件(`perm.getKpRule()`)則不改型別, 改以 `Object.defineProperty` 設自有屬性.
- **測試表示 `__proto__` 的做法**: 一般物件做 map 無法表示 `__proto__` 鍵, 斷言改比對 `name=isActive` 串接字串(UNIT-AP-*), 或以 `Object.defineProperty` 建立期望物件.
- **Bash 以 `node -e "…"` 寫入含反引號、`$`、換行跳脫的程式碼會被 shell 展開而靜默壞掉**(本輪兩次: 範本字串被置空、腳本被拆行): 要改的檔案一律用 Write／Edit 工具或先 Write 成腳本檔再執行.
- **repo 內檔案為 CRLF**: 以字串比對做文字替換的腳本要先把 `\r\n` 正規化再還原(`make-prerun02.mjs` 為例); Edit 工具則自動保留.
- **磁碟**: C: 槽餘量降到 1 GB 以下時 e2e 會 `ENOSPC`(run01 最終全跑 stainfor 2 個失敗); 外審副本勿複製 `node_modules`, 副本放 repo 之 `tmp/` 下由上層 `node_modules` 自動解析即可.
- **查值站點修完不等於授權語意對稱(run03 sol 外審)**: 同一份 JSON 有「伺服端解碼」與「編輯器讀取」兩條讀路徑時, 只修查值函數仍會留下顯示與授權不一致——解碼規則(物件形式以外層鍵為名／值內 `name` 覆蓋、值為物件時取 `isActive`、陣列形式以元素 `name` 為名)須在伺服端與編輯器共用同一份(`getRuleEnable`), 新增格式相容時兩端同改. 盤點「顯示什麼就存什麼、存什麼就授權什麼」要逐格式(字串值／物件值／陣列形式)與逐名稱類別(一般／含 `.`／原型鍵名)做矩陣.
- **「空白列」判準別只看欄位是否為空字串**: 同步列映射後, 會被伺服器覆寫之欄位(`userId`、`timeCreate`…)與空容器(`[]`、`{}`)都不是內容; 定義成「有內容的欄位＝非空字串／有限數字／布林」比列舉「哪些算空」穩.

- **新增「改動全表」的測試檔要自己收尾, 且收尾要保列序與原文**(`e2e-array-form` 先後踩兩個坑): ①`<table>.select` 回傳依**主鍵**排序(users 為 admin／john／mary／peter), 而 `updateXxx` 以**陣列位置**重給 `order`——收尾若直接把 select 結果送回, users 列序反轉(base seed 為 peter／mary／john／admin), 後續 e2e 檔擷取之 `BASE_SEED` 列序與標準圖相反(即「多檔合跑之後端狀態污染」節的「列序相反」現象; 原誤標 ADR-017); 須先依 `order` 排序再送; ②收尾與擷取要對稱(`before` 讀三表現況、`after` 原樣寫回), 而不是「濾掉自己的列」——被 UI 存檔過的 base 列其 `cgrups` 原文會被重新序列化. 驗證用「每檔起點各表內容摘要」(`tmp/run89/snap-abort.mjs`, `SNAP_FIELDS=1` 逐欄位摘要): 修後唯一差異欄位是 `order`(全新種子為 0 起算 peter:0…admin:3, 任何 UI `updateXxx` 後為 1 起算)——這是既有 e2e 一律會發生的正規化(各檔 `resetDb` 皆然), 非本檔遺留.
- **外審(sol＋minimax)在第一版解碼上各找出 2 個高嚴重度——「fail-closed」要先問「對哪個運算而言」**: ①陣列形式缺 `mode` 之啟用元素, 伺服端不納入合併(不授權), 第一版編輯器卻因改讀陣列而顯示啟用、存檔補預設 OR 而**增權**(而我在帳本把它歸為「物件形式亦然, 非本輪引入」——對物件形式成立、對陣列形式是本輪新引入); ②同名 AND／OR 並存, 取末項或「停用」皆增權: `mergeRules` 對 OR 聯集單調(捨去 OR 支只會變小), 但 AND 是限制(停用/捨去 AND 支反而使結果變大)。所以「停用有疑義者」不一定是 fail-closed; 保留 AND 支、捨 OR 支才是。**這類單調性與順序依賴, 手排幾個案例找不全**: 把「元素字母表 × 長度 ≤ 3」全窮舉(`unit-cvKpToObj` PR-001, 4369 組, 約 0.3 秒)並以 `getUserRules` 為真理, 一次就找出第三個我沒想到的——**`objAND` 依群組順序**(AND 合併對後者獨有之鍵設 n、對前者獨有之鍵不動, 結果因順序而異), 編輯器存檔依對話框順序重寫鍵, 故兩個以上 AND 群組且規則集不同時任何存檔(物件形式亦然)都可能改變授權——既有、非本輪引入, 窮舉中計數略過並寫入限制。性質測試要先寫「期望性質」(相等／不增), 讓違反的組合自己現形, 不要先替每個組合手寫預期。
- **外審的「過度概括」類意見要逐條回頭改文字與測試**(minimax#3、sol#7): 「存檔輸出維持物件形式」對兩個關聯對話框不成立(`isEqual` 為真時原字串不動), 我的 e2e 斷言「存出須為物件形式」是靠夾具多帶一個停用元素才成立——夾具形狀換來的綠燈。改為: 直接編輯器斷言物件形式, 關聯對話框斷言「授權不變、不含不應啟用之名稱」。守門只比筆數(minimax#4、sol#1)、靜態不變式只計次數不驗位置與條件(sol#2)同屬此型: 守門與不變式要附「判定器自測」(`LC-002b`、`SITE-NS-001b`, 以條件包覆、單行 if、缺 after 等反例證明判定器會紅), 否則「測試宣稱的不變式強於實際檢查」。
- **web 測試鎖**: `quiet-run --lock` 被 `taskkill /F /T` 強殺後會留下殘留鎖(持有者 pid 已不存在); 之後的 `--lock` 執行不會自動搶, 只是一直等(日誌甚至尚未建立, 容易誤判為卡住)。確認持有者 pid 已死且 owner 是自己(`owner=w-web-perm`)後, 刪除自己的殘留鎖目錄即可; 他人的鎖不動。
- **全套單一行程結果(2026-10-20 run01)**: 修後第 1 次 `npm test` 536 過／0 敗, 74 分 33 秒(基準 387 過／24 敗, 84 分; 新增 `e2e-array-form` 7 案＋14 次檔尾還原約 +5 分, 其餘為 unit 新增); 外審後的 2 次改碼(缺 mode、AND 保留、name 去除、crules 轉型)各使已跑的全套作廢重來(17:05 與 17:18 兩次中止), 教訓: **外審要在起全套之前做完**, 不要與全套並行(80 分鐘的全套被外審結果推翻是最貴的返工). `cgrups`／`cpemis` 同名重複元素(伺服端任一啟用即授權, 編輯器後者覆蓋)與「群組元素缺 mode」(物件形式亦然, 既有)皆以測試固定其現況(DF-005／DF-006), 日後有人改解碼會看到差異.
- **欄位值純量(第 92 項②)**: 四表 schema 型別只有 `STRING`／`INTEGER`／`TEXT`, 無合法物件型欄位, 預檢集中在 `validateRowsBeforeWrite`(唯一共用點)加一道 `isScalar` 即同時覆蓋兩條寫入路徑; 站點不變式 `SITE-NS-001` 守「寫入呼叫只在兩檔、皆在驗證之後」. 既有 `VR-007` 曾以斷言「物件欄位不驗」固定舊行為, 改為標記「R-FIELD-SCALAR-01 起改為拒絕」而非靜默刪除; `VR-OI-003` 的物件／陣列 `length` 同理改判 `fieldNotScalar`.
- **換行風格逐檔不同, 腳本式插入前先判**: 本機 `grep -c $'\r' 檔` 在 Git Bash 下對 LF 檔也回「行數」(MSYS grep 文字模式), 不可信; 判換行用 `git ls-files --eol 檔`（`w/lf`／`w/crlf`／`w/mixed`）。本倉工作樹有 LF 檔(多數)與 CRLF 檔(如 `VeCrules.vue`、`mShare.mjs`、`README.md`), 以腳本在 LF 檔插入 `\r\n` 會留下 `w/mixed`（本輪曾發生於四個 .vue, 已修回）; 改完以 `git ls-files --eol -m` 全檢。
- **第三輪外審(sol, 2026-10-20)補查的三個邊界**(讀碼屬實; 進度與待裁示見 `tmp/run89/risks.md` 11～13): ①空字串名稱——編輯器路徑 `ckKey(rows,'name')` 以 `isestr` 拒收, 但 `syncAndReplaceTabs` 只驗主鍵, `name:''` 可入庫且伺服端 `arrFinder` 以 `===` 採納, 編輯器解碼一律視為無效, 存檔移除該授權; 凡在編輯器以 `isestr` 當「合法名稱」判準, 都要先確認寫入端是否真的擋了; ②「捨 OR 支只會變小」僅在整組只有**一個** AND 名稱時成立(`PR-005` 固定): 有第二個 AND 名稱時 `mergeRules` 的 AND 合併初值會從 OR 聯集改為首個 AND 支, 不換序亦增權——「單調」類論證須先寫出前提再窮舉, 且窮舉的**略過條件**本身要有對照測試; ③括號配對加逐行正規式的靜態判定器非 AST, 擋得住常見形狀, 擋不住刻意構造(`if (false)` 單獨成行、包在 `if(false){…}`、置於模板字串), 宣稱「無條件」前先寫清楚能力邊界。
- **修補腳本要可重跑**: 一次寫多檔的 `patch-*.mjs` 在第二個檔失敗時, 第一個檔已寫入; 重跑會把「以錨點字串前綴再插入」的編輯重複套用(本輪曾使 `PR-005` 重複)。腳本先判「新字串已在檔內則略過」, 或每檔單獨一支。

## 授權存檔不變: 保序、無損表示判定、清單頁解碼、同步名稱(2026-10-20 run02, ADR-031; 主控 run01 複審 R1～R6)
- **先求「授權到底依賴什麼」再設計**: 讀 `mergeRules` 得「沒有有效 OR 項時以第一個 AND 項為起始, 其餘 AND 只約束它含有的鍵」→ 結果對 AND 項順序的依賴只經「無 OR 時的第一個 AND 項是誰」(其餘 AND 項彼此可交換; `objAND` 只約束後項含有的鍵, 外審 minimax#3 更正我原先寫反的敘述)與同名雙模式; 這使「保序」(而非逐步比對)足以讓存檔不變, 並把無法無損表示的格縮到兩類. 判定函數 `getKpLossy` 先以 `tmp/run02/proto.mjs` 對原函式 `getUserRules` 窮舉(U = 存檔前後授權不等之格, D = 判定有損之格), 驗 **U ⊆ D、漏判 0** 後才入 `src/`; D ⊋ U(保守側)可接受, U ⊄ D 不可. 數字見 ADR-031(291,015 格).
- **夾具要能分辨「正確」與「碰巧正確」**: 初版關聯對話框保序夾具(`[g2 AND, g1 AND, M3 停用]`)在舊碼下也綠——`revRows` 每次自原字串重算, 刪除再加入同名不會移位, 重排只可能來自**解碼序**; 改為「停用在前之重複元素」`[g1 AND 停用, g2 AND, g1 AND, M3 停用]`(任何元素首次出現之序 ≠ 有效元素首次出現之序)後, 舊解碼才轉紅. 凡寫「修前紅」先確認夾具真的讓舊碼紅(跑一次紅測)再寫修法.
- **有損列的「不重寫」要另有停用項才測得到**: 關聯對話框以 `isEqual(解碼原值, 新值)` 決定是否改寫; 有損使用者只含啟用項時 `isEqual` 恆真, 不重寫是天然的, 守衛移除變異會存活. 夾具加一個停用項(`M3 n`/`P3 n`)使 `isEqual` 為假, 變異才轉紅.
- **測試編號不得與既有檔重名**: 新增 `LS-` 與 `unit-lockSave` 的 LS-001～005 撞名(帳本對照表以編號為鍵), 改 `KL-`; 動工前 `rg "'XX-0"` 查前綴.
- **e2e 變異借 harness 自己的 dev server**: 每次 mocha 重啟前後端(webpack 首編), 故不必等熱更新; 但變異執行期間不可編輯 src/test 其他檔(動到被測檔會污染)——文件類(spec/README/CLAUDE_*.md)可編輯.
- **清單頁解碼 + 物件形式原樣回傳同一參考** 使標準圖不變: 不重產標準圖的前提是「物件形式顯示逐位元不變」, 以 `cvKpToObj` 對無需修改者回傳同一參考為保證; 驗證用既有清單頁 e2e 全綠(比對標準圖).
- **`syncAndReplaceTabs` 與後台 `ckKey` 不對稱是授權缺口**: 後台拒收空名稱而同步不拒; 兩個寫入入口的名稱檢查要成對(`isestr`), 且置於 `delAll` 之前; 順手檢查既有測試是否倚賴「缺 id 由伺服器產生」(API-sync-017 的 `{order:0}` targets 列即是, 改以 users 驗內容判定).
- **外審與全套並行的代價(2026-10-20 run02 第三輪重演)**: 第三輪 minimax 與全套並行,審查回報時全套已跑 20 分鐘; 回報的 #1(停用→啟用 AND 名稱依既有位置成為第一個 AND 項)為語意級邊界, 修它須動 `keepKeyOrder`／`keyOrderOf`／`getKeyOrderLost`＋窮舉參考集, 全套作廢重跑會超出時限, 只能列待裁示. 外審的審查簡報若含「窮舉性質」(如 PR-004／PR-006), 請審查者另行檢查**參考集是否涵蓋『使用者變更』(啟用／停用／模式切換)而非只涵蓋『未變更存檔』**——本輪窮舉全是未變更存檔, 變更類狀態沒有進入空間表.
- **守門的「預期序」不可取自含停用者位置的參考**: 停用元素的位置只在被啟用後才影響授權, 預期序應只錨定「參考中有效之元素」; 取全部鍵序會把停用者的位置當成既成事實(第三輪 #1).
